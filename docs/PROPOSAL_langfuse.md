# Предложение: LLM-observability (Langfuse) для разбора инцидентов

Дата: 2026-07-29. Автор-черновик: R&D (WEB-2305). Решение - за командой/Рашидом.
Статус: предложение, НЕ внедрение. Это продуктовое решение вне скоупа WEB-2305.

## Проблема (что болит сегодня)

- Инцидент прилетает в телеграм: "странно, не было end_call со стороны агента".
- Причину ищем руками: `extra_scripts/incident_collect/collect_incident.py`
  (941 строка) собирает логи + Redis + БД по uuid звонка.
- Что именно LLM получил на вход и что вернул - не видно как связная картина.
  Промпты живут в коде и БД, версий у них нет.
- Нет ответа на "на какой версии промпта шёл этот звонок" и "сколько это стоило".

## Что даёт Langfuse

- **Трейс по одному id.** Открываешь звонок по call/session id - видишь вход,
  выход, вложенные шаги, время, токены. Замена ручного сбора логов.
- **Управление промптами.** Промпт становится версионированной сущностью со
  своей историей, а не строкой в коде/БД. Видно, какая версия шла на звонке.
- **Метрики и оценки.** Стоимость и латентность на вызов; можно вешать оценки
  качества (eval) на выборку звонков.
- **Без фреймворка.** SDK работает поверх прямых API-вызовов - LangChain/
  LlamaIndex тянуть НЕ нужно (их мы отдельно отклонили - ретрофит рабочего кода).

## Почему именно Langfuse (а не Phoenix/Helicone)

- Ядро **MIT**, self-host без лицензионных оговорок для внутреннего использования.
- Prompt-management закрывает вторую боль (промпты без версий) - у Phoenix слабее.
- Helicone - прокси в пути запроса: для realtime-голоса это риск задержки/отказа,
  поэтому отклонён. Phoenix - достойный запасной вариант, если Langfuse окажется
  тяжёл в эксплуатации.

## Честная цена (ops)

- Self-host Langfuse v3 = Postgres + ClickHouse + Redis + S3-совместимое
  хранилище. Postgres и Redis у нас уже есть; **ClickHouse и объектное
  хранилище - новые компоненты** в инфраструктуре (бэкапы, мониторинг, обновления).
- Это не "одна библиотека", а сервис. Для маленькой команды - заметная нагрузка
  на devops. Взвесить против экономии времени на разборах инцидентов.
- Интеграция в код: обернуть LLM-вызовы SDK-декоратором/контекстом - по одному
  сервису, аддитивно, без переписывания логики.

## Как пилотировать (минимальный риск)

1. **Начать с офлайн-сервиса, НЕ с realtime-движка.** Кандидаты: аналитика/judge
   в `backend/` (openai уже в зависимостях) или `asterisk-json-creator-llm`
   (офлайн-генерация). Realtime `cybernet3.0/llm/` (`async_llm_server`) - в
   последнюю очередь, там цена ошибки выше.
2. Поднять Langfuse в dev, обернуть LLM-вызовы одного сервиса.
3. Взять 5-10 реальных инцидентов из телеграма за неделю и разобрать их через
   трейсы вместо `collect_incident.py`. Замерить: быстрее ли, полнее ли картина.
4. Решение go/no-go по результату пилота: окупает ли экономия времени
   поддержку ClickHouse+S3.

## Что это НЕ меняет

- Не трогаем realtime-путь на пилоте.
- Не тянем LLM-фреймворк (прямые вызовы остаются).
- `collect_incident.py` остаётся, пока пилот не докажет замену.
- Связка с нашим skill `incident-flow`: шаг "собрать данные" сможет ссылаться на
  трейс Langfuse вместо ручного скрипта - но только после успешного пилота.
