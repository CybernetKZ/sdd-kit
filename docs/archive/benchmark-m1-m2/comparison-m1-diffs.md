# Сравнение решений WEB-2314: nude vs sdd-kit+tools (диффы, m1)

## Главное: два разных архитектурных решения одной задачи

Тикет: "прокинуть Internal RAG API в External gateway, не забыть авторизацию".
Обе армы добавили external-роуты `GET /external/api/v1/knowledge-base[/{uuid}]`
с ролями SUPERUSER/WORKFLOW_ENGINEER/ADMIN и `target_service: vac`. Дальше пути
расходятся радикально:

| | **nude** | **sdd-kit+tools** |
|---|---|---|
| Куда проксирует | **Публичное** приложение VAC (`VOICE_AGENT_URL`) | **Внутреннее** приложение VAC (`VOICE_AGENT_INTERNAL_URL`) |
| Кто скоупит по фирме | **VAC** (`has_cross_firm_access`): SUPERUSER/WE видят все фирмы, ADMIN - свою | **Gateway** (`scope_to_firm` флаг правила): пин фирмы в query + фильтрация ответа; кросс-фирмы нет НИ У КОГО |
| Что для этого понадобилось | Мост в **SSO**: KeyService пишет plain `userdata:{key_prefix}` (primary+replica), чтобы VAC разрезолвил API-key контекст как JWT | Новый секрет `VOICE_AGENT_INTERNAL_API_KEY` (гейтвей владеет кредом, клиентский X-API-Key срезается), fetch-then-filter |
| Обоснование выбора | Комментарий в config.py: "public app enforces firm scoping via user context, the internal one does not" | design.md D1: "VAC has no external mount (main.py:323)... the gateway is what makes the call external" |

**Армы "увидели" разные факты о VAC** - и обе задокументировали своё. Судя по
`va_endpoints_auth_rules.yml` (KB-роуты уже ходят на `VOICE_AGENT_URL` для
фронта), публичное приложение эти пути обслуживает - выбор nude реален, но
требует, чтобы VAC принял API-key-контекст (ради чего nude и полез в SSO).
Выбор sdd консервативнее: не доверять апстриму и запереть всё на гейтвее.

## Модель доверия и безопасность

**nude - делегирование + один настоящий vuln-фикс:**
- Нашёл и закрыл **дыру имперсонации**: клиентские `x-user-context` /
  `x-authenticated` / `x-auth-signature` раньше пролетали в апстрим как есть,
  а VAC не проверяет HMAC -> любой мог назваться кем угодно
  (`request_forwarder.py`: strip `GATEWAY_AUTH_HEADERS` + 2 теста). **В арме
  sdd эта дыра осталась открытой** - sdd срезал только `X-API-Key`.
- Fail-fast валидация правил на старте (`main.py` lifespan + `AuthRules`
  KNOWN_ROLES/empty-roles) + guardrail-тест "ни одно external-правило не
  даёт PUBLIC".
- Ценные NOTE-комменты: webapi-кэш никогда не хитует (и почему это "фича"),
  отзыв ключа не чистит Redis-ключи (TTL-время жизни отозванного ключа).
- Риск: **пишет в чужой namespace** (`userdata:` - контракт JWT-стратегии)
  из KeyService; прямой Redis-контракт между SSO и VAC становится шире и
  нигде не специфицирован (в нашем-то бенчмарке спек-стора!).
- Риск: кросс-фирменная видимость SUPERUSER/WE наружу через API-ключ -
  сознательное решение, но наружная поверхность с кросс-фирмой это
  сильное решение для external API.

**sdd - недоверие к апстриму, глухая изоляция:**
- `scope_to_firm` как декларативный флаг правила; пин фирмы в query
  (клиентский `firm_uuid` отбрасывается), повторная фильтрация тела ответа,
  fail-closed (объект без `firm_uuid` = чужой), 404-неразличимость чужих
  ресурсов, срез `x-total-count`/`x-page-count` (утечка агрегатов), отказ
  на non-JSON, upstream 401/403 -> 502 (не светить внутренний кред), 403 до
  апстрима при неразрешимой фирме.
- Ревью-панель (3 агента) поймала CRITICAL (NameError на старте) до сдачи.
- MINI-REPORT про VA-side дыру вместо чужого фикса - **по правилу репо**
  ("не чини чужое - запиши"); nude это правило дважды мягко нарушил
  (drive-by: rate-limiter fix в conftest, валидация правил шире тикета).
- Риск: fetch-then-filter - деталь чужой фирмы скачивается и отбрасывается;
  общий секрет на 6 окружений (helm values) = ops-бремя и одна точка
  компрометации; кросс-фирменных ролей нет вообще (может не совпасть с
  продуктовым ожиданием).

Оба набора сильные; sdd глубже по своей фиче, nude шире по поверхности
(имперсонация, валидация правил) + починил флейк всего suite.

## Ops-готовность

- nude: не требует новых секретов; обновил `web_api_authorization.md`
  (клиентская дока с firm-scoping семантикой). Helm не трогал - нечего.
- sdd: `.env.example`, helm values ×6 окружений, migration plan в design.md
  (провижининг ключа = ручной шаг до деплоя), Test-Cases doc, mini-report.

## Вердикт

**Мержить оба нельзя - они несовместимы по маршрутизации.** Решение сводится
к продуктовому вопросу, который тикет не задал: "должен ли external KB-доступ
уметь кросс-фирму для привилегированных ролей, и принимает ли публичный VAC
API-key-контексты?"

- Если да (и SSO-мост согласуют с владельцами VAC) -> **nude архитектурно
  чище**: одна точка enforcement (VAC), меньше кода на горячем пути, роли
  работают как на /va. Но SSO-мост обязан пройти отдельное ревью - запись в
  чужой Redis-namespace без спеки это именно то, от чего защищает spec-store.
- Если нет / быстро и безопасно -> **sdd**: самодостаточно, fail-closed,
  не трогает другие сервисы, но провижининг секрета в 6 окружений и
  отсутствие кросс-фирмы.

**Черри-пики в любом случае:**
- из nude -> sdd: фикс имперсонации (strip `GATEWAY_AUTH_HEADERS`) - это
  реальная уязвимость, она нужна независимо от выбора; startup-валидация
  правил + PUBLIC-guardrail; фикс rate-limiter в conftest.
- из sdd -> nude: 404-неразличимость и срез count-заголовков (если останется
  gateway-скоупинг где-либо); ревью-панель как практика - она единственная
  поймала CRITICAL до сдачи.

**Про подходы:** nude дал более широкое исследование системы (нашёл дыру в
соседнем сервисе и починил её), sdd дал более дисциплинированный продукт
(спека, дизайн-док с альтернативами, изоляция fail-closed, соблюдение правил
репо, самопроверка панелью). Это ровно та разница, которую и должен был
показать бенчмарк: свобода исследует, методология страхует.
