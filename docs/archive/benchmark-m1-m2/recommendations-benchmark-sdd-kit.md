Хороший вопрос, но сначала - неприятная правда о дизайне, потому что при текущем плане никакие метрики не спасут.

## 0. Проблема дизайна: n=1

Один запуск на арму = чистый шум. Разброс между двумя прогонами *одной и той же* армы на одной задаче легко составляет
2-3× по токенам и ±40% по размеру диффа. Любая разница, которую вы увидите на одном прогоне, будет неотличима от
случайности.

Минимально осмысленный вариант:

- **3-5 задач × 3 прогона на арму** (итого 18-30 сессий). Задачи разных типов: багфикс в одном файле, фича на 3-5
  файлов, рефакторинг/миграция. Гипотеза: sdd-kit почти не помогает на первом типе и сильнее всего - на третьем. Если
  мерить только на одной задаче, вы измерите не sdd-kit, а её тип.
- **Измерительные прогоны - в headless (`claude -p` с фиксированным промптом)**, иначе главным confounder'ом станет
  оператор: во второй арме вы уже знаете задачу и подсказываете лучше. Интерактивные прогоны делайте отдельно и только
  для оценки DX, не для цифр.
- **Чередуйте порядок** (A,B,B,A,...), а не "сначала все A, потом все B" - иначе latency API и ваша собственная усталость
  залезут в результат.

## 1. Метрики: пять уровней

Выберите **одну** первичную метрику заранее. Остальное - диагностика, объясняющая *почему*.

### L0. Результат (решающий уровень)

Без него всё остальное бессмысленно: агент, который сжёг в 3 раза меньше токенов и не решил задачу, "выиграл" по всем
cost-метрикам.

| Метрика                 | Как считать                                                                          |
|-------------------------|--------------------------------------------------------------------------------------|
| **Task success**        | Прошёл acceptance criteria из тикета: да/нет + градация (0/0.5/1)                    |
| **Human interventions** | Сколько раз человек вмешался и перенаправил. Лучший единичный прокси реальной пользы |
| **Rejected edits**      | Сколько правок вы отклонили (снимается автоматически)                                |
| **Time-to-mergeable**   | До состояния PR, который вы бы реально влили                                         |
| **Review rounds**       | Число циклов ревью до approve                                                        |

**Рекомендуемая первичная метрика: `$ на принятую задачу`** (cost / task_success). Она одна закрывает и стоимость, и
качество. Вторичная - число вмешательств.

### L2. Стоимость

Критично: **не суммируйте токены в одно число**. У четырёх типов разная цена (output дороже input в разы, cache read -
на порядок дешевле, cache write - дороже input). Разбивайте:

- `input` (uncached), `output`, `cacheCreation`, `cacheRead` - отдельно
- **`cost_usd`** - итог, уже с правильными весами
- **Cache hit rate** = cacheRead / (input + cacheRead). Тут будет самый интересный эффект: sdd-kit добавляет большой
  стабильный префикс (спеки, CLAUDE.md), который отлично кэшируется. Ждите роста cacheCreation и cacheRead с падением
  uncached input - по сырым токенам это выглядит как "стало хуже", по деньгам может быть лучше.
- **Стоимость генерации sdd-kit (шаг 4)** - обязательно посчитать отдельно и указать **break-even: сколько задач нужно,
  чтобы окупить.** Плюс частота регенерации при устаревании артефактов.

### L3. Процесс и контекст (объясняет разницу)

- Число turn'ов агента и число tool call'ов
- Разбивка tool call'ов: Read / Grep / Glob / Edit / Bash. Отношение **"прочитано файлов : изменено файлов"** - прямая
  мера точности наведения на контекст, и именно тут sdd-kit должен выигрывать
- **Число компактификаций и pre/post токены** - лучший индикатор давления на контекст
- Пиковое заполнение окна
- Число тупиковых ветвей (агент пошёл не туда и откатился)
- Ошибки API / retries - иначе спишете чужую latency на арму
- Wall-clock - самая шумная метрика, зависит от загрузки API и времени суток. Держите как справочную, не как основную

### L4. Качество кода (автоматизируемо, объективно)

- Собирается / линт чистый / типы чистые / тесты зелёные - **бинарные гейты, считаются до всякой субъективщины**
- Размер диффа: +/− строк, число файлов. Меньше ≠ лучше в вакууме - только в паре с task success
- **Scope creep**: файлы, тронутые вне ожидаемого blast radius (список ожидаемых файлов зафиксируйте *до* прогонов)
- Новые зависимости, новые абстракции/слои
- **Галлюцинации API**: число ошибок компиляции/импорта на несуществующие символы
- Дельта покрытия тестами по изменённым строкам
- Дельта цикломатической сложности, дублирование
- Соответствие конвенциям репо (частично ловится линтером, остальное - в рубрику)

### L5. Качество по рубрике (человек или LLM-судья)

Требует трёх вещей, иначе не считается:

1. **Рубрика написана до просмотра результатов** (корректность, читаемость, конвенции, качество тестов, "влил бы я
   это" - 1-5)
2. **Слепое ревью**: снять маркеры арм, перемешать диффы, ревьюер не знает, что где
3. Желательно ревьюер ≠ автор эксперимента

### L6. Стабильность

- Медиана + разброс (min/max или IQR) по трём прогонам, **не среднее по одному**
- Pass@1 vs pass@3
- Дисперсия размера диффа внутри армы - если внутри армы разброс больше, чем между армами, эксперимент ничего не показал

## 2. Как снимать это автоматически

Не считайте руками - Claude Code умеет отдавать почти весь L2/L3 через OpenTelemetry. Включается переменными окружения:

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
export OTEL_METRIC_EXPORT_INTERVAL=10000
export OTEL_RESOURCE_ATTRIBUTES="arm=sdd,task=WEB-2334,run=1"   # ключевое: тегируйте арму!
```

Последняя строка - самое важное для вашего кейса: `OTEL_RESOURCE_ATTRIBUTES` навешивается на каждую метрику и событие,
так что арму/задачу/номер прогона можно потом просто отфильтровать в бэкенде. Ограничения формата строгие: только
`key=value` через запятую, без пробелов внутри значений.

Что откуда берётся:

| Что нужно                                   | Источник                                                                                                                        |
|---------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------|
| Токены по типам                             | метрика `claude_code.token.usage`, атрибут `type` = `input` / `output` / `cacheRead` / `cacheCreation`                          |
| Деньги                                      | `claude_code.cost.usage` (USD); на событии `api_request` есть `cost_usd` и `cost_usd_micros`                                    |
| Токены/латентность на запрос                | событие `claude_code.api_request`: `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `duration_ms` |
| Число человеческих turn'ов                  | события `claude_code.user_prompt` (есть `prompt_length`)                                                                        |
| Отклонённые правки                          | `claude_code.code_edit_tool.decision`, атрибут `decision` = accept/reject, плюс `source`                                        |
| Tool call'ы, их длительность и объём вывода | `claude_code.tool_result`: `tool_name`, `duration_ms`, `success`, `tool_input_size_bytes`, `tool_result_size_bytes`             |
| Давление на контекст                        | `claude_code.compaction`: `trigger` (auto/manual), `pre_tokens`, `post_tokens`                                                  |
| Строки кода                                 | `claude_code.lines_of_code.count`, атрибут `type` = added/removed                                                               |
| Активное время (без idle)                   | `claude_code.active_time.total`, атрибут `type` = `user` / `cli`                                                                |
| Ошибки и retry                              | `claude_code.api_error`, `claude_code.api_retries_exhausted` (`total_attempts`)                                                 |
| **Реально ли сработал sdd-kit**             | `claude_code.skill_activated`: `skill.name`, `invocation_trigger` (`user-slash` / `claude-proactive`), `skill.source`           |

Последняя строка - отдельно подчёркиваю. Типичный провал такого рода инструментов: скилл установлен, но **ни разу не
активируется сам** (именно на этом развалился Ponytail в независимом тесте JetBrains). Через `skill_activated` вы это
увидите сразу, а не будете сравнивать арму B с ней же самой.

Если нужна максимальная гранулярность - есть beta-трейсинг (`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` +
`OTEL_TRACES_EXPORTER`), который даёт дерево спанов `interaction -> llm_request -> tool` с `ttft_ms` и токенами на каждый
запрос.

Для верификации: после запуска проверьте, что в бэкенд пришла метрика `claude_code.session.count`; если нет -
`claude --debug` покажет ошибки экспорта. Учтите, что цифры стоимости - приблизительные (для точного биллинга -
консоль).

Транскрипты сессий лежат в `~/.claude/projects/*/*.jsonl` и их можно парсить как fallback, но формат внутренний и
меняется между версиями - не строить на нём основной пайплайн.

## 3. Замечания по вашим шагам

**Шаг 1 (инвентаризация).** Кроме ручного обхода `~/.claude/`, снимите машинный список: события
`claude_code.plugin_loaded` и `claude_code.hook_registered` эмитятся один раз на старте сессии и дают полную опись
плагинов (с `has_hooks`, `has_mcp`, `plugin.scope`) и хуков (с `hook_source`: `userSettings` / `projectSettings` /
`policySettings` / `pluginHook`). Это и есть ваш baseline-снапшот, и им же потом проверите, что шаг 2 сработал. Плюс
`/status` и `/context` в интерактиве.

**Шаг 2 (отключить всё) - не удаляйте ничего.** Три варианта, от грубого к точному:

- `claude --safe-mode` (или `CLAUDE_CODE_SAFE_MODE=1` для headless) - отключает всё: CLAUDE.md, плагины, скиллы, хуки,
  MCP. Флаг появился в 2.1.169 и в CLI-reference он до сих пор не задокументирован, только в чейнджлоге. **Но для армы B
  он не годится**: он выключит и артефакты sdd-kit тоже.
- Изолированный `CLAUDE_CONFIG_DIR` - отдельный чистый конфиг на арму, глобальный ваш не тронут. Самый надёжный способ
  получить воспроизводимость.
- Точечно: `--setting-sources project` (отрезать user/local), `--strict-mcp-config --mcp-config ./mcp.exp.json` (только
  заданные MCP, игнорируя остальные источники), `--disable-slash-commands`, `--settings ./exp-settings.json`.

Для армы B нужен именно второй или третий вариант: глобальное окружение чистое, проектные артефакты sdd-kit живые.

Известный баг: `--strict-mcp-config` не переопределяет `disabledMcpServers` из `~/.claude.json` - если сервер там
числится отключённым, флаг его не поднимет. Проверьте по событию `mcp_server_connection`, что подключилось ровно то, что
вы ожидали.

**Отдельная арма C.** Добавьте третью: ваш реальный повседневный конфиг, без sdd-kit. Иначе вы измерите sdd-kit
относительно искусственно обеднённого окружения и не узнаете, не даёт ли ваша текущая настройка того же эффекта
дешевле - ровно тот исход, на котором Ponytail проиграл семисловному промпту.

**Шаги 4 и 6-7 - порядок у вас правильный,** и это стоит отметить: sdd-kit генерируется *до* выбора задачи, значит его
артефакты не могли быть подогнаны под конкретный тикет. Не меняйте этот порядок. Но лучше пойти дальше и **выбрать 3-5
задач заранее, до генерации**, зафиксировав список письменно - иначе появляется соблазн выбрать задачу, которая "хорошо
ложится" на sdd-kit.

**Шаг 6 (YouTrack MCP).** Вытащите тикет **один раз, вне измеряемых прогонов**, и вставляйте идентичный текст в обе
армы. Иначе MCP-сервер становится второй независимой переменной (разное число tool call'ов, разный объём вытянутого
контекста, разная стоимость), и вы не разделите вклад sdd-kit и вклад походов в YouTrack.

**Шаг 5 (два репозитория параллельно).** Прогоняйте **последовательно**, не одновременно: два клона одного бэкенда
подерутся за порты, БД и кэши, и вы получите испорченный wall-clock и падающие тесты. Плюс зафиксируйте и сверьте SHA
обоих клонов, и проверьте, есть ли в самом репозитории закоммиченный CLAUDE.md/AGENTS.md - если есть, он в обеих армах
одинаковый, это нормально, но должно быть записано.

**Шаг 8 (INIT.md:1-33).** Прогон по инструкции - это исполнение процесса, а не измерение. Если арма A выполняет
"свободный" промпт, а арма B - 33 шага структурированной процедуры, вы сравниваете не sdd-kit, а "процедура vs без
процедуры". Решите честно, что именно тестируете: **сам kit** (тогда промпт в обеих армах идентичный, различие только в
наличии артефактов) или **kit+методологию как продукт** (тогда так и назовите в выводах, и добавьте арму "просто хороший
промпт без kit" как контроль).

## 4. Зафиксировать письменно до первого прогона

Заполните это до старта и не меняйте потом - иначе интерпретация подстроится под результат:

1. Первичная метрика (одна) и порог, при котором вы признаёте sdd-kit полезным
2. Список задач + acceptance criteria по каждой
3. Ожидаемый blast radius по каждой задаче (для scope creep)
4. Рубрика качества, 1-5 по осям
5. Определение "вмешательства" и "попытки"
6. Модель, effort, permission mode, версия Claude Code, SHA репо - одинаковые везде
7. Что делаем с прогонами, где агент вообще не справился (исключаем? считаем как 0?)
8. Стоимость генерации sdd-kit и целевая точка окупаемости

И заранее договоритесь о честном исходе: вполне вероятный результат - "на односложных багфиксах хуже, на многофайловых
фичах лучше, окупается с N-й задачи". Это полезный вывод. Ответ "в целом лучше на 30%" по одному прогону - нет.
