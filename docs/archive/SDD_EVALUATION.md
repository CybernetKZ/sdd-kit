# Оценка SDD-кандидатов: карточки, матрица, финальный список кандидатов

Статус: готово (кабинетный обзор - разбор по документам и коду, без запуска в бою).
Дата: 2026-07-27.

Как оценивали. Читали исходники и промпт-шаблоны клонов в `refactor_v4/`. Также читали
GSD и ECC, установленные в системе (через субагентов Fable/Opus). Плюс сравнивали
с нашим внутренним эталоном `conversation_flow`. Каждое утверждение опирается
на файл и строку в репозитории кандидата или на `OUR_PATTERNS.md`. Что проверить
не удалось - помечено "(не проверено)". Версии кандидатов взяты по HEAD локальных
клонов. Исходный проект на GitHub мог уйти вперёд, см.
`spec-compare/docs/reassessment-2026-07-23.md`.

Пояснения к терминам, которые встречаются дальше:

- **brownfield** - работа с уже существующим кодом, а не с проектом с нуля.
- **delta-спека** - спека, описывающая только изменение, а не весь функционал целиком.
- **гейт** - автоматическая проверка, которая блокирует работу, если условие не выполнено.
- **bus factor** - проект держится на одном человеке.

## 0. Итог за 30 секунд

Главный фильтр: инструмент должен работать с существующим кодом и с несколькими
репозиториями.

- Фильтр проходит полностью только OpenSpec.
- Условно проходят GSD и наш паттерн conversation_flow - как слои внутри одного репозитория.
- spec-kit, BMAD, cc-sdd и superpowers фильтр проваливают.
- Провалившие выбывают из финального списка кандидатов. Сумма баллов при этом не важна.

**Рекомендуемый стек из слоёв.** Слои закрывают четыре узких места из постановки задачи.

**Слой 1. Без спеки код не пишется**

- Инструмент: **OpenSpec** - delta-спеки (описание только изменения).
- Проверка в CI: `openspec validate --all --strict --json`.
- Почему: единственная машинно-проверяемая модель дельта-изменений.

**Слой 2. Контекст и карта репозитория**

- Файл контекста: тонкий **AGENTS.md/CLAUDE.md**, не длиннее 500 строк.
- Карта модулей: в стиле раздела 14 документации conversation_flow (либо GSD map-codebase).
- Первичное наполнение спек: **ecc:spec-miner**.
- Почему: 3.75 поисковых вызова на одну правку - измеренная боль.

**Слой 3. Контракты между сервисами**

- Хранилище: **центральный OpenSpec-store** для контрактных спек.
- Схемы: закреплённые OpenAPI и redis JSON.
- Проверка в CI: contract-тесты.
- Почему: ось WBN↔VA даёт 35% тикетов VA; сырьё уже есть (файлы `CONTRACT_*.md`).

**Слой 4. Ревью и гейты**

- Единая CI-точка: **`make test`** по образцу conversation_flow.
- Автоматическое ревью кода агентами: **ECC-ревьюеры** (python/fastapi/database) на границе PR.
- Доноры промптов: review-механика superpowers и cc-sdd.
- Почему: `make test` в CI - единственный работающий у нас пример принуждения.

Ни один инструмент не покрывает больше двух слоёв. Это подтвердилось.

## 1. Карточки кандидатов

Каждая карточка идёт по одной схеме: механика -> фильтр -> принудимость ->
порог входа и живучесть -> цена цикла -> agent-agnostic -> покрытие четырёх узких
мест -> вердикт.

### 1.1 OpenSpec v1.6.0 (`refactor_v4/openspec`) - ПРОХОДИТ ФИЛЬТР

**Механика.** 12 скиллов и слэш-команд: `/opsx:explore -> propose -> apply -> sync -> archive`
(`src/core/profiles.ts:14-32`). Модель из двух каталогов. `openspec/specs/<capability>/spec.md` -
накопленная истина. `openspec/changes/<id>/` - дельта: proposal.md, дельта-спеки,
design.md, tasks.md и машинные метаданные `.openspec.yaml`
(`src/utils/change-utils.ts:122-182`).
Грамматика дельт - `## ADDED|MODIFIED|REMOVED|RENAMED Requirements`
(`src/core/parsers/requirement-blocks.ts:166-169`).
`openspec archive` - механический движок применения дельт. Запись двухфазная:
сначала всё пересобирается в памяти, потом перевалидируется, потом пишется
(`src/core/archive.ts:471-518`). Порядок применения - RENAMED->REMOVED->MODIFIED->ADDED
(`src/core/specs-apply.ts:286`). Если MODIFIED теряет сценарии, будет жёсткая ошибка
(`specs-apply.ts:360-365`).

**Существующий код и несколько репозиториев.** Работа с существующим кодом -
центр дизайна: "You do not document your whole codebase to start... specs only for what
you're about to change" (`docs/existing-projects.md:3,33`). Массовую конверсию старых
документов автор отвергает осознанно (`:88-92`). Несколько репозиториев закрываются
через **stores (beta)**. Это отдельный репозиторий планирования, который регистрируется
на машине по имени (`docs/stores-beta/user-guide.md:23-26`). Есть `references:` -
read-only индекс чужих спек. Контент не инлайнится, лимит ≤50KB
(`src/core/references.ts:1-10,431-446`). Оговорки две. Первая: "no sync, ever" -
свежесть держится на git pull (`user-guide.md:327-329`). Вторая: извлечения спек
из кода нет - так решено по философии.

**Принудимость - лучшая в наборе.** Есть настоящие Zod-схемы: `why.min(50)`,
`deltas.min(1).max(10)` (`src/core/schemas/change.schema.ts:10-38`) и правило
"Requirement must have at least one scenario" (`base.schema.ts:4-19`).
Команда `openspec validate --all --strict --json` даёт машинный JSON-вердикт
и exit 1 при ошибках (`src/commands/validate.ts:365,382`). Таблица exit-кодов
описана в `docs/agent-contract.md:88-125`.

**Три дыры, закрывать самим:**

1. Валидируются только дельта-спеки. proposal и tasks не проверяются (`validate.ts:282`).
2. Флаг `--strict` почти не влияет на changes.
3. Есть обходы: `archive --no-validate`, `--skip-specs`, zero-delta
   (`archive.ts:309-310,378-387`).

CI и hooks в комплект не входят. Свой `ci.yml` OpenSpec даже не гоняет validate
на собственных спеках.

**Порог входа и живучесть.** Лёгкий путь объявлен машинно: `skip_specs: true`
в `.openspec.yaml` для рефакторинга и тулинга (`src/core/change-metadata/schema.ts:36-41`).
Это примерно 2 LLM-прохода. Полный цикл - 4 прохода.
Исходный проект на GitHub: 695 коммитов, последний 2026-07-23, лицензия MIT.
74% коммитов сделал один человек (Tabish Bidiwale, git shortlog) - то есть
проект держится на одном человеке.

**Agent-agnostic.** 28 адаптеров, включая claude, codex, cursor, cline
(`src/core/command-generation/registry.ts:46-73`). Файлы-результаты - обычный markdown и YAML.

**Покрытие четырёх узких мест.** (a) гейт "сначала спека, потом код" - **да**.
(b) карта - частично: каталог specs/ - живая карта capability, но якорей код↔спека нет.
(c) контракты - частично: спеки через stores и references есть, contract-тестов нет.
(d) авто-ревью агентами - **нет**.

**Вердикт.** Единственный кандидат, который переживает фильтр. И единственный,
кто даёт CI-гейт одной строкой. Слабости - нет ревью, нет contract-тестов,
нет майнинга спек, stores в бете, проект на одном человеке. Всё это закрывается
другими слоями стека.

### 1.2 GSD v1.28.0 (`gsd-core` + системная установка) - проходит условно

**Механика.** Сначала map-codebase: 4 маппера дают 7 документов в `.planning/codebase/`
(`workflows/map-codebase.md:118-127`). Затем new-project. Дальше на каждую фазу:
discuss -> plan (researcher + planner + plan-checker, ревизионный цикл ≤3,
`plan-phase.md:1204`) -> execute (executor на план, волнами; verifier пишет VERIFICATION.md) ->
verify-work (UAT).

**Существующий код и несколько репозиториев.** Живая карта - лучшая из всех.
Есть инкрементальный ремап `--paths` со штампом `last_mapped_commit`
(`map-codebase.md:30-49`). И есть **гейт на дрейф после execute, который автоматически
перезапускает маппер** (`execute-phase.md:950`).
Для нескольких репозиториев есть `new-workspace --repos` - копии или worktrees
плюс общий `.planning/`. Но это только техническая обвязка без логики.
Кросс-репо модели контрактов нет.
Извлечения спек из кода тоже нет: ingest-docs читает только уже существующие документы.

**Принудимость.** Есть явная таксономия гейтов (`references/gates.md:9-57`).
plan-checker выдаёт блокирующие ошибки структурированным YAML
(`agents/gsd-plan-checker.md:141-148`).
verifier проверяет машинные `must_haves` из frontmatter плана, а TBD/FIXME - жёсткий
блокирующая ошибка (`agents/gsd-verifier.md:151-156,464`). `gsd-tools` - детерминированный Node CLI
с JSON-выводом.
**Но** hooks только советуют: "SOFT guard - advises, not blocks"
(`hooks/gsd-workflow-guard.js:6-12`). Единственный блокирующий hook (Conventional Commits)
включается вручную (`gsd-validate-commit.sh:3-9`). CI-интеграции нет.
Не запустил `/gsd:*` - ничего не сработало.

**Порог входа и живучесть.** Есть лестница: `/gsd:fast` (без PLAN.md, ≤3 файла) ->
`/gsd:quick` -> полный цикл. Это лучший "малый путь" в наборе.
Исходный проект на GitHub: 4770 коммитов, последний 2026-07-27 (сегодня), лицензия MIT.
60% коммитов - один человек. Цена полного цикла высокая: 6-12 LLM-проходов на фазу.

**Agent-agnostic.** Runtime-shim примерно на 20 harness'ов (`map-codebase.md:72`),
файлы-результаты - markdown и YAML.

**Покрытие.** (a) да, но только внутри пути `/gsd:*`. (b) **да, лучшее**. (c) нет.
(d) частично: checker -> verifier -> UAT, но внешнего жёсткого блока нет.

**Вердикт.** Самая сильная архитектура гейтов и самая сильная карта. Но как
обязательный стандарт для команды, которая игнорирует конвенции, GSD не работает
без внешнего CI-слоя. Роль в стеке: опциональная дисциплина фаз для крупных фич,
плюс map-codebase как генератор карты - конкурент нашей карты из раздела 14
документации conversation_flow.

### 1.3 conversation_flow LIVING SPEC (внутренний эталон) - проходит как паттерн для одного репозитория

**Механика.** `docs/DOCUMENTATION.md` - 7504 строки, версия v1.55.0. Правило приоритета
над патч-историей записано в L5-8. Раздел 14 - аннотированное дерево проекта
на 241 строку, у файлов проставлены номера ТЗ (L5102-5342). Раздел 17 - changelog
примерно на 87 релизов, формат "[версия][дата] ТЗ №N + затронутые секции + тесты" (L5597).
Номер ТЗ сквозной. Заголовки секций несут провенанс: "ТЗ №49; заменяет №45, №46 отменён"
(L3444). Тесты лежат как `test_patchNN.py` - 62 файла, 1325 функций.

**Принудимость - единственный работающий у нас пример.** Проверено дословно.
`Makefile:210`: `test: lint-brand lint-migrations lint-ruff` плюс pytest.
`lint_brand.py` блокирует мерж (return 1, L114). `lint_migrations.py` запрещает
DROP/RENAME/NOT NULL без default и требует один alembic head.
`.github/workflows/ci.yml` гоняет `make test` на каждый pull_request.
Спеку охраняют тесты: `test_patch44.py:358-365` проверяет наличие секции
в DOCUMENTATION.md, а `:350` - что сам Makefile не разобрали.
**Дыра.** Нет generic-проверки "changelog дописан, версия поднята" (подтверждено grep).
Обновление спеки в DoD держится на прозе и ручных ассертах. Закрывается
примерно 50-строчным `lint_spec.py` по образцу `lint_migrations.py`.

**Ограничения.** Нескольких репозиториев нет по построению: один документ,
один счётчик ТЗ. Контракты - только `integration-guide.md` и `cybernetrag_openapi.json`,
причём OpenAPI авторитетен лишь для запросов (guide L8-11).
Начальная спека дорогая: 7504 строки - это steady state после 59 ТЗ.
Файл на грани поддерживаемости и целиком в контекст не влезает.

**Цена и переносимость.** 1-2 LLM-прохода на задачу плюс детерминированный `make test`
(примерно 60 секунд, 0 токенов). Максимально agent-agnostic: Markdown, Make и CI,
ноль зависимостей от Claude Code.

**Покрытие.** (a) частично - гейт на PR, спека после кода. (b) **да** - раздел 14
плюс CLAUDE.md. (c) слабо. (d) гейты - да, ревью - нет.

### 1.4 ECC v2.0.0 (установлен, `ecc@ecc`, commit ec92b528) - слой, не стандарт

**Механика.** 67 агентов, 271 скилл, 92 команды, 34 hook-скрипта. SDD-элемент здесь один:
`agents/spec-miner.md`. Он извлекает поведенческие спеки из существующего кода
**ровно в формат OpenSpec** (`openspec/specs/<capability>/spec.md`), с якорями
`enforced:`, `test:`, `Last verified: (commit)`. Бюджет - до 15 файлов на capability.

**Принудимость - решающая находка.** Под текущим профилем `ECC_HOOK_PROFILE=minimal`
(`~/.claude/settings.json`) активен **один** блокирующий хук: запрет
`git commit --no-verify` (`block-no-verify.js:541`, exit 2).
Всё остальное либо выключено логикой профилей (`scripts/lib/hook-flags.js:35-51`),
либо не блокирует в принципе. `quality-gate.js` **никогда не вызывает `process.exit`**
(L140-149), объявлен `async`, и по сути это просто форматтер: "Lint and type checks
are not part of this gate" (`commands/quality-gate.md:25-26`).
ECC умеет писать спеки через spec-miner, но ничто в ECC их не читает и не гейтит:
grep `openspec` по scripts/hooks/commands даёт 1 файл.

**Живучесть.** Shallow clone (1 коммит), поэтому активность исходного проекта
на GitHub - (не проверено).
Автор один. Установка от 2026-06-17. Рекомендация: закрепить коммит и вендорить то,
от чего зависим.

**Покрытие.** (a) нет. (b) слабо. (c) нет.
(d) ревью - **да**: code-reviewer с порогом уверенности и запретом на недоказанные
HIGH/CRITICAL, плюс ревьюеры python/fastapi/database. Гейты - нет.

**Вердикт.** Берём spec-miner для первичного наполнения спек по существующему коду
и 3-4 ревьюеров.
Вызывать ревьюеров надо с границы PR (CI или pre-push), а не из Claude-хуков.
Профиль `strict` гейт "сначала спека, потом код" не покупает, зато добавляет трение:
`gateguard-fact-force` блокирует первую запись в файл.

Плюсы: самый живой исходный проект на GitHub в наборе (GitHub Inc., 1574 коммита, 263 автора,
последний 2026-07-24), 36 интеграций, lean-пресет.

### 1.7 cc-sdd 3.0.2 (`refactor_v4/cc-sdd`) - НЕ ПРОХОДИТ ФИЛЬТР

Стиль Kiro: 17 скиллов, цепочка steering -> discovery -> requirements (EARS) -> design ->
tasks -> impl -> validate.
**Нескольких репозиториев нет совсем**: grep `monorepo|multi-repo` по репозиторию
даёт 0 совпадений.
Дельта делается как merge-in-place без версионирования. Хуже того, шаги design и tasks
**задним числом проставляют `approved: true` вышестоящим документам**
(`kiro-spec-design/SKILL.md:129-134`).
Поле `spec.json.ready_for_implementation` мёртвое: его никто не читает и не пишет
(6 вхождений - это шаблоны и примеры).
`--profile minimal` тихо не работает: нет `-min` манифестов.
Исходный проект на GitHub: 429 коммитов, **последний 2026-04-27, то есть 3 месяца тишины**.
91% коммитов - один автор.
Цена запретительная: не меньше 3 субагент-диспатчей на каждую подзадачу,
батчинг запрещён (`kiro-impl/SKILL.md:87`). На фичу из 20 задач это 60-100+ вызовов.
**Сильное.** Лучший в наборе review-цикл implementer -> reviewer -> verify.
Вердикт парсится строго (`kiro-impl:134-135`), требуется evidence фазы RED
(`kiro-review:86-88`), есть анти-рационализационная таблица. Плюс концепт `steering/`
(product/tech/structure).
**Вердикт.** Выбывает. Донор: механический чеклист kiro-review и структура steering.

## 4. Финальный список кандидатов и как стек ложится на 5 репозиториев

**Финальный список кандидатов: OpenSpec (79.5) + CF-паттерн (77.0) + GSD (58.5, опционально).**
ECC - обязательный донор слоя ревью, но не самостоятельный кандидат.

Раскладка по репозиториям:

1. **Каждый из 5 репозиториев** получает: `openspec/` (specs и changes); тонкий
   AGENTS.md как canonical плюс CLAUDE.md-симлинк, до 500 строк (ADR-0002);
   `make test` как единую точку (lint-стек репозитория + `openspec validate --all --strict` +
   pytest); CI-workflow на pull_request с обязательным check (ADR-0003).
2. **Центральный store-репозиторий** (`openspec store`) держит контрактные спеки
   пересекающихся поверхностей: frontend `api/v1`, external WebAPI, redis
   keys/json/streams cybernet3.0. Каждый репозиторий ссылается на него через
   `references:` (ADR-0001). Данные за центральность: 60 кросс-репо тикетов
   сосредоточены в оси WBN↔VA (35% тикетов VA). Контракт "внутри одного репозитория"
   осиротил бы именно их.
3. **Первичное наполнение** делаем через `ecc:spec-miner` - по одной capability на репозиторий,
   до 15 файлов за проход. Он заполняет `openspec/specs/` из кода.
   Полную bulk-конверсию не делаем. Так велит философия OpenSpec
   (`docs/existing-projects.md:88-92`), и она совпадает с нашей практикой
   living-документов.
4. **Мелкие задачи** (медианный PR - 3-7 файлов) идут через `skip_specs: true`.
   Это машинно объявленный лёгкий путь вместо тихого обхода.
5. **conversation_flow** остаётся на своём LIVING SPEC - работает, не трогаем.
   Добавляем ему `lint_spec.py` (generic-проверка changelog и версии) и reference
   на `openspec`-store для своих внешних контрактов.
6. **Крупные фичи и миграция WEB-2303**: опционально накрываем GSD-дисциплиной фаз
   поверх файлов-результатов OpenSpec. map-codebase уже установлен. Решение отложено до пилота.

Что строим сами (бюджет "клея", по карточкам):

- CI job плюс запрет `--no-validate` и zero-delta archive - это дыры OpenSpec;
- валидатор proposal и tasks: OpenSpec их не проверяет (`validate.ts:282`);
- `lint_spec.py` для CF-паттерна, примерно 50 строк по образцу `lint_migrations.py`;
- contract-тесты по закреплённым схемам (слой 3);
- PreToolUse-hook "нет активного change -> нет правки кода" (ADR-0003, вторичный контур).

### 5.1 spec-kitty v3.2.6 - дочитан по исходникам, отклонён (2026-07-27)

Раньше он был отклонён только потому, что не был склонирован. Теперь клон прочитан
(`refactor_v4/spec-kitty`, HEAD от 2026-07-27). Вывод не изменился: отклонить.

Что в нём хорошо (честно):

- Самый жёсткий гейт "сначала спека, потом код" из всех кандидатов. Порядок работы
  зашит в машину состояний: код нельзя начать, пока нет spec.md, plan.md и tasks.md
  (`src/doctrine/missions/software-dev/mission.yaml:33-58`).
- Настоящая автоматика git-worktree: отдельная рабочая копия на каждый пакет работ
  (`src/specify_cli/core/vcs/git.py:115`).
- Канбан-доска и журнал событий по каждому пакету работ (`status.events.jsonl`).

Почему всё равно отклонён:

- Проваливает наш главный фильтр, теперь это подтверждено кодом. Спеки живут внутри
  одной "миссии" и умирают вместе с ней (архивируются). Накопленного живого свода
  спек, как в OpenSpec, нет. Извлечения спек из кода нет. Поддержки нескольких
  репозиториев нет - только монорепо (`docs/adr/3.x/2026-05-18-1-monorepo-charter-scope.md`).
- Очень дорогой цикл: минимум 7 проходов LLM на одно изменение против ~3 у выбранного
  стека. Лёгкого пути для мелкой правки нет вообще.
- Неподъёмная платформа: 335 тысяч строк Python, около 100 команд CLI. Это треть
  размера всей нашей кодовой базы - ради инструмента процесса.
- Опасная скорость поломок: 73% из 7 480 коммитов - один человек; 45 релиз-кандидатов
  на одну минорную версию; между версиями нужны миграции данных (`spec-kitty migrate`).
- Его сильные куски (worktree, канбан) нельзя забрать отдельно - они работают только
  внутри всей машины состояний. Worktree-изоляцию мы получаем бесплатно средствами
  git и Claude Code.

## 6. Ограничения этого обзора

- Это кабинетный обзор. Цены циклов даны в проходах, не в токенах и не в минутах.
  Замеры будут в пилоте.
- Версии взяты по HEAD клонов. У spec-kit и superpowers исходные проекты на GitHub
  дрейфуют быстро (`reassessment-2026-07-23.md:55-59`).
- Активность исходного проекта на GitHub у ECC - (не проверено): shallow clone.
- Статистика Skill-вызовов не видит активаций через hooks и слэш-роутинга
  мимо Skill tool.
