# Где и как проверяем логику сервиса (WBN)

Статус: анализ выполнен 2026-07-27. Это продолжение WEB-2305, уже после ADR-0001...0005.

Вопрос был такой: что становится источником истины при проверке логики. Варианты - graphify, `OVERALL LOGIC_240526.md`,
`POST_CALL_PROCESSOR_LLM_REDIS_CONTRACT.md` или что-то ещё.

Все утверждения ниже проверены по файлам и коду. Там, где проверки не было, стоит пометка.

## Ответ коротко

Главная мысль: проверка логики - это цепочка. Одного документа не хватит.

Ниже роли участников. "Гейт" здесь означает автоматическую проверку, которая блокирует мерж.

| Источник                                                                             | Роль в стеке                                                                                                                                  | Гейт?                                                     |
|--------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------|
| `POST_CALL_PROCESSOR_LLM_REDIS_CONTRACT.md`                                          | **флагман контрактного store** -> машинный реестр ключей + генерируемые contract-тесты                                                         | да (CI)                                                   |
| `TELEPHONY_IN_REDIS_STREAM_CONTRACT.md`                                              | контрактная половина -> JSON Schema + матрица кодов в store; половина с эксплуатационной шпаргалкой - отдельно                                 | да (CI), после починки дрейфа                             |
| `OVERALL LOGIC_240526.md` (+ POST_CALL_PROCESSOR_LLM_LOGIC, CALL_CAMPAIGN_LIFECYCLE) | **вход для spec-mining (автоматическое извлечение спек из кода)** -> `openspec/specs/<capability>/spec.md`; после майнинга - обзор со ссылками | нет (сырьё)                                               |
| graphify                                                                             | навигация/контекст (triage при майнинге, blast-radius при ревью)                                                                              | **никогда** - граф содержит INFERRED-рёбра, это не оракул |
| Существующие pytest e2e (pcp: 94 файла / 1478 функций)                               | исполнитель проверок - уже покрывают сценарии OVERALL LOGIC, не хватает только якорей на спеки                                                | да, когда попадут в CI                                    |

Пояснение к таблице. Извлечение спек идёт и из существующего кода, и из документов.

## 1. Две блокирующие находки

Их надо починить раньше всего остального.

### Находка первая: папка `docs/` не входит в репозиторий WBN

Это вложенный клон другого репозитория - `github.com/octrow/cybernet-docs.git`. Он спрятан через `.git/info/exclude:31`.
Проверка простая: `git ls-files docs` возвращает 0 файлов.

`shared_docs/` - это второй клон, и он уже разошёлся с первым. Файл OVERALL LOGIC отличается на 1 592 байта, mtime
2026-07-01.

Итог: наша "авторитетная логика" живёт в личном репозитории. Она невидима для ревью PR и для любой автоматической
проверки.

Решение:

- контрактные части переезжают в центральный store (ADR-0001);
- результат извлечения спек кладём в `openspec/specs/` внутри WBN;
- `shared_docs/` удаляем.

### Находка вторая: тестов в CI нет вообще

В `.github/workflows/` девять workflow. Поиск `grep pytest|make test` по ним даёт 0 совпадений.

`Makefile:70-72` гоняет pytest только для `backend`. То есть 1 478 тестов post-call-processor и все e2e-тесты остаются
вне гейта.

Решение - это первый практический шаг ADR-0003: завести pytest в CI и расширить `make test` на все сервисы.

## 2. Оценка источников

### OVERALL LOGIC_240526.md - свежий, но это сырьё, а не контракт

- Имя файла обманывает. Frontmatter говорит: `created: 2026-04-29, updated: 2026-07-24` (строки 11-12). У файла 14
  коммитов. Это самый сопровождаемый документ в папке.
- Что внутри: кросс-сервисный boundary-контракт потоков. Цепочка BACKEND -> asterisk-json-creator -> call-dispatcher ->
  post-call/post-chat-processor. Есть цитаты с точностью до file:line.
- Документ сам объявляет себя подчинённым Redis-контракту. Строки 16-20: "любое расхождение - баг в этом документе". И
  честно несёт 3 маркера `⚠ TRACE` - это места известной лжи (строки 69, 210, 617).
- Машинная проверяемость низкая: это проза без markdown-заголовков. Зато нумерованные потоки ложатся почти один к одному
  на сценарии OpenSpec.
- Capabilities для майнинга: `call-campaign-lifecycle`, `telephony-consumption`, `post-call-processing`,
  `retry-scheduling`, `campaign-completion`, `external-call-campaign-api`.

### POST_CALL_PROCESSOR_LLM_REDIS_CONTRACT.md - сильнейший документ, почти готовый контракт

- Обновлён 2026-07-24, 11 коммитов. Frontmatter перечисляет 13 файлов-источников и golden-фикстуры (строки 16-32).
  Golden-фикстуры - это эталонные данные, снятые с реального стенда.
- Что внутри:
    - таблицы "константа -> шаблон ключа -> владелец";
    - матрица чтения и записи по 5 сервисам (строка 206);
    - инвентарь TTL (строки 107-204);
    - реестр дрейфа с точностью до file:line (строки 475-499).
- Из реестра дрейфа: ключи собираются f-string в `call-dispatcher-llm/monitor.py:125-128`; префикс `judge:report:` лежит
  в чужом keyspace; `CallCampaignSettings` определён **трижды** в трёх сервисах.
- Как конвертировать в store: файл `redis-keys.yaml` плюс 4 семейства генерируемых тестов. Первое - соответствие
  `settings.redis.*` реестру. Второе - линт "нет литеральных ключей". Третье - равенство JSON Schema трёх
  Pydantic-моделей. Четвёртое - валидация golden-фикстур.

### TELEPHONY_IN_REDIS_STREAM_CONTRACT.md - настоящий контракт, но самый дрейфующий

Проверенный дрейф против кода. Всё перечисленное - реальные расхождения.

- Строка 186 утверждает, что код 96 входит в `SUCCESS_TELEPHONY_CODES`. Это **ложь**. Файл
  `post-call-processor-llm/core/config.py:527-535` явно его исключает. При этом OVERALL LOGIC (строки 373-380) здесь
  верен.
- Строка 170: код 16 -> COMPLETED, без ретрая. Устарело после WEB-2298. Теперь это VOICEMAIL_REACHED и ретрай возможен.
- Строка 426 указывает модель по адресу `model/dataclass.py:297-314`. **Такого файла нет.** Реальный адрес -
  `schema/schema.py:321`. Вдобавок в документе пропущено поле `call_direction`.
- Все цитаты строк сползли на 8-20 строк.

Плюс половина файла - это шпаргалка по redis-cli (строки 29-114 и 429-577). Это эксплуатационная шпаргалка, а не
контракт.

Отдельная ирония. В `core/config.py:568-571` уже стоит баннер "WIRE-CONTRACT... drift MUST be flagged in review". Ревью
этот дрейф не ловит. А параметризованный тест строк на 20 поймал бы все четыре пункта сразу.

### graphify - работает, но это навигация

- CLI установлен в `~/.local/bin/graphify`. Кодовый граф WBN живой: работает `graphify watch`, обновление 2026-07-27 16:
  53, 38 846 узлов и 71 994 рёбер. Лог запросов показывает, что графом реально пользуются для навигации.
- **Ссылка в `~/.claude/CLAUDE.md` была битая.** Путь `~/.claude/skills/graphify` не существует. Реальный путь -
  `~/.agents/skills/graphify/SKILL.md`. Исправлено 2026-07-27.
- Граф документации в `docs/graphify-out/` стух: последнее обновление 2026-06-11. И собрался он частично - 5 из 14
  чанков failed. Его надо пересобрать или удалить. Сейчас это ловушка.
- Вердикт: у графа есть рёбра с провенансом INFERRED, то есть выведенные. Поэтому оракулом он быть не может. Его роль -
  triage при извлечении спек и `graphify affected X` при ревью. В CI не включать.

### Существующие тесты - покрытие уже есть, трассировки нет

- Объёмы: post-call-processor - 94 файла и 1 478 функций; backend - 118 файлов и 1 190 функций.
- Около 20 e2e-сценариев названы по поведению. Примеры: `test_e2e_retry_cycle_status_reason.py`,
  `test_e2e_call_campaign_completion_full_flow.py`. Они работают на golden-фикстурах, снятых с dev и анонимизированных.
  Схема фикстур версионирована и **цитирует OVERALL LOGIC** - см. `tests/fixtures/golden/_schema.md:8-14`.
- Но ссылок на `wbn-project-logic` во всех тестах pcp всего **3 штуки**. Недостающее звено - якоря вида
  `@pytest.mark.spec("post-call-processing/REQ-NNN")`.

## 3. Целевая цепочка проверки

```
логика (потоки)                        контракты (границы)
OVERALL LOGIC + *_LOGIC.md             REDIS_CONTRACT + TELEPHONY_IN (контрактная часть)
   │ извлекаем спеки                      │ переводим в машинные файлы store:
   │ (spec-miner; graphify - triage)      │ redis-keys.yaml, telephony-in.schema.json,
   ▼                                      │ telephony-codes.yaml, call-campaign-settings.schema.json
openspec/specs/<capability>/spec.md       ▼
   │ Requirement/Invariant + test-якоря   генерируемые contract-тесты в каждом репо
   ▼                                      (config==store, no-literal-keys lint,
pytest c @pytest.mark.spec(...)           schema-equality, golden-валидация)
   └────────────┬─────────────────────────┘
                ▼
   make test (все сервисы) + spec-coverage -> обязательный CI-check на PR
```

## 4. Порядок работ

1. Починить провенанс документов - это первая блокирующая находка про вложенный клон `docs/`. Пока она не решена, гейт
   слеп.
2. Завести pytest в CI и расширить `make test` - это вторая блокирующая находка.
3. Майнить **Redis-контракт первым**. У него максимум сигнала, он уже нормативен и уже несёт реестр дрейфа. Результат -
   store и contract-тесты.
4. Майнить OVERALL LOGIC вторым. Три маркера `⚠ TRACE` разрешить прямо в ходе майнинга, а не тащить в спеки.
   TELEPHONY_IN чинить по коду при конвертации: код 96, код 16 и WEB-2298, путь модели.
5. Проставить spec-якоря в примерно 20 существующих e2e-файлов. Поведение там уже покрыто. Не хватает только
   трассировки.
6. `docs/graphify-out/` пересобрать или удалить. Кодовый `graphify watch` оставить.

## 5. Прочий отмеченный дрейф

Это бэклог для store-тестов.

- `call-dispatcher-llm/monitor.py:125-128` - 4 ключа собираются f-строками, мимо `settings.redis.*`.
- `post-chat-processor/.../judge_service.py:327,351,384` - `judge:report:{chat_uuid}` лежит в общем keyspace с pcp.
- `CallCampaignSettings` - 3 независимых определения: call-dispatcher, asterisk-json-creator, backend.
- `TELEPHONY_CALL_KEY` (backend) против `TELEPHONY_CALL` (pcp) - один шаблон, два имени.
- `CALL_CAMPAIGN_LIFECYCLE_LOGIC.md` (2026-06-10) отстаёт от документа, который на него ссылается, - OVERALL LOGIC (
  2026-07-24). Вероятно, в нём нет WEB-2061 и WEB-2298 (не проверено построчно).
