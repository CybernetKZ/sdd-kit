# Глоссарий

Термины, которые в наших документах означали разное. Здесь - единственное значение.
Одна мысль на строку. Дата: 2026-07-30 (grill-сессия по WORKFLOW.md); дополнено 2026-07-31 (ADR-0012), 2026-08-01 (ADR-0015, ADR-0016) и 2026-08-03 (ADR-0019 и ADR-0020, grill-сессии по миграции conversation_flow и дедупликации); 2026-08-04 (ADR-0022 и ADR-0023, grill-сессии по ревизии текстов кита и подключению репозиториев).

## Процесс

- **RAISE** - наш внутренний intake-процесс (форма заявки + RICE + доска Voicebot+LLM, VB-A-92...96). Не useraise.dev и не научные RAISE. См. ADR-0009.
- **intake** - шаг 1 feature-flow: допрос тикета разработчиком/агентом. Подача и валидация заявки - это RAISE, не intake.
- **тир задачи** - light / standard / deep. Меняет глубину подготовки (гриль, исследование), не гейты. См. ADR-0010.
- **гриль** - допрос плана до имплементации: агент (opus/fable) задаёт вопросы, разработчик отвечает; без ответа - вопрос автору тикета. След: секция "Grill" в proposal.md change'а. Это практика, не устанавливаемый инструмент.
- **эпик** - разбит на YouTrack-задачи на intake; 1 задача = 1 PR (исключение: фикс уже принятой фичи едет по исходной задаче). Один change на весь эпик (ADR-0011); флаг над эпиком - по требованию, а не обязателен (ADR-0015); тесты пишутся один раз на change, handoff один - в конце (ADR-0013). Подозревать необъявленный эпик при прогнозе >1500 строк или >2 дней на PR (ADR-0012).
- **test-author** - агент кита (`templates/agents/test-author.md`, `model: sonnet`), который пишет падающие тесты по спек-дельте ДО реализации: один тест на `#### Scenario:`, трейсер `# spec: <requirement> / <scenario>`, AAA, подтверждённый RED. Нетестовые файлы не трогает. Владение фазой 3 человеком-QA - целевое состояние, не текущее (ADR-0016).
- **оспорить тест** - dev не правит чужой тест, а возвращает его на фазу 3 с аргументом "противоречит Scenario X"; арбитр - текст Scenario. Неясен сам Scenario - спек-дельта назад автору (ADR-0012).
- **executor** - агент кита (`templates/agents/executor.md`, `model: sonnet`), который выполняет утверждённый план: идёт строго по tasks.md change'а до зелёных тестов. Не правит тесты, не коммитит; любое отклонение от плана - стоп и отчёт оркестратору. Умные решения (диспуты, правка плана, ревью) остаются у оркестратора на модели сессии (ADR-0021).
- **провенанс гриля** - обязательная шапка секции `## Grill` в proposal.md: кто грилил (`plan-griller agent` или `session inline`), сколько вопросов, что изменилось в плане. Инлайн-гриль законен на standard-тире; на deep обязателен агент - шапка это показывает (ADR-0021).
- **handoff** - перевод тикета в `ready_to_test` + комментарий тестировщику до 1 абзаца. Для эпика - один, в конце. `ready_to_test` держит релиз: бесфлаговое не едет в prod без вердикта QA (чеклист релиза, ADR-0013). Не путать с CURRENT_HANDOFF.md (передача сессии агента).
- **TBD** - у нас это trunk-based development (ADR-0006). "Будет определено позже" пишем словами, не аббревиатурой.
- **тестовый режим** - файлы созданы, но не закоммичены в git. Это не staging.

## Подключение репозиториев (ADR-0023)

- **store фикс-путём** - cybernet-specs живёт ОДНИМ клоном на машину в `~/cybernet/cybernet-specs`; клонирует и регистрирует его install.sh --machine-only. Не сабмодуль (машинный реестр openspec: id → один путь) и не копия-подпапка (копии разъезжаются). Свежесть - ручной `git pull` («no sync, ever» by design).
- **граф в git** - `graphify-out/graph.json` коммитится: первый билд (LLM) один раз на команду, обновление `make sdd-index` (AST, без ключа) перед большим intake. Навигация, не гейт - ADR-0004 в силе.
- **Graph probes** - строка провенанса в proposal.md: какие символы planner прогнал через граф (или `graph absent: <почему>`). Честность вместо церемонии, как у гриля; не гейт.
- **local-first** - серверного CI нет вовсе (sdd-ci.yml/autoreview.yml в архиве кита); гейты только локальные: pre-commit, spec-guard, `--no-verify`-блокер, make sdd-check/sdd-test/sdd-review/sdd-flags. TBD-дисциплины - процесс-правило без автоматики.

## Тексты кита (ADR-0022)

- **канон процедуры** - skills (feature-flow/incident-flow): процедуру исполняет агент, поэтому её единственный полный текст живёт там. WORKFLOW.md - обзор (диаграммы, карта инструментов, grounding-таблица, статус), не второй экземпляр процедуры.
- **grounding-таблица** - таблица в WORKFLOW.md "правило/кусок -> ADR". Единственное место, где правило из промпта связывается со своим ADR: в самих промптах теги `ADR-XXXX` не живут, остаётся правило фразой.
- **shared block** - осознанный дословный дубль между backend-reviewer и database-reviewer (файл сабагента обязан быть самодостаточным). Помечается маркером `<!-- shared block: edit in sync with ... -->`; сборка из фрагментов не заводится.
- **языковая политика промптов** - текст промптов английский; вывод агента человеку (вопросы разработчику, комментарии YouTrack, пояснения findings, отчёты) русский; машинные теги/вердикты английские. Исключение: tools/cf/* остаются русскими (миграционные протоколы, заморозка после фазы 3 CF).

## Спеки

- **спека (capability spec)** - файл в `openspec/specs/<capability>/spec.md`. Описывает поведение prod.
- **change (дельта)** - активная папка `openspec/changes/<id>/`: proposal + спек-дельты + tasks. Архивируется в спеку, когда флаг включён в prod (ADR-0011).
- **спек-дельта** - Requirements + Scenarios (WHEN/THEN) внутри change'а; то, что QA валидирует и из чего пишет тесты. Слово "манифест" не используем - раньше означало то же самое (ADR-0012).
- **store** - наш центральный репозиторий cybernet-specs (только 4 внешних границы). Потребитель store - **агент**, а не машинный гейт: он читает спеки чужого сервиса на intake и планировании (`openspec show <spec> --type spec --store cybernet-specs`) вместо клонирования соседнего репо (ADR-0015). OpenSpec-фича `store` - механизм; SmartAndPoint ProjectStore - чужой отклонённый инструмент (ADR-0008).
- **LIVING SPEC** - `docs/DOCUMENTATION.md` в conversation_flow. С ADR-0019 ведётся ПАРАЛЛЕЛЬНО openspec-спекам: канон - openspec, агент генерирует обновление §/§17/версии из спек-дельты в тех же коммитах; при конфликте текстов прав openspec. Warn-проверка pre-commit остаётся постоянно.
- **tz-NNN** - id change'а в conversation_flow: сквозная нумерация ТЗ (продолжает счёт docs/patches, следующий №85). YouTrack-id, если есть, пишется в proposal.md, не в имя (ADR-0019).
- **патч (conversation_flow)** - легаси-формат ТЗ в `docs/patches/patchNN-*.md`; заморожен на №84 (ADR-0019). Все 83 конвертируются в `openspec/changes/archive/tz-0NN-*/`, оригиналы остаются.
- **вердикт** - словарь plan-стадии двухсостоянный и единый: `готово к реализации`/`требует правок` ≡ `PLAN HOLDS`/`FIX THE PLAN` (ADR-0020). Вердикт ревьюеров кода: Block только на CRITICAL, **HIGH = Warning** ("мерж с явным принятием риска", advisory-first ADR-0015); контракт вывода - paste-ready блок либо ровно `LGTM - no CRITICAL/HIGH issues`, всегда со строками `Tests checked:`/`Residual risk:`.
- **tz-review** - тонкий скилл payload'а CF (наследник patch-review): механический аудит change-документа ДО гриллера - формат, facts-vs-code грепом, brand-lint, номер; документ не правит, вывод - замечания + вердикт. НЕ дубль plan-griller (тот - интерактивный допрос с записью в `## Grill`); шаги идут парой: tz-review -> plan-griller (ADR-0020).
- **enforced: якоря** - ссылки на код в спеке, формат `path/to/file.py:ClassName.method` (путь от корня репо, символ после двоеточия); spec-lint резолвит путь и сверяет свежесть этих файлов с git diff. Якорь без пути не резолвится - спека уходит в MISSING.

## Гейты и проверки

- **блокирующий гейт** - проверка, мимо которой физически нельзя пройти. Сегодня такие только локальные: spec-guard (PreToolUse, exit 2), запрет `git commit --no-verify`, pre-commit с `make sdd-check`.
- **advisory-гейт** - проверка, которая честно краснеет, но ничего не держит. Сегодня это ВСЕ серверные проверки: sdd-gate, tbd-gates, autoreview - branch protection выключена, required check не назначен (ADR-0015). Красный advisory-гейт всё равно чиним; он не блок, а сигнал.
- **гейт** (без уточнения) - раньше означало "блокирующая проверка". Сейчас всегда уточняем, какой именно; warn-only проверки (spec-lint до SPEC_LINT_STRICT, секция audit в sdd-doctor) гейтами по-прежнему не называем.
- **make sdd-check** - локальная блокирующая проверка: AGENTS.md ≤500 строк + openspec validate + sdd-flags (spec-lint внутри - консультативный). Бежит в pre-commit.
- **sdd-gate** - тот же sdd-check в CI на PR. Задумывался как required check; сегодня required не назначен, то есть advisory (ADR-0015).
- **make test** - единая точка входа CI по ADR-0003: линтеры + sdd-check + pytest + контрактные тесты. Ещё не реализован ни в одном репо.
- **autoreview** - PR-ревью в CI: AI-ревью (скипается без токена первым же шагом). Мерж не блокирует - как и всё остальное в CI сегодня (ADR-0015).
- **tbd-гейты** - возраст ветки (2 дня warn / 5 дней красный) и размер PR (ADR-0006). Считают честно, мерж не держат: advisory (ADR-0015).
- **spec-guard** - PreToolUse-хук: код в guarded-путях не правится без активного change. Обхода нет ни для urgent, ни для light-тира.

## Ревью и приоритеты

- **ревью** - уточняем какое: ревью-агенты локально (`make sdd-review`), autoreview в CI, человеческое ревью PR.
- **CRITICAL/HIGH/MEDIUM/LOW** - severity находок ревью.
- **low/medium/high/critical** - приоритет баг-репорта RAISE. Другая шкала, не смешивать.
- **urgent** - категория RAISE: блокирует запуск клиента или риск потери клиента. Не "горит у стейкхолдера".

## Флаги

- **feature-флаг** - запись `имя -> expires` в `feature_flags.py`, включается переменной `FLAG_<NAME>=1` (по умолчанию выключен везде). Полный lifecycle - docstring `templates/feature_flags.py` + ADR-0007.
- **флаг - инструмент по требованию (dormant)** - ни один шаг процесса не требует заводить флаг (ADR-0015). Берём, когда работу действительно нельзя показывать: миграция фиксированного контракта, branch by abstraction, эпик, чей полуготовый вид не должен быть доступен в prod. "Эпик = обязательно флаг" больше не читаем как правило.
- **просроченный флаг** - `expires` в прошлом: 7 дней WARN, потом FAIL (`make sdd-flags`).
- **включение флага в среде** - открытый вопрос: где физически ставится `FLAG_X=1` на stage/prod (helm values? `.env` сервиса? переменные CI/CD?) и у кого туда доступ. Ответить до первого боевого флага (ADR-0015).
