# План презентации: переход разработки на Spec-Driven Development

Аудитория: команды разработки CybernetAI. Длительность: ~30-40 минут + вопросы.
Цель: объяснить, почему меняем процесс, что именно выбрали, как будет выглядеть
работа над задачей, и что меняется для каждого разработчика.

---

## Часть 1. Зачем это нужно (проблема)

### Слайд 1. Титульный
- "Переход разработки на процесс, управляемый спецификациями (Spec-Driven Development)"
- Контекст: подготовка к миграции на HubTalk, отказу от Asterisk, появлению новых сервисов.
- Задача Web-2305, дата, докладчик.

### Слайд 2. Как мы работаем сейчас - измеренные факты
(источник: OUR_PATTERNS.md, анализ git-истории четырёх репозиториев и 2 ГБ транскриптов агентов)
- Исправлений больше, чем новых функций: 33,2 % против 26,0 % по 1576 pull request.
- 18,4 % задач потребовали больше одного pull request - задачу переделывали.
  Худшие случаи: WEB-2001 - 9 pull request, WEB-1560 - 8.
- Размер pull request: медиана в web-backend-new 412 строк, но верхние 10 % - от 4221 строки и 62 файлов.

### Слайд 3. Дисциплина процесса - почему методички не работают
- Три разные стратегии слияния на четыре репозитория.
- Привязка к тикету: от 2 % (postcall-analytics) до 73 % (web-backend-new).
- 1780 коммитов в cybernet3.0 залиты в основную ветку мимо pull request - там же переделки 43,8 %.
- **Главный вывод:** договорённости без автоматических проверок у нас не выживают.
  Это измеренный факт, а не мнение. Поэтому основа нового процесса - автоматические
  блокирующие проверки, а не документ с правилами.

### Слайд 4. Четыре узких места
1. Неясные технические задания -> переделки после ревью.
2. Контекст: пять репозиториев, ~1 млн строк кода; агент не знает систему -
   3,75 поисковых запроса на одну правку, 95 % токенов уходит на чтение контекста.
3. Интеграционные ошибки между сервисами: ось web-backend-new ↔ voice-agent
   даёт 35 % задач voice-agent; контракты описаны в неформальных markdown-файлах
   без схем и без проверок.
4. Очередь на ревью и тестирование.

## Часть 2. Что выбрали (решение)

### Слайд 5. Как выбирали
- Рассмотрено 23 инструмента и методики (OpenSpec, spec-kit, BMAD, GSD, cc-sdd,
  superpowers и другие) - читали исходный код, а не рекламу.
- Главный фильтр: инструмент обязан работать с существующим кодом (не "с нуля")
  и с несколькими репозиториями. Фильтр полностью проходит только OpenSpec.
- Критерии с весами: работа с существующим кодом и несколькими репозиториями (30),
  принудительность проверок (25), порог входа и живучесть проекта (20),
  стоимость цикла (15), независимость от конкретного агента (10).
- Вывод: ни один инструмент не закрывает больше двух узких мест - собираем **стек из слоёв**.

### Слайд 6. Стек из четырёх слоёв
| Слой | Что закрывает | Инструмент |
|---|---|---|
| 1. Спецификация до кода | неясные задания, переделки | OpenSpec: дельта-спецификации + `openspec validate --strict` в CI |
| 2. Контекст и карта репозитория | агент не знает систему | тонкий AGENTS.md (≤500 строк, CLAUDE.md - символическая ссылка), карта модулей; первичное наполнение спецификаций - агент spec-miner |
| 3. Контракты между сервисами | интеграционные ошибки | центральный репозиторий cybernet-specs: спецификации контрактов (api/v1, внешний WebAPI, redis-потоки) + контрактные тесты в CI |
| 4. Ревью и гейты | очередь на ревью | агенты-ревьюеры (python / fastapi / database), единая точка `make test` в CI на каждый pull request |

### Слайд 7. Ключевые понятия (глоссарий для команды)
- **Дельта-спецификация** - описание только изменения, а не всей системы целиком.
- **Гейт** - автоматическая проверка, которая блокирует слияние, если условие не выполнено.
- **Контракт** - зафиксированная схема взаимодействия между сервисами.
- **Feature-флаг** - переключатель: код влит, но выключен, пока не готов;
  у каждого флага есть владелец, тикет и дата удаления.

### Слайд 7а. Без магии: что такое "скиллы", "правила" и "хуки" на самом деле
- "Скиллы", "правила", "плагины" - маркетинговые названия. На деле это тексты-инструкции
  (промпты), которые подставляются в контекст модели: в каждый запрос или в ключевые
  точки работы. Модель может их не выполнить - это совет, а не гарантия.
- Хуки (pre-commit, PreToolUse, PostToolUse) - обычный детерминированный код,
  привязанный к событиям (Claude Code или git). Пример: автоформатирование после каждой
  правки кода агентом. Выполняется всегда - проигнорировать невозможно.
- Следствие 1: принуждение строится только на детерминированном коде (хуки + CI);
  промпты - только совещательный слой.
- Следствие 2: **проверяемость обязательна.** У каждого скилла и инструмента должен
  быть способ убедиться, что он реально сработал. Непроверяемое - вычищаем
  (95 % из ~285 скиллов не использовались ни разу).

## Часть 3. Как будет выглядеть работа (рабочий процесс)

### Слайд 8. Путь задачи от заявки до слияния (схема из WORKFLOW.md)
0. **Приём заявки (процесс RAISE):** форма + приоритизация RICE -> тикет в YouTrack.
   Ошибки - сразу тикетом, без приоритизации, но с обязательными полями
   (окружение, шаги, ожидаемое/фактическое).
1. **Проверка задания:** сверить утверждения тикета с кодом и спецификациями;
   серьёзная развилка - вопрос автору, работа ждёт; мелкие пробелы - зафиксировать
   допущения и продолжить.
2. **План:** OpenSpec-изменение (предложение + дельта-спецификации + задачи);
   для сложных задач - "прожарка" плана: граничные случаи, откат, миграции.
3. **Тесты - от QA, до кода:** QA проверяет манифест (у каждого требования есть
   измеримый сценарий) и пишет тесты по сценариям до реализации; разработчики тесты
   не пишут. Тесты должны сначала упасть. Отдельный процесс: QA-SDD-PROCESS.md.
4. **Реализация:** ветка feature/WEB-XXXX от dev; код и спецификация меняются вместе.
5. **Проверка и ревью:** ручная проверка по документу тест-кейсов,
   `make sdd-check`, агенты-ревьюеры по диффу.
6. **Слияние и передача:** pull request -> блокирующие проверки CI -> слияние ->
   комментарий для тестировщика (что и как проверить).

### Слайд 8а. Прототип вместо ожидания
- Серьёзная развилка в задании - вопрос автору. Но пока ждём ответа, работа не обязана
  стоять: часто выгоднее собрать прототип по рекомендуемому варианту.
- Прототип - тоже артефакт: он явно помечен как прототип, к нему прилагается просьба
  проверить. Ответ автора либо подтверждает направление, либо прототип дёшево
  выбрасывается - это всё равно быстрее, чем простой.
- Задачи разные - путь разный: мелкую понятную правку делаем сразу по лёгкому уровню;
  сложную или рискованную - через полную проверку спецификаций (следующий слайд).

### Слайд 9. Три уровня задач - глубина подготовки масштабируется, проверки нет
| Уровень | Что добавляется / убирается |
|---|---|
| Лёгкий | минимальная спецификация (зачем + что + регрессионный тест); без "прожарки" плана |
| Стандартный | полный процесс со слайда 8 |
| Глубокий | + фаза исследования архитектуры с записью решения (ADR) |
- Важно: **проверки одинаковы на всех уровнях.** Спецификация существует всегда,
  тесты, ревью и CI - обязательны. Обойти нельзя даже для "мелочи" - именно мелкие
  задачи (медианный pull request - 3-7 файлов) чаще всего обходят правила.

### Слайд 10. Ветки, размер изменений и feature-флаги
(источник: REPORT_TBD_PROJECTSTORE.md, решения ADR-0006/0007)
- Оставляем схему "ветка -> pull request -> dev". Прямые коммиты в основную ветку -
  нет: они отключают все проверки.
- Новые дисциплины: возраст ветки (предупреждение после 2 дней, блокировка после 5),
  размер pull request (сверхбольшие - только с обоснованием в описании).
- Feature-флаги с обязательными полями "владелец, тикет, дата удаления";
  просроченный флаг: 7 дней предупреждение, потом блокировка сборки.
- Зачем флаги: миграция на HubTalk и отказ от Asterisk - большие замены делаются
  через прослойку и переключатель, а не через долгоживущую ветку.

### Слайд 11. Автоматические проверки - что именно блокирует
- Перед коммитом (локально): запрет правки кода без активного OpenSpec-изменения,
  линтеры, `make sdd-check`.
- На pull request (CI, блокирующие): `make test` = линтеры + проверка спецификаций +
  pytest + контрактные тесты; проверка возраста ветки и размера pull request.
- На pull request (CI, совещательные): комментарии агентов-ревьюеров.
  Блокирует только быстрая детерминированная проверка - чтобы ревью не заставляло
  копить большие изменения.

### Слайд 12. Инструменты на каждом этапе
- youtrack-mcp - чтение и комментирование тикетов из агента.
- OpenSpec - спецификации и изменения; cybernet-specs - контракты между сервисами.
- context7 - актуальная документация библиотек; Graphify - граф знаний по репозиторию.
- Агенты-ревьюеры + статический анализ (ruff, radon, semgrep и другие).
- Установка на машину разработчика - одним скриптом setup-dev.sh.

## Часть 4. Честность и план внедрения

### Слайд 13. Что отклонили и почему (важно для доверия к выбору)
- spec-kit, BMAD, cc-sdd, superpowers - не работают с несколькими репозиториями
  и/или проверки - только текст для модели, без реальной блокировки.
- "Чистый" trunk-based development (коммиты прямо в dev) - убирает точку,
  к которой прикреплены все проверки; уже пробовали в cybernet3.0 - результат на слайде 3.
- ProjectStore - "память проекта", а не хранилище спецификаций: нет поддержки
  нескольких репозиториев, проверка никогда не блокирует. Забрали две идеи, плагин не ставим.
- Платформы feature-флагов (Unleash и другие) - избыточны, пока не нужна
  процентная раскатка; свой реестр из одного модуля.

### Слайд 14. Известные слабости и как они закрыты
- OpenSpec: валидация с обходами, проект держится на одном человеке ->
  свои проверки в CI, запрет обходных флагов, закреплённая версия.
- Хранилища спецификаций (stores) в статусе "бета" -> используем с оговорками,
  свежесть - через git pull.
- Пороги (размер pull request, возраст ветки) - стартовые значения по репозиторию,
  калибруются по данным пилота.

### Слайд 15. Порядок внедрения
1. Чистка текущей обвязки агентов (более 95 % из ~285 скиллов не использовались ни разу).
2. В каждом репозитории: openspec/, тонкий AGENTS.md, `make test`, CI-проверка.
3. Первичное наполнение спецификаций агентом spec-miner - по одной способности за проход.
4. Центральный репозиторий контрактов; первые контракты - ось WBN ↔ VA и redis-потоки.
5. Метки размера и предупреждения возраста ветки - сначала без блокировки, спринт сбора данных.
6. Реестр feature-флагов; первый потребитель - работы по HubTalk / Asterisk.
7. Включение блокирующих порогов после замеров.
- Пилот: замеряем размер pull request и долю переделок до и после.

### Слайд 16. Что меняется лично для разработчика (итог)
- До кода - короткая спецификация изменения (для мелкой задачи - минимальная).
- Ветка живёт не дольше нескольких дней; большое изменение делится на части за флагом.
- Ревью начинают агенты, человек смотрит их выводы и дифф.
- Один вопрос вместо десяти правил: "зелёный ли `make sdd-check`?"
- Ожидаемый эффект: меньше переделок (сейчас 18,4 %), меньше исправлений
  (сейчас 33 % всей работы), быстрее контекст для агентов.
