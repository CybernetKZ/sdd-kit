# Методичка: SDD-стек CybernetAI (WEB-2305)

Обновлено: 2026-07-30. Решения - в `ADR/` (0001...0011), план внедрения (июль 2026) - в `archive/NEXT_STEPS.md`.
Схема всего процесса с точками подключения инструментов - `../WORKFLOW.md`.
Словарь терминов - `GLOSSARY.md`.

## Что это и зачем

Мы переходим на spec-driven development (SDD): поведение сервисов описано спеками,
изменения кода идут через изменения спек, правила проверяются автоматически.

Стек из четырёх слоёв:
1. **OpenSpec** - спеки и изменения в папке `openspec/` каждого репозитория.
2. **Центральный store** (`cybernet-specs`) - контракты между сервисами (redis-потоки, API).
3. **Гейты** - `make sdd-check` в CI на каждый pull request + хуки локально.
4. **Авто-ревью PR** - AI-ревью по нашим правилам (advisory; ruff-автофикс живёт в pre-commit).

## Установка на своей машине (один раз)

```bash
cd /путь/к/репозиторию && sdd-kit/install.sh --repo-only
```

(без флага `install.sh` дополнительно предложит поставить личные инструменты - см. ниже)

Скрипт идемпотентный: существующие файлы не трогает, ставит только недостающее.
Что он спросит и сделает:
- проверит git, node, uv; предложит поставить openspec CLI, если его нет;
- найдёт или предложит склонировать youtrack-mcp;
- если нет токена YouTrack - даст ссылку (https://cybernet.youtrack.cloud/users/me?tab=account-security),
  примет ввод скрыто и сохранит в `.env` сервера MCP (токен никогда не попадает в репозиторий);
- поставит: AGENTS.md (+симлинк CLAUDE.md), openspec/, Makefile.sdd, CI-гейт,
  авто-ревью, хуки, ruff.toml (только если у репо нет своего конфига ruff), .mcp.json;
- в конце сам прогонит проверку окружения и ревизию мусора (`make sdd-doctor`).

Обновление кита (вышла новая версия шаблонов - хуки, агенты, скиллы, CI):
```bash
cd /путь/к/sdd-kit && git pull
cd /путь/к/репозиторию && /путь/к/sdd-kit/install.sh --refresh
```
`--refresh` перезаписывает только файлы кита и печатает, что изменилось; `AGENTS.md`,
`.spec-guard-paths`, `feature_flags.py`, `ruff.toml`, `openspec/`, `.mcp.json` не трогает,
про разошедшийся `hooks` в `.claude/settings.json` предупреждает. Итог смотреть `git diff`
до коммита.

Подключение к store (если ещё не сделано):
```bash
git clone <store-repo> ~/cybernet/cybernet-specs   # когда появится боевой store
openspec store register ~/cybernet/cybernet-specs --id cybernet-specs
```

## Свежий клон бэкенда: запуск стека

sdd-kit ставит SDD-обвес, но НЕ секреты и НЕ поднимает контейнеры. Чтобы стек
реально работал на свежем клоне WBN:

1. **Скопировать реальные `.env` из рабочего клона** (в git их нет, в
   `.env.example` секретов нет). Для WBN это 8 файлов:
   ```bash
   SRC=~/cybernet/web-backend-new   # существующий настроенный клон
   for s in api-gateway-service asterisk-json-creator-llm backend \
            call-dispatcher-llm post-call-processor-llm post-chat-processor \
            sso-service validation-service; do
     cp "$SRC/$s/.env" "$s/.env"
   done
   ```
   `make sdd-doctor` предупредит, если какой-то `.env` забыт (профиль WBN
   проверяет наличие всех восьми; сами значения doctor не читает).
2. **Поднять контейнеры** - WBN и VA (WBN ходит в voice-agent-constructor):
   ```bash
   docker compose up --build -d                                   # в WBN
   (cd ~/cybernet/voice-agent-constructor-backend && docker compose up --build -d)
   ```
   Локальные оверрайды - в `docker-compose-local.yml`, если он нужен твоей задаче.

## Ежедневная работа

0. **Начинаешь таску WEB-\*?** Скажи агенту "новая таска WEB-XXXX" - сработает
   skill `feature-flow` (ставится kit'ом): допрос тикета против кода и спек
   (вопросы аналитику ДО кода) -> выбор тира -> план + гриль -> тесты до кода ->
   имплементация -> ручная проверка -> ревью -> PR -> передача тестировщику.
   **Инцидент из телеграма?** Дай агенту uuid звонка/кампании - skill
   `incident-flow` поведёт: собрать данные (collect_incident.py) -> док о причинах
   (баг / клиент / инфра; клиент или инфра - док и есть результат, стоп) ->
   план -> регрессионный тест ДО фикса -> фикс -> проверка против инцидента.
1. **Выбери тир задачи** (ADR-0010) - light / standard / deep:
   - light: мини-изменение (почему + что + регрессионный тест), без гриля и тест-дока;
   - standard: полный feature-flow;
   - deep: + исследование архитектурных вариантов (ADR) + обязательный гриль.
   Тир из тикета - по умолчанию; ты всегда можешь поменять; не задан - агент выберет сам.
   Тир и обоснование пишутся в change - ревьюер может оспорить.
   Гейты одинаковы на всех тирах: спека, тесты, sdd-check, ревью, CI. Обхода spec-guard нет.
2. **Перед правкой кода** - создай изменение: `/opsx:propose "WEB-XXXX: что меняем"`.
   Без активного изменения в `openspec/changes/` правка кода по защищённым путям будет заблокирована
   (файл `.spec-guard-paths` перечисляет, какие пути защищены).
   Standard/deep: прогрилль план (edge cases, откат, миграции, кросс-сервисные
   эффекты) и запиши вопросы+ответы секцией `## Grill` в proposal.md.
3. **Тесты до кода.** Тесты существуют ДО реализации - это требование
   процесса, CI-гейта на порядок нет. Пишет их **не тот, кто пишет
   реализацию**: агент `test-author` (ADR-0016) по спек-дельте change'а -
   один тест на `#### Scenario:`, трейсер `# spec: <requirement> / <scenario>`,
   подтверждённый RED. Ты гоняешь их локально по ходу реализации и не правишь:
   тест, который выглядит неверным, оспаривается через текст Scenario
   (ADR-0012). Валидация человеком-QA (`sdd-kit/QA-SDD-PROCESS.md`) - целевое
   состояние; пока её нет, в PR это помечается.
   Для light-тира RED = регрессионный тест, воспроизводящий баг.
4. **Пиши код и спеку вместе.** Спека - не бумажка после, а часть изменения.
   Эпик не влезает в ветку на 2 дня? Несколько маленьких PR под ОДНИМ change
   (ADR-0011). Feature-флаг тут - по требованию, а не обязательный шаг
   (ADR-0015): берёшь, если полуготовое состояние не должно быть доступно
   в prod. С флагом change архивируется, когда флаг включён в prod по
   умолчанию. Lifecycle флага - docstring `feature_flags.py` + ADR-0007.
5. **Коммить как обычно.** Хук pre-commit сам: прогонит ruff (автофикс + формат),
   поймает мусор (маркеры мержа, большие файлы, `breakpoint()`, токены и ключи,
   битые JSON/YAML/TOML, случайные сабмодули) и запустит `make sdd-check`.
   Прямой коммит в main/master/prod/stage заблокирован; в dev - предупреждение.
   Сознательный обход (редко!): `SDD_ALLOW_PROTECTED=1 git commit ...`.
   `git commit --no-verify` заблокирован отдельным хуком - не пытайся.
   Ветка разошлась с dev больше чем на 2 дня - хук предупредит: rebase или дели change.
   Сжался контекст агента или новая сессия? Агент сам читает
   `.claude/last-session-state.md` - пакет выживания пишется хуком перед сжатием.
6. **Открой pull request.** На PR бегут sdd-gate (`make sdd-check`) и
   tbd-гейты (возраст ветки: предупреждение на 2 дня, красная на 5; размер PR -
   лейблы `long-lived-ok`/`xl-ok` требуют строку "Why ..." в описании).
   **Мерж они сегодня не держат**: branch protection выключена, required check
   не назначен - это осознанное решение (ADR-0015). Красное всё равно чиним.
   Реально блокируют только локальные хуки (spec-guard, pre-commit, запрет
   `--no-verify`).
   Авто-ревью - совещательное: ruff-замечания строчными комментариями,
   AI-ревью одним комментарием (только CRITICAL и HIGH, по правилам из
   `.claude/agents/`); AI получает отчёт статических инструментов
   (radon, complexipy, vulture, semgrep) и обязан проверить каждую наводку
   по коду. Замечания разбирай как ревью, но мерж они сами не блокируют.
7. **После мержа в dev** (ADR-0011): переведи тикет в `status: ready_to_test`
   и оставь комментарий тестировщику - что и как проверять, КРИСТАЛЬНО просто,
   до одного абзаца; добавь имя флага и как его включить (`FLAG_<NAME>=1`),
   если флаг есть, и ссылку на тест-док. QA включает флаг на stage по этому
   комментарию; включение в prod - отдельное осознанное действие после проверки.

## Команды-шпаргалка

| Команда | Что делает |
|---|---|
| `make sdd-check` | AGENTS.md на месте и ≤500 строк + `openspec validate --all --strict` + spec-lint + `sdd-flags` |
| `make sdd-flags` | просроченные feature-флаги: 7 дней после `expires` - предупреждение, дальше отказ; нет реестра - сразу OK |
| `make sdd-doctor` | проверка окружения: git/node/python/uv/ruff/openspec, claude и gh CLI с авторизацией, store зарегистрирован, токен youtrack, хуки на месте + секция `audit` (лишние MCP, чужие агент-конфиги, посторонние skills/agents); у каждой находки код и команда фикса `next:`; `--json` для машин |
| `python3 .claude/scripts/spec-lint.py` | свежесть спек (не устарели ли против кода) + метаданные |
| `openspec view` | дашборд спек и изменений |
| `openspec show <spec> --type spec --store cybernet-specs` | читать контракт из store |
| `openspec doctor` | здоровье связки репо ↔ store |

## Спеки: откуда берутся и как не протухают

- Первичные спеки добывает агент **spec-miner** из кода (по одной capability за раз).
- В каждой спеке есть `Last verified (commit)` и якоря `enforced:` на код.
- **spec-lint** сравнивает их с реальными изменениями кода: спека устарела - увидишь
  предупреждение в `make sdd-check` (позже включим блокирующий режим `SPEC_LINT_STRICT=1`).
- Кросс-сервисные контракты живут в store; репозитории читают их через `references:`
  (read-only). Синхронизации нет by design: обновляешь store обычным `git pull`.

## Ruff

- У WBN свой конфиг (`backend/pyproject.toml`: select=ALL + большой ignore) - он главный.
- Остальным репозиториям kit кладёт `ruff.toml` с явным `select`
  (классические E/F + I, UP, C4, ISC, ICN, RET, SIM, TID, W).
  Явный select нужен, потому что дефолты ruff с версии 0.15/0.16 - это 400+ правил,
  на живом коде это шум и поведение меняется от версии к версии.
- Параметры выровнены с решениями WBN: E402 игнорируется, F401 разрешён
  в `__init__.py` (реэкспорты), двойные кавычки; target py310 - floor
  из-за cybernet3.0 (VA/PCA на 3.12 - можно поднять у себя).
- Что выключено сознательно: FA/TC (ломают интроспекцию FastAPI/Pydantic -
  WBN у себя игнорирует те же правила), PTH/TD/FURB (шумно на brownfield),
  S (безопасность - включим поправилно).

## Авторизация AI-шагов (важно)

Мы работаем **по подписке Claude Code, без API-ключа Anthropic**.
- Локально ничего настраивать не надо - CLI уже залогинен.
- Токен `CLAUDE_CODE_OAUTH_TOKEN` - **у каждого свой, на своей машине**
  (решение Daniil 2026-07-29): общий секрет в GitHub не заводим.
- AI-ревью запускай локально: `make sdd-review` - прогоняет твой дифф против dev
  через ревьюеров репозитория на твоём логине. AI-шаг в CI без секрета просто
  пропускается (за секунды, первым шагом job).
- Если когда-то понадобится токен для личной автоматизации: `claude setup-token`
  в настоящем терминале (не через пайп!), хранить только у себя.
- Никогда не использовать флаг `--bare` - он ломает подписочную авторизацию.

## Правила, которые чаще всего забывают

- AGENTS.md - канон, не длиннее 500 строк; CLAUDE.md - только симлинк.
- Файлы, попадающие в репозиторий, - только на английском.
- Секреты не пишутся в репозиторий никогда (хук это ещё и проверяет).
- Не растим монолиты: в VA `agent_service.py` (7311 строк) объявлен замороженным -
  новую логику класть рядом, не внутрь.
- Сгенерированные файлы (`migrations/`, `generated/`) руками не правим.

## Личные инструменты (ставишь себе сам, kit их в репо не кладёт)

Тот же установщик предлагает всё рекомендованное:
```bash
sdd-kit/install.sh --machine-only
```
Базовый стек ставится по умолчанию [Y/n]: ponytail, rtk, Graphify,
ast-grep. Опциональные - по явному согласию [y/N]: gh-axi,
chrome-devtools-axi, serena (после прошлой пробы остаётся мусор `.serena/` -
секция audit в sdd-doctor его флагирует, поэтому только opt-in). Что уже стоит - распознаёт
и пропускает. Подробности:

- **ponytail** - скилл "самое ленивое работающее решение": меньше кода,
  меньше токенов. Включается на своей машине, не в репозитории.
  (caveman отдельно не существует - это тестовый стенд внутри ponytail.)
- **gh-axi / chrome-devtools-axi** - обёртки gh и браузер-отладки под агентов:
  компактный вывод, подсказки следующего шага; по бенчмаркам автора дешевле
  и точнее, чем сырой gh или MCP.
- **ast-grep** - структурный поиск и переписывание кода по AST (кодмоды):
  массовые механические рефакторинги по всем репо, включая фронтенд.
  Не гейт - ручной инструмент по случаю.
- **Graphify** - карта репозитория как граф знаний; навигация и контекст,
  никогда не гейт (`graphify watch` на WBN уже работает).
- **Chrome DevTools MCP / Playwright** - для фронтенд-отладки; профиль
  web-frontend-new в sdd-kit добавляет chrome-devtools в `.mcp.json` автоматически.
- **RTK** (github.com/rtk-ai/rtk) - прокси, сжимающий вывод shell-команд до попадания
  в контекст (git log -> hash+тема, pytest -> только падения). Установка:
  `curl -fsSL https://raw.githubusercontent.com/rtk-ai/rtk/refs/heads/master/install.sh | sh`,
  затем `rtk init -g` и добавить напечатанный хук в `~/.claude/settings.json`,
  перезапустить Claude Code. Честно знать: "до 90%" - это сокращение bash-вывода,
  а не счёта; встроенные Read/Grep/Glob через хук не проходят.
  Не включать RTK-инструкции, пока не установлен бинарник - иначе шумит на каждую команду.
- **Headroom** - выпилен из стека 31.07.2026 (ADR-0014). Заявленные 60-95%
  не воспроизводятся: замеры дают 0-2% сжатия, при этом прокся ломает
  префикс prompt-кэша и итоговый счёт растёт на 45-62%. Не ставить.
- **grill-with-docs** - допрос плана до имплементации (обёртка над скиллами
  `/grilling` + `/domain-modeling`). Хорошая командная практика: полный план ->
  grill -> только потом код.
- **Поиск в интернете**: встроенного WebSearch в Claude Code достаточно для команды.
  SearXNG MCP - опция для тех, кто держит свой инстанс (приватность, без лимитов).
- **Свои skills из частых паттернов**: если один и тот же промпт/процесс повторяется
  третий раз - оформи его как skill (`.claude/skills/` у себя) и поделись с командой.
- **Модели и усилие** (ADR-0010): привязка закреплена в скиллах и агентах,
  помнить не нужно - план/гриль/исследование идут на Opus/Fable,
  имплементация на сессионной модели, ревьюеры берут модель из frontmatter,
  механические шаги - Haiku. Вручную: Sonnet - базовые задачи, Opus/Fable -
  сложные и планирование. `/effort` выбирай по задаче, не держи максимум всегда.
- **Не раздувай обвес**: каждый лишний MCP/skill ест контекст. `make sdd-doctor`
  покажет, что у тебя лишнего в репозитории.
