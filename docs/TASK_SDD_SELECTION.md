Статус: desk review выполнен 2026-07-27 (Fable 5 + субагенты). Артефакты готовы:
`OUR_PATTERNS.md` (фаза 0), `SDD_EVALUATION.md` (карточки + матрица + shortlist),

## 1. Цель

Выбрать и стандартизировать процесс написания кода ИИ-агентами (SDD-стек) для команд
CybernetAI, чтобы кратно ускорить работу над проектом. Стандарт должен пережить
предстоящие рефакторинги: миграцию на HubTalk-архитектуру, отказ от Asterisk,
появление новых сервисов.

**Не цель этой задачи:** выбирать между вариантами A/B/C продуктовой архитектуры,
проводить пилот, сводить репозитории в монорепо. Миграция по WEB-2303 — первый
рабочий груз для выбранного процесса, а не предмет выбора здесь.

## 2. Что зафиксировано (входные ограничения)

| Ограничение | Следствие для выбора |
|---|---|
| Основной агент — Claude Code; переходники на codex/cursor/aider допустимы, но не требуются | agent-agnostic — приятный бонус, вес низкий |
| Команда систематически не соблюдает правила и конвенции | **принуждение обязательно**: hooks + гейты в CI, а не методичка |
| Группы по 2-3 человека (несколько групп) | тяжёлые ролевые церемонии (21 агент BMAD) — накладные расходы |
| Примерно фиксированы контракты: frontend `api/v1`, external WebAPI, redis keys/json/streams для `cybernet3.0` | контрактные спеки обязаны быть первоклассной сущностью |
| 5 репозиториев, ~1.05M LOC, три несовместимых стиля контекста: `CLAUDE.md` (WBN/VA), `AGENTS.md` (cybernet3.0), LIVING SPEC (conversation_flow) | brownfield + multi-repo — критерий №1 |

## 3. Четыре узких места и покрытие

Ни один кандидат не закрывает все четыре. Выбираем **стек из слоёв**, и матрица
обязана показывать покрытие по каждой строке отдельно.

| Узкое место | Слой, который лечит | Кандидаты слоя |
|---|---|---|
| Неясные ТЗ, переделки после ревью | спека-гейт до кода | OpenSpec, spec-kit, cc-sdd, GSD |
| Контекст: 5+ репо, агент не знает систему | живая карта/спека репо + индексация | LIVING SPEC (CF), Graphify, serena, тонкий CLAUDE.md ≤500 строк |
| Интеграционные баги между сервисами | контрактные спеки + contract-тесты в CI | OpenSpec-спеки контрактов, схемы redis/OpenAPI, newman/pytest |
| Очередь на ревью и QA | многоагентное авторевью + гейты | ECC-ревьюеры, ruff/radon/complexipy/vulture/pylint, hooks |

## 4. Критерии и веса

| # | Критерий | Вес | Как проверяем (кабинетно) |
|---|---|---|---|
| 1 | Brownfield + multi-repo: работа с существующим кодом, дельта-изменения, спеки поверх 5 репо | 30 | наличие delta/change-механики, поддержка нескольких корней, есть ли spec-mining из кода |
| 2 | Принудимость: гейты, hooks, DoD, невозможность обойти | 25 | какие точки контроля предусмотрены; можно ли повесить PreToolUse/CI-гейт; есть ли машинно-проверяемый артефакт |
| 3 | Порог входа для группы 2-3 человека + живучесть upstream | 20 | объём обязательных артефактов на задачу; commits/последний релиз/лицензия/число мейнтейнеров |
| 4 | Стоимость цикла: токены и время на одну задачу | 15 | число обязательных LLM-проходов и агентов на задачу; оценка по докам, точный замер — в пилоте |
| 5 | Agent-agnostic (codex/cursor/aider/cline) | 10 | формат артефактов: markdown-в-репо против проприетарных скиллов |

Итог по каждому кандидату — взвешенная сумма + явное покрытие таблицы §3.
Критерий 1 применяется как **фильтр**: провал по нему выбивает кандидата из shortlist
независимо от суммы.

## 8. Открытые решения (ADR-заготовки, статус: открыто)

**ADR-0001. Где живут спеки при растущем числе репозиториев.**
Варианты: центральный репозиторий capability/контрактных спек + тонкий `CLAUDE.md` в
каждом репо; спеки внутри каждого репо (как LIVING SPEC у CF); монорепо.
Контекст: фиксированные контракты пересекают границы репо, поэтому «спека внутри репо»
оставляет межсервисные контракты бесхозными. Решение не принято.

**ADR-0002. Единый формат файла контекста агента.**
Сейчас `CLAUDE.md` (WBN/VA), `AGENTS.md` (cybernet3.0), LIVING SPEC (CF). Требование
`INIT.md`: ≤500 строк на репозиторий. Нужно одно правило и путь миграции остальных.

**ADR-0003. Механизм принуждения.**
Предварительно (со слов заказчика) pre-hooks приемлемы. Кандидаты: PreToolUse-hook,
блокирующий правку кода без спеки; CI-гейт «нет спеки/changelog → PR не проходит»;
`make test` как единая точка входа по образцу CF. Решение не принято.

**ADR-0004. Судьба текущего обвеса harness.**
Подключены сотни ECC-скиллов, GSD, vercel-плагин, ~15 MCP — это противоречит пункту
`INIT.md` об оптимальном количестве. Нужно решить: чистим до внедрения SDD, после, или
не чистим. Данные для решения даёт фаза 0 (что не использовалось ни разу).

**ADR-0005. Кто отвечает за бэкенд-часть сравнения с HubTalk.**
`WEB-2303-Hubtalk-comparison.md` покрывает UI/админку и молчит про post-call (~320k LOC),
SSO/Keycloak, api-gateway, validation-service и redis-контракты `cybernet3.0`. Это
пробел в исходной задаче «список фич»; закрывается отдельным тикетом, а не этой задачей.

## 9. Глоссарий

- **SDD** — spec-driven development: спека как согласованный артефакт до написания кода.
- **Brownfield** — изменение существующей системы (наш случай) в противоположность
  greenfield-старту с нуля.
- **Delta/change-спека** — описание только изменения относительно текущего поведения
  (подход OpenSpec), в отличие от полного статичного описания системы.
- **LIVING SPEC** — единый документ-источник правды, обновление которого входит в DoD
  каждой доработки (реализовано в `conversation_flow/docs/DOCUMENTATION.md`).
- **ТЗ №N** — принятая в `conversation_flow` нумерация доработок; на неё ссылаются тесты
  и changelog.
- **Гейт** — автоматическая проверка, блокирующая продвижение работы (hook или CI-шаг).
- **Сайт 1 / Сайт 2** — в `WEB-2303`: текущий production и целевая платформа HubTalk.
- **Слой стека** — одна из четырёх функций из §3: спека, контекст, контракты, ревью.
  Стандарт собирается из слоёв; один инструмент редко покрывает больше двух.
- **Узкое место** — этап, ограничивающий скорость всей цепочки; лечится адресно.
- **TBD (Trunk-Based Development)** — работа короткими ветками с ежедневным вливанием в
  общую ветку. Мы берём только дисциплины (лимит возраста ветки и размера PR), сами
  ветки и PR остаются (ADR-0006).
- **Feature-флаг** — переключатель в конфигурации: код влит, но выключен, пока не готов.
  У каждого флага есть владелец, тикет и дата смерти `expires` (ADR-0007).
- **Expand/contract** — миграция контракта в три шага: добавить новое рядом со старым →
  переключить потребителей → удалить старое.
- **Branch by abstraction** — большая замена без долгой ветки: прослойка над старым
  компонентом, флаг выбирает реализацию, потом прослойка удаляется.
- **RAISE** — внутренний процесс подачи и приоритизации заявок (форма + RICE + доска
  Voicebot + LLM). Слой над SDD-стеком (ADR-0009). Не путать с методологией useraise.dev
  (разбор: `sdd-kit/research-useraise-methodology.md`, не внедряем).
- **RICE** — формула приоритета заявки: Reach × Impact × Confidence ÷ Effort.
