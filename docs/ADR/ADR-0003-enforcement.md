# ADR-0003. Как заставить агентов и разработчиков соблюдать правила (механизм принуждения)

Статус: **принято** (предварительное решение после кабинетного обзора; ждёт подтверждения Daniil). Дата: 2026-07-27.

## Решение

Выбрано два контура защиты, главный из них — проверка в CI.

**Контур 1, главный — CI-гейт на pull request.**
Гейт здесь — это проверка, через которую нельзя пройти, если что-то не так: пока проверка не пройдена, изменения нельзя влить в основную ветку.
Работает по образцу того, что уже сделано в conversation_flow.
В каждом репозитории команда `make test` должна быть единой точкой входа и включать:
- локальные линтеры репозитория (например ruff для Python и подобные);
- `openspec validate --all --strict --json` — проверка корректности спек;
- проверки `lint_spec` — что при изменении кода задеты соответствующий changelog и спека;
- pytest;
- контрактные тесты — это тесты на границе между сервисами, на слое контрактов между сервисами.

Эта проверка должна быть обязательным («required») check в CI, а ветка dev должна быть защищена от прямых пушей мимо pull request.

**Контур 2, вспомогательный — PreToolUse-hook** в файле `.claude/settings.json` каждого репозитория.
PreToolUse-hook — это перехватчик, который срабатывает до действия агента (например до правки файла) и может это действие запретить.
Такой хук должен блокировать команды Edit/Write по путям с кодом, если для них нет активной задачи в `openspec/changes/<id>/` (либо если в её метаданных явно указано `skip_specs: true`).
Хук нужно написать самим — это небольшой скрипт (примерно 50–100 строк), который завершается с кодом ошибки exit 2, если правило нарушено.
Отдельно: уже работающий ECC-хук, который запрещает `git commit --no-verify`, нужно оставить как есть.

Идея «`make test` как единая точка входа» — принята.
Идея «полагаться только на хуки, без CI» — отклонена.
Идея «полагаться только на методичку без технической защиты» — отклонена, потому что это не совместимо с тем, насколько высоко в задаче оценена важность принудительности (вес 25 из 100).

## Обоснование данными

Единственный в компании реально работающий пример принуждения правил — это связка `make test` + CI на pull request в conversation_flow (`Makefile:210`, `.github/workflows/ci.yml`).
Именно там же было доказано, что произвольное правило про стиль оформления (lint_brand) можно превратить в обязательное примерно сотней строк кода на Python.

Все остальные «гейты» в существующих фреймворках на деле не заставляют ничего делать — это либо просто текст-инструкция для LLM, либо необязательная (opt-in) настройка.
ECC в профиле minimal умеет блокировать только `git commit --no-verify` (сам инструмент `quality-gate.js` вообще не умеет ничего блокировать, строки 140–149).
Хуки GSD прямо в своём коде описаны как «мягкая защита, которая советует, но не блокирует» (`gsd-workflow-guard.js:6-12`).
У superpowers есть только один хук на старте сессии.
У BMAD и spec-kit механизма принуждения нет вообще.
Вывод: если полагаться только на хуки, принуждение правил провалится.

Масштаб того, что разработчики обходят процесс, если его не заставлять технически, тоже измерен: в cybernet3.0 было 1780 коммитов мимо pull request, использовались три разные стратегии слияния веток, а привязка коммитов к номеру тикета была всего на уровне 2–73% (данные из `OUR_PATTERNS.md`).
Отсюда вывод: гейт обязан стоять там, где его нельзя обойти технически, — то есть быть обязательной проверкой прямо в pull request.

Контур с хуками всё равно нужен в дополнение к CI.
Хук ловит нарушение сразу, в момент правки файла, — это дёшево.
CI ловит нарушение на границе, перед вливанием в основную ветку, — это гарантированно, но позже и дороже по времени разработчика.
Использование pre-хуков в целом одобрено заказчиком — это упомянуто в разделе открытых решений в постановке задачи (`TASK_SDD_SELECTION.md`).

## Риски

Прямые пуши в ветку dev обходят проверку pull request.
Поэтому нужно включить защиту ветки (branch protection) одновременно с внедрением гейта — иначе гейт останется чисто декоративным, как это уже случилось в cybernet3.0.

Есть способы обойти сам валидатор OpenSpec — например команда `archive --no-validate` или пустая (zero-delta) правка.
Эти обходы должны закрываться дополнительной проверкой поверх, уже в CI (описано в `SDD_EVALUATION.md`).
