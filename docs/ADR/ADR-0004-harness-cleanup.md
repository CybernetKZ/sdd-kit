## Решение

Чистить обвес нужно **до** того, как внедрять SDD (spec-driven development, разработка через спецификации), а не после.
Причина: если внедрять новый стандарт поверх обвеса, 95% которого никогда не используется, этот мусор попадёт и в сам стандарт.

Конкретные решения по компонентам (на основе данных фазы 0 из `../archive/OUR_PATTERNS.md`):

| Компонент | Действие | Основание |
|---|---|---|
| serena MCP | удалить | 0 вызовов за всю историю |
| youtrack MCP | **оставить** | 0 вызовов, но тикеты - центр рабочего процесса (60% документов привязаны к id тикета WEB-...); неиспользование - это проблема привычки, а не признак ненужности; пересмотреть решение через квартал |
| chrome-devtools MCP (в составе ECC), плагин vercel, коннекторы claude_ai_* | удалить / отключить | 0 вызовов |
| ECC целиком (271 скилл, 67 агентов) | сократить до нескольких ревьюеров (python / fastapi / database / общий) и spec-miner; зафиксировать версию на коммите ec92b528 | реально использовался только ecc:code-review (3 вызова); ревьюеры и spec-miner входят в выбранный стек инструментов |
| RTK.md (инструкция в глобальном CLAUDE.md) | удалить инструкцию | сам rtk не установлен - инструкция мёртвая, но она всё равно занимает место в контексте каждой сессии |
| GSD | оставить установленным | 9 реальных вызовов gsd:* - это единственный фреймворк, которым реально пользовались; кандидат на роль слоя фаз (описано в `../archive/SDD_EVALUATION.md`) |
| context7, searxng, postgres-readonly, headroom, claude-in-chrome | оставить | 101 / 80 / 48 / 43 / 5 вызовов соответственно - ими реально пользуются |
| ponytail | оставить | активируется через хук, поэтому статистика по вызовам Skill tool его не видит (это известная оговорка в данных) |

## Обоснование данными

Из примерно 285+ установленных названий скиллов реально вызывались только 9.
Всего 28 вызовов Skill tool за 1021 сессию.

В `../archive/INIT.md:15` прямо написано требование: количество mcp-серверов и скиллов должно быть оптимальным, потому что слишком большое их число забивает контекст.
Замер это подтвердил: 95% токенов уходит на cache read разросшегося контекста, а листинг скиллов и схем MCP-инструментов попадает в каждый системный промпт.

Чистить сначала - дешевле по деньгам и времени.
Сама чистка занимает один день.
Если внедрять SDD поверх грязного контекста, это постоянный "налог" на каждую сессию каждого разработчика - то есть повторяющиеся потери времени и токенов.

## Отклонено

Вариант "почистим после внедрения SDD" отклонён.
Налог в виде разросшегося контекста будет платиться весь период внедрения, а инерция по принципу "работает - не трогай" превратит чистку в вечный TODO, который никогда не будет сделан.

Вариант "не чистим вообще" отклонён - он прямо противоречит требованию из `../archive/INIT.md` и собранным данным.
