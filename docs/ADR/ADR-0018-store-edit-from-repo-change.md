# ADR-0018. Как репо-change правит контракт в сторе: два change'а, явная задача-связка

Статус: **принято**. Дата: 2026-08-03 (по итогам ручного прогона WEB-2318, фрикция P5).

## Проблема

В brownfield-репозитории локальный `openspec/specs/` пуст, а все кросс-репо
контракты лежат в сторе `cybernet-specs` (ADR-0001). Значит типичный тикет,
который меняет границу между сервисами, обязан править спеку **в чужом
репозитории**. В ките не было сказано ни слова о том, как это оформить.

Что происходило без правила (прогон WEB-2318): агент понял, что контракт надо
менять, и просто вынес это отдельными пунктами в `tasks.md` — без указания,
где именно возникает change стора, кто его мержит и что происходит с
репо-change'ем, пока стор-PR висит. Второй агент на том же тикете оформил бы
это иначе. Есть и соблазн похуже: правка `cybernet-specs/openspec/specs/**`
руками из репо — README стора это прямо запрещает («Never hand-edit
`openspec/specs/**` directly»), а стор для потребителя вообще read-only.

## Решение

**Правка стор-контракта — это ВСЕГДА отдельный change в `cybernet-specs`,
связанный с репо-change'ем явной задачей.**

1. **Репо-change несёт «зачем» и «что из этого следует».** В `proposal.md`
   репо-change'а: какое требование стора меняется, почему, и какие
   репозитории-потребители задеты (список — в `README.md` стора и в поле
   `context:` его `openspec/config.yaml`).
2. **Сам текст спеки правится только в сторе, его собственным change-флоу**
   (README стора, «How to add or change a contract»):
   `openspec/changes/<store-change-id>/` с `proposal.md`, `tasks.md` и
   дельтой на капабилити в `specs/<capability>/spec.md` под
   `## ADDED|MODIFIED|REMOVED Requirements`; затем
   `openspec validate <store-change-id> --strict`, PR с тегом владельца
   каждого задетого репозитория, после мержа — перенос в
   `openspec/changes/archive/`.
   Из репо все чтения стора идут через `--store cybernet-specs`
   (`openspec list --specs --store cybernet-specs`,
   `openspec show <spec> --type spec --store cybernet-specs`);
   писать в стор из репо нельзя, даже если CLI позволяет `--store` на записи.
3. **`tasks.md` репо-change'а несёт явную задачу-связку** — отдельным пунктом,
   с id стор-change'а, например:

   ```markdown
   - [ ] store: change `cybernet-specs / wbn-va-rpc-web-call-session`
         (MODIFIED Requirement «...»); PR: <ссылка>; блокирует архивацию
   ```

   Если id ещё не создан — задача формулируется как «создать change в
   cybernet-specs», и id проставляется, как только он есть. Ссылка в одну
   сторону обязательна; обратная ссылка (стор-change → тикет WEB-XXXX в его
   `proposal.md`) желательна и стоит одну строку.
4. **Репо-change не архивируется, пока стор-PR открыт.** Архивация репо-change
   означает «контракт таков» — а он ещё не таков. Это дополнение к обычным
   условиям архивации (ADR-0011: флаг включён в prod по умолчанию; без флага —
   последняя задача смержена и проверена).
5. **Порядок мержа: стор первым, если код зависит от нового контракта**;
   иначе — репо первым, а стор-PR закрывает расхождение до архивации.
   Второе допустимо только внутри одного репозитория-владельца обеих сторон;
   если стороны в разных репозиториях, стор идёт первым.

## Почему так, а не «править стор прямо из репо-change'а»

- **Стор — общий.** Его change ломает или чинит всех потребителей сразу,
  поэтому ему нужен свой ревью со своими владельцами (README стора, п. 3).
  Внутри репо-PR эту правку никто из соседних команд не увидит.
- **Стор — read-only для потребителя** по устройству механизма OpenSpec store:
  он индексирует, а не инлайнит; локально это клон, который может отставать
  (ADR-0015). Запись в клон из другого репо — тихий локальный форк контракта.
- **Одна общая CI-проверка.** `store-ci.yml` (`openspec validate --all
  --strict`) — единственный гейт стора; он срабатывает на PR в сторе и никогда
  не увидит правку, приехавшую мимо.
- **Явная задача — единственное, что переживает контекст.** Без строки в
  `tasks.md` связь «этот тикет ждёт того PR» живёт только в голове агента,
  который её придумал.

## Отклонённые альтернативы

- **Один change на два репозитория.** OpenSpec такого не умеет: change живёт
  в одном planning home (`openspec status --json`, поле `planningHome`), и
  `allowedEditRoots` ограничивает правки корнем этого репозитория.
- **Копировать стор-спеку в локальный `openspec/specs/` и править там.**
  Прямо противоречит ADR-0001 и превращает контракт в две расходящиеся копии.
- **Гейт в CI, который блокирует мерж репо-PR до мержа стор-PR.**
  Против advisory-first (ADR-0015) и требует кросс-репо CI, которого нет.
  Держим это правилом архивации, а не серверным гейтом.
