# ADR-0005. Кто отвечает за бэкенд-часть сравнения с HubTalk

Статус: **отложено** - вынесено в отдельный тикет, за рамки этой задачи. Дата: 2026-07-27.

## Решение

Документ `../archive/WEB-2303-Hubtalk-comparison.md` покрывает только UI и админку: в нём разобраны дизайн, информационная архитектура и административные экраны (первые два раздела документа).
Бэкенд-часть сравнения он не покрывает - это пробел.

Пробел закрывается отдельным тикетом в YouTrack: "Backend gap-анализ Сайт 1 -> Сайт 2".
В скоуп этого тикета входит:
- обвязка post-call обработки (примерно 320 000 строк кода);
- SSO/Keycloak;
- api-gateway и validation-service;
- redis-контракты cybernet3.0 (ключи, json, потоки).

Ответственного назначает Daniil - это должен быть бэкенд-лид направления миграции.
В рамках кабинетного обзора (по документам и коду, без запуска) назначить ответственного невозможно.

Рекомендация по организации работы: этот тикет стоит делать первой рабочей задачей в рамках выбранного SDD-процесса, вместе с WEB-2303.
Причина: контрактные спеки на слое контрактов между сервисами (описано в `../archive/SDD_EVALUATION.md`, пункт 2) и есть основной результат такого gap-анализа.
Без зафиксированных контрактов gap-анализ бэкенда просто нельзя будет проверить.

## Обоснование

Ещё в постановке задачи было отмечено, что список фич - это неполный список, и бэкенд-пробел придётся закрывать отдельным тикетом (это зафиксировано в разделе открытых решений в постановке задачи, `../archive/TASK_SDD_SELECTION.md`, и повторено в этом же ADR-0005).
Здесь фиксируется только механизм и скоуп этой работы, а не решение по существу сравнения.

Связка с SDD (spec-driven development) не притянута искусственно.
Перечисленные бэкенд-поверхности - это ровно те "примерно зафиксированные контракты", которые упомянуты как ограничение в постановке задачи (тоже в `../archive/TASK_SDD_SELECTION.md`).
Их первичное оформление в store (см. ADR-0001) одновременно даёт материал и для gap-анализа.
