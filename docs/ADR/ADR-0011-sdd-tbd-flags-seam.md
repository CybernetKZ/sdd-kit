# ADR-0011. Стык SDD (OpenSpec) + RAISE + trunk-based с флагами; handoff после мержа

Статус: **принято** (решения подтверждены Daniil 2026-07-30 в grill-сессии по WORKFLOW.md).
Дата: 2026-07-30.

## Контекст

Три уже принятых слоя должны работать вместе:
RAISE (ADR-0009) решает, ЧТО берём в работу; SDD-стек (ADR-0001…0003) — КАК
из тикета получается код; TBD-дисциплины (ADR-0006) + флаги (ADR-0007) — КАК
код едет в dev короткими ветками. Гейт возраста ветки (FAIL > 5 дней)
создаёт шов: эпик не помещается в одну ветку, значит один OpenSpec change →
несколько маленьких PR за флагом. Три вопроса были без ответа: когда
архивируется change, что видит QA за выключенным флагом, что происходит
с тикетом после мержа.

## Решения

### 1. Эпик = один change, несколько PR; архив при включении флага в prod

Спека описывает поведение prod. Спек-дельта живёт в `openspec/changes/<id>/`
все PR эпика и архивируется, когда флаг включён в prod по умолчанию.
Удаление флага (по `expires`, ловит `make sdd-flags`) — отдельный маленький
PR без нового change. Долго висящий change — не баг, а честное «эпик в
процессе»; старение ловим по `expires` флага, не по возрасту change.

Отклонено: архив после последнего PR эпика (спека врёт про prod, пока флаг
выключен); один change на каждый PR (теряется цельная картина эпика,
оверхед +$4.6 на каждый кусок).

### 2. Состояние флагов по средам: вкл в dev/stage, выкл в prod

Конвенция в `feature_flags.py`: новый флаг по умолчанию включён в dev и
stage, выключен в prod. QA всегда видит новое поведение на stage. Включение
в prod — отдельное осознанное действие после проверки QA. Имя флага
разработчик пишет в комментарии тестировщику.

Отклонено: везде выкл + QA включает сам (ломается на первом забытом шаге);
флаги только для эпиков без правила сред (правило сред нужно всё равно).

### 3. Handoff после мержа: `ready_to_test` + комментарий ≤ 1 абзаца

После принятия PR в dev разработчик переводит тикет в
`status: ready_to_test` и оставляет комментарий тестировщику: что и как
проверять — кристально просто, до одного абзаца (плюс имя флага, если есть,
и ссылка на test-cases док для standard/deep тира). Для light-тира отдельного
дока нет — QA проверяет по шагам воспроизведения из баг-репорта RAISE.
Это шаг 8 feature-flow; youtrack-mcp двигает статус.

### 4. Гриль плана оставляет след в самом change

Секция «Grill» в `proposal.md`: список острых вопросов и принятых ответов,
одна строка на решение. Архивируется вместе с change — история решений
остаётся. Отклонено: отдельный `council.md` (ещё один артефакт); без
артефакта (через месяц никто не вспомнит, почему выбрали вариант Б).

### 5. serena — из core в opt-in; ast-grep — из opt-in в core

Устранено противоречие NEXT_STEPS («serena SKIP, .serena/ — мусор») против
setup-dev.sh (serena в core). Решение: serena опциональна (y/N), ast-grep —
в core-стек. Правки внесены в `setup-dev.sh` и `sdd-kit/README.md`.
