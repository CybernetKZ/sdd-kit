# ADR-0001. Где хранить спецификации, если репозиториев становится больше

Статус: **принято** (предварительное решение после кабинетного обзора; ждёт подтверждения Daniil). Дата: 2026-07-27.

## Решение

Выбран гибридный вариант из двух уровней.

**Уровень 1 — внутри каждого репозитория своя папка `openspec/`.**
В ней лежат спеки (specs) на локальные возможности репозитория (capability).
Там же лежат «changes» — так называемые delta-спеки, то есть описания только того, что меняется, а не всей спеки целиком.
Дополнительно в каждом репозитории должен быть тонкий файл контекста для агента, не длиннее 500 строк (описан в ADR-0002).

**Уровень 2 — один центральный репозиторий-store.**
Store — это отдельный репозиторий, где лежат общие контрактные спеки, то есть договорённости, которые касаются сразу нескольких сервисов.
Механизм называется «OpenSpec stores» и пока находится в статусе beta.
В store переносятся только контракты, которые пересекают границы репозиториев: API `api/v1` для фронтенда, внешний WebAPI, а также ключи/json/потоки redis в cybernet3.0.
Каждый репозиторий подключается к store через настройку `references:` в своём `openspec/config.yaml`.
Это read-only индекс (`openspec/src/core/references.ts:1-10`), то есть репозиторий может читать чужие контракты, но не редактировать их оттуда.

Два других варианта отклонены.
Монорепо (все сервисы в одном репозитории) отклонён явно — он не входит в цель задачи (это зафиксировано в разделе открытых решений в постановке задачи, `TASK_SDD_SELECTION.md`).
Вариант «все спеки в каждом отдельном репозитории» (чистый CF-вариант) тоже отклонён.
Причина: при этом варианте межсервисные контракты остаются ничьими — этот риск был зафиксирован ещё на этапе обсуждения решения.

## Обоснование данными

Кросс-репозиторные изменения существуют, но их немного и они сосредоточены в одном месте.
60 из 721 тикета (8,3%) затрагивают больше одного репозитория.
Почти все такие тикеты идут по оси WBN ↔ VA (два конкретных репозитория).
Для VA это вообще 35% всех его тикетов (данные из `OUR_PATTERNS.md`).
Вывод: контрактный слой нужен, но не «всё связано со всем» — хватает центрального store с несколькими контрактными спеками, полная централизация не нужна.

Материал для store уже существует, писать спеки с нуля не придётся.
Сейчас эти контракты записаны как markdown-файлы внутри WBN: `TELEPHONY_IN_REDIS_STREAM_CONTRACT.md`, `POST_CALL_PROCESSOR_LLM_REDIS_CONTRACT.md`, `FE_GOAL_ACHIEVED_CONTRACT.md` и другие (список в `OUR_PATTERNS.md`).
Их нужно перенести в store, а не писать заново.

OpenSpec выбран, потому что это единственный вариант, где механизм связи между репозиториями уже работает, а не является идеей на бумаге.
Store регистрируется на машине по имени, его содержимое никогда не вставляется целиком в другой репозиторий (не инлайнится), а индекс весит не больше 50 КБ (`docs/stores-beta/user-guide.md:23-26`).

## Риски и оговорки

Stores — это ещё функция в статусе beta.
Синхронизации нет вообще: свежесть чужих спек равна свежести того, что скачано (checkout) локально (`user-guide.md:327-329`).
Способ снизить риск: добавить CI-задачу, которая падает, если локальная копия store устарела (сравнивается SHA-хэш коммита).

Репозиторий conversation_flow не переходит на OpenSpec целиком.
Его текущий формат LIVING SPEC и так работает.
Он будет только публиковать свои внешние контракты в store, ничего больше у себя не меняя.

## Состояние внедрения (2026-07-28, тестовый режим)

Уровень 1 сделан: папка `openspec/` есть во всех 4 репозиториях (WBN, VA, PCA, cybernet3.0).
В каждом лежит по одной добытой спеке, все проходят `openspec validate --all --strict`.

Уровень 2 сделан в тестовом виде: store живёт в `~/cybernet/cybernet-specs`.
Внутри 3 контракта: telephony-in-redis-stream, post-call-processor-llm-redis, engine-redis-contract.
Store зарегистрирован на машине: `openspec store register . --id cybernet-specs`.
Все 4 репозитория подключены через `references: [cybernet-specs]` в `openspec/config.yaml`.
Проверено: `openspec doctor` — ok во всех 4; чтение чужой спеки из WBN работает
(`openspec show telephony-in-redis-stream --type spec --store cybernet-specs`).

Осталось: завести боевой store-репозиторий в организации (решает Daniil),
перенести туда содержимое тестового, добавить контракты api/v1 и внешнего WebAPI,
подключить conversation_flow (публикация его контрактов).

## Дополнение (2026-07-28): судьба «workspace» в OpenSpec

В OpenSpec раньше была модель «workspace» для мульти-репо.
Её удалили целиком (PR #1190, смержен 2026-06-23, вышло в 1.5.0) и заменили на stores.
То есть наш выбор (store + `references:`) — это действующая модель, а не устаревшая.
Ветки workspace-* в репозитории OpenSpec — остатки отклонённого подхода, на них смотреть не нужно.
Команда `workset` — не мульти-репо механизм, а просто локальный «открыть папки вместе», ничего не коммитит.
Правило «синхронизации нет, тяни сам» — осознанный инвариант OpenSpec, а не недоделка беты.
Поэтому наш CI-гейт на устаревание store (сравнение SHA) остаётся обязательным — апстрим его не заменит.
Версию пиновать точно: `@fission-ai/openspec@1.6.0` (беты stores прямо обещают ломающие изменения).
За чем следить: issue #1436 (структурный каталог репозиториев в store) и PR #1286 (`--serves`, кросс-репо статус) — второе прямо про нашу ось WBN↔VA.
