# ADR-0009. RAISE (внутренний intake-процесс) дополняет SDD-стек, не заменяет его

Статус: **принято** (решения подтверждены Daniil 2026-07-30 в grill-сессии). Дата: 2026-07-30.

## Контекст

Компания перешла на процесс подачи и приоритизации заявок «RAISE»
(support.cyber-net.ai, статьи VB-A-92…96): единая форма заявки, оценка RICE,
доска Voicebot + LLM, ежемесячный разбор бэклога, отдельные пути для срочных задач и багов.
Локальная копия: `../RAISE-intake-process.md`.

**Разводим имена.** В обиходе живут несколько «RAISE»:
наш внутренний intake-процесс; мёртвая методология useraise.dev
(разбор: `sdd-kit/research-useraise-methodology.md`, вердикт — не внедрять); ещё три научных.
В документах слово RAISE без уточнения означает только наш intake-процесс.

## Решение

RAISE — слой НАД SDD-стеком: он решает, какая задача попадает в работу.
SDD-стек (OpenSpec + гейты + store, ADR-0001…0003) решает, как из тикета получается код.
Стык — шаг 1 skill `feature-flow`: «допросить тикет».

1. **feature-flow читает форму заявки.**
   Поля «проблема», «ожидаемый результат», «альтернативы» из формы RICE
   ложатся в why-секцию OpenSpec change — заявитель уже написал этот контекст.
2. **Формы в тикете нет — предупреждение, не блок.**
   Агент отмечает отсутствующие поля, задаёт вопросы автору тикета
   с рекомендованными ответами и параллельно продолжает работу по рекомендованным ответам.
   Исключение: серьёзные бизнес-развилки — тут работа ждёт ответа автора.
   Валидация заявок — работа владельца процесса RAISE, не разработчика.
3. **Срочные задачи и баги: спека всегда, но минимальная.**
   Urgent-путь RAISE ускоряет приоритизацию, но не отменяет процесс разработки —
   ровно как в самом RAISE: срочный статус не означает автостарт разработки.
   Баг и urgent идут через skill `incident-flow`: короткий OpenSpec change
   (почему + что + регрессионный тест). Обхода spec-guard для срочных задач нет,
   иначе «срочно» становится лазейкой мимо всех гейтов.
4. **incident-flow выравнивается с шаблоном баг-репорта RAISE**
   (среда, Dialogue ID, шаги, фактический/ожидаемый результат, приоритет по шкале low…critical):
   сбор улик читает эти поля из тикета вместо повторного допроса.

## Отклонённые варианты

- **Блокировать работу без заполненной формы RICE** — отклонено:
  разработчик становится заложником чужого процесса и будет работать в обход скилла.
- **Обход spec-guard для critical-багов** (спека задним числом за 24 часа) — отклонено:
  задним числом означает никогда.
- **Игнорировать форму RICE** — отклонено: теряем готовый why-контекст.
