# ADR-0010. Тиры задач и привязка моделей к фазам

Статус: **принято** (решения подтверждены Daniil 2026-07-30 в grill-сессии по WORKFLOW.md).
Дата: 2026-07-30.

## Контекст

Один процесс для всех задач не работает: простой баг не требует исследования
архитектуры, а эпик требует. Бенчмарк уже показал цену: оверхед кита ≈ +$4.6
на задачу, +57% на точечном багфиксе (report-m2.md). Нужен лёгкий путь,
который не превращается в лазейку мимо гейтов.

Вторая проблема: «Sonnet для базовых, Opus/Fable для сложных» из INIT.md —
совет, а не механизм. Работает только у тех, кто помнит правило.

## Решения

### 1. Три тира: light / standard / deep

Меняется только глубина подготовки. **Гейты одинаковы для всех тиров**:
спека всегда (минимальная для light), тесты, sdd-check, ревью, CI.
Обхода spec-guard нет ни на одном тире (подтверждает ADR-0009).

| Тир | Что входит |
|---|---|
| light | мини-спека (incident-flow-стиль), без гриля плана, без test-cases дока; регрессионный тест, воспроизводящий баг ДО фикса |
| standard | как feature-flow сейчас: intake → change → гриль → test-cases док → тесты → имплементация → ревью → PR |
| deep | standard + фаза исследования архитектурных подходов (сравнение вариантов, ADR) + обязательный гриль плана |

Отклонено: тиры, ослабляющие гейты (стимул занижать тир ради обхода ревью);
два тира вместо трёх (средние задачи получают лишний вес).

### 2. Выбор тира

- Тир задан в тикете → используется по умолчанию.
- Разработчик ВСЕГДА может поменять тир.
- Тир не задан → агент выбирает сам по сигналам
  (категория RAISE, число сервисов, миграции, новые контракты).
- Тир и обоснование пишутся в OpenSpec change — ревьюер видит и может оспорить.

### 3. Модели закрепляются в скиллах и агентах sdd-kit

Механизм, а не память:

- план / гриль / исследование (deep) — opus/fable (скилл говорит это агенту
  на соответствующих шагах);
- имплементация — текущая сессионная модель;
- ревью-агенты — `model` в frontmatter агента;
- механические шаги (bulk-правки, прогон линтеров) — haiku.

Плюс короткая таблица в методичке. Отклонено: только таблица в методичке
(ноль поддержки в коде); жёсткая привязка модели к тиру задачи (внутри одной
задачи фазы всё равно разные).

### 4. RED-first: требование в скилле, без CI-гейта

feature-flow требует: тесты по плану пишутся до имплементации, агент
показывает RED-прогон в отчёте. Механического гейта на порядок нет — его
честно не построить (коммит-порядок ломается rebase/squash). Для light-тира
RED = регрессионный тест, воспроизводящий баг до фикса.

Отклонено: жёсткий «тесты отдельным первым коммитом» (обманывается, ломает
rebase); убрать RED из процесса (теряем «тест проверяет план, а не реализацию»).
