# Авторинг ТЗ как OpenSpec change

Артефакт — каталог `openspec/changes/tz-NNN-<slug>/`:

| Файл | Что в нём |
|---|---|
| `proposal.md` | шапка-цитата, контекст, позиция, дизайн, вне scope, что затрагивается, `## Grill` |
| `specs/<capability>/spec.md` | дельта: `## ADDED Requirements` / `## MODIFIED Requirements` с `#### Scenario:` |
| `tasks.md` | критерии приёмки как чек-лист `- [ ]` |

**Файлы в `docs/patches/` больше не создаются** — архив закрыт (`docs/patches/README.md`).
Эталон стиля proposal — `openspec/changes/archive/tz-082-*` … `tz-084-*` (свежие,
конвертированы из patch82–84); ранние архивные — беднее, на них не ориентироваться.
Прочитать 2 свежих change'а целиком до написания.

Цепочка процесса: **`/tz` → `/tz-review` → `plan-griller` → `test-author` →
`/tz-implement`** (ADR-0020: review и грилл — оба шага, не взаимозаменяемы).

## Шаг 1. Номер и id

Двойная нумерация (ADR-0019 §7):

- **id change** — `tz-NNN-<kebab-slug>`, `NNN` = сквозной номер ТЗ с ведущими
  нулями (`tz-092-...`), slug английский, как имена в архиве.
- **YouTrack-id** (если есть) — строкой в `proposal.md` (`> Тикет: WEB-1234`),
  **не** в имени каталога.

Следующий свободный номер = **максимум из четырёх источников** (считать, не
угадывать; ADR-0019 писался при №84 — цифра в нём устарела):

```bash
grep -oP 'ТЗ №\K[0-9]+' docs/DOCUMENTATION.md | sort -n | tail -1     # §17 changelog
ls docs/patches/ | grep -oP 'patch\K[0-9]+' | sort -n | tail -1       # легаси-архив
ls openspec/changes/ openspec/changes/archive/ | grep -oP '^tz-0*\K[0-9]+' | sort -n | tail -1
```

Нюансы: **№33 использован дважды** (справочник LLM-моделей и события звонка в
Истории) — при подсчётах не споткнуться; ТЗ №85–91 существуют только в
`docs/patches/` (в `changes/archive/` их нет — конвертация закрыта на №84),
поэтому `ls archive` в одиночку даёт заниженный номер.

**Change'ы не переписываются задним числом.** Реализованное требование —
зафиксированная история; коррекция — всегда **новый номер** (примеры: №48
корректирует №47, №49 заменяет модель №45/№46).

## Шаг 2. Разведка по коду — до текста

Ссылки — на **реальные** файлы, классы и поля, не на общие слова. До первой
строки текста проверить Grep/Read:

- какие модули/схемы/таблицы затрагиваются — точные пути
  (`engine/schema.py::TransferSpec`, `storage/models.py`, …);
- **какие capability затронуты** — `ls openspec/specs/` (20 штук) и прочитать
  Requirements тех, что трогаются: дельта пишется поверх существующих `id:`,
  а не «с нуля»;
- **точки расширения** — где уже заложен паттерн для подобного (реестры,
  builders, `*_PROVIDERS`/`*_KEY_ENVS`, репозитории) — перечислить в шапке-цитате;
- что из требуемого **уже реализовано** — в `## Позиция`, чтобы исполнитель
  достраивал, а не писал с нуля;
- кросс-репо контракты, если трогаются: `openspec list --specs --store cybernet-specs`,
  затем `openspec show <spec> --type spec --store cybernet-specs` (ADR-0018:
  правка контракта — отдельный change+PR в store, задача на него — в `tasks.md`).

Факты о внешнем мире (возможности провайдеров, параметры чужих API, версии
SDK), которые не удалось подтвердить, **не утверждать наугад** — писать явно
«**проверить перед реализацией**» и собирать в отдельный
`## Проверить перед реализацией` (образец — patch60 §5, tz-084 §5).

## Шаг 3. Структура артефакта

### 3.1 `proposal.md`

1. **H1**: `# tz-NNN — <Название по-русски>`.
2. **Шапка-цитата** (`>` сразу под H1, как в tz-082…084): тикет YouTrack;
   зависимости от прежних ТЗ и capability («Опирается на: №83 (hangup-путь),
   №82 (гвард D3), …»); **точки расширения** («всё уже в коде, проверено»);
   **подтверждение осуществимости** («Осуществимость подтверждена по пиновым
   SDK: …»).
3. `## Контекст` — что не работает/чего не хватает, с наблюдёнными фактами
   (uuid сессий, file:line, числа), а не общими словами.
4. `## Позиция / зафиксированные решения` — что уже есть в коде, решения
   принятые заранее (D1, D2, …), матрица покрытия таблицей, если уместно.
5. `## Дизайн` — нумерованные `### §1…§N` по темам: только то, что нужно
   исполнителю и не выражается Requirement'ом (алгоритм, порядок вызовов,
   имена env, тайминги). Нормативное поведение живёт в спек-дельте, не здесь.
6. `## Проверить перед реализацией` — если есть неподтверждённые внешние факты.
7. `## Вне scope` — что осознанно не делается (при пользе — «отметить в спеке
   как возможности»), с фазовостью: узкая фаза 1 + явно отложенная фаза 2.
8. `## Что затрагивается` — по каждому затронутому ТЗ / capability / § спеки:
   что меняется/дополняется; последним пунктом — «Требование DOC / BRAND: …»
   (обновление `docs/DOCUMENTATION.md` + §17 + brand-clean).
9. `## Grill` — **обязательная секция с шапкой провенанса** (ADR-0021).
   Заполняет главная сессия после `plan-griller`; `/tz` оставляет заготовку:
   ```
   ## Grill
   Grilled by: <plan-griller agent | session inline> | questions: N | plan changes: <одна строка или "none">
   ```
   Пустая или без шапки — `/tz-implement` останавливается.
10. `## Тир` — тир и **обоснование** (см. шаг 5), чтобы ревьюер мог оспорить.

### 3.2 Спек-дельта `specs/<capability>/spec.md`

- Ключевые слова — **английские** (`## ADDED Requirements`,
  `### Requirement:`, `#### Scenario:`, WHEN/THEN); текст — **русский**
  (ADR-0019 §6).
- Одна capability = один файл дельты; новое поведение — `## ADDED`,
  изменение существующего Requirement — `## MODIFIED` с **полным** текстом
  нового варианта.
- Каждое Requirement несёт метаданные (ADR-0017), как в `openspec/specs/`:
  ```
  ### Requirement: <короткое имя>
  <!-- id: <capability>.<kebab-id> -->
  <!-- enforced: path/to/file.py:Symbol -->
  Система SHALL …
  ```
  Якорь `enforced:` указывает на файл **и символ**, которые будут существовать
  после реализации; если файла/символа ещё нет — так и писать (планируемый
  путь), но не выдумывать несуществующий символ в уже существующем файле
  (дефект M1: `agent.py:build_agent_session`, которого никогда не было,
  прошёл все гейты; теперь `spec-lint.py` валидирует символ подстрокой).
- **Каждое Requirement — минимум один измеримый Scenario** (WHEN/THEN), плюс
  краевые: невалидный ввод, права, пустые значения, повторные вызовы.
  Scenario'ы — вход `test-author`; отдельного раздела «Тесты» больше нет.

### 3.3 `tasks.md`

Критерии приёмки прежнего формата, как чек-лист `- [ ]` — проверяемые
утверждения, не «сделать хорошо». Последний пункт всегда:

```
- [ ] Тесты change'а зелёные; `make test` зелёный; спек-дельта применена
  в `openspec/specs/`; `docs/DOCUMENTATION.md` (§8.x/§14/§16) + §17 changelog +
  версия `1.NN.0` обновлены; brand-clean.
```

Отдельными задачами: регенерация `flow.gen.ts`, alembic-миграция, i18n-локали,
задача на store-change (ADR-0018) — если применимо.

## Шаг 4. Зашитые принципы платформы (сверять каждый пункт)

- **DoD доработки** = спек-дельта в `openspec/specs/` (канон) **+**
  обновление `docs/DOCUMENTATION.md` (§8.x/§14/§16) + запись в §17 changelog +
  bump minor-версии `1.NN.0` (ADR-0019 §5 — документ ведётся параллельно навсегда).
- Правка `engine/schema.py` ⇒ **регенерация `flow.gen.ts`**
  (`python scripts/gen_ts_types.py`) — в дизайне и в `tasks.md`.
- Новый API-домен ⇒ роутер в **`api/routes/`** + `include_router` в
  `api/main.py` (существующие в корне `api/` не переносить).
- Новая таблица ⇒ репозиторий от **`_RepoBase`** в `storage/repos/*.py` +
  реэкспорт в `storage/repos/__init__.py` + модель в `storage/models.py` +
  **alembic-миграция** (гард `scripts/lint_migrations.py`, append-only).
- Границы пакетов исполняемые (`scripts/lint_imports.py`): `engine/` не
  импортирует UI/API/доменные пакеты, `monitoring/` — лист, `api/` никто не
  импортирует. Новое исключение — только в ALLOWLIST с причиной.
- UI-строки ⇒ **i18next, все 6 локалей** (`editor/src/i18n/locales/`,
  `tests/test_i18n.py`).
- **Brand-clean**: `scripts/lint_brand.py` сканирует все `.md`, включая сам
  proposal — конкурирующие продукты упоминать нельзя (перевыражать:
  «референсная платформа»); вендоры инфраструктуры допустимы.
- Версионирование флоу (№18): новые поля схемы — часть снапшота published-версии;
  справочники — freeze-on-write (№33 §6).
- **Изоляция по организации** (№17/№40): любая новая сущность / реестр / запись
  — scoped по организации (contextvar-tenancy в репозиториях, наследование
  каталогов вниз по иерархии). Требование + Scenario + критерий приёмки.
- **Латентность**: если трогается голосовой путь (тёрн, STT/TTS, LLM-вызовы,
  вебхуки в звонке) — отдельный §: влияние на тёрн (round-trip, число
  **последовательных** LLM-вызовов), меры смягчения (timeout, filler-реплика,
  кэш №31, стриминг первого предложения) и требование **замера p50/p90
  до/после** для оптимизаций.
- **Внешние SDK**: клиент изолировать в одном модуле (образец —
  `api/livekit_sip.py`); **best-effort** — недоступность внешнего сервиса не
  роняет CRUD/агента; версии **пинить** и сверять с текущей.
- **Обратная совместимость** при добавлении полей в существующие схемы:
  дефолт или вывод из существующего поля, чтобы старые флоу не ломались
  (образец — №57 `sip_method`: не задан ⇒ вывод из `mode`).
- Константы движка — `frozenset`/`MappingProxyType` (тест ТЗ №10).

## Шаг 5. Тир и конвейер

Тир задаётся по таблице «тир → конвейер → модели» из
`.claude/skills/feature-flow/SKILL.md` §1b (ADR-0021) — **свою тировку не
изобретать**. Сигналы: категория запроса, число затронутых пакетов,
миграции, кросс-репо контракты, голосовой путь.

- `light` — точечная правка/регресс: минимальный proposal (контекст + один
  Requirement с одним Scenario), гриль пропускается, тест всё равно пишет
  `test-author` до кода.
- `standard` — этот скилл как написан; гриль агентом или инлайн **с шапкой
  провенанса**.
- `deep` — + сравнение вариантов в `design.md` (`openspec instructions design
  --change <id> --json`); гриль **только агентом** `plan-griller`.

Тир и обоснование — в `## Тир` proposal.md; разработчик может его переопределить.

## Шаг 6. Гейты перед сдачей

```bash
npx -y @fission-ai/openspec@1.7.0 validate --all --strict   # пин как в Makefile.sdd
python3 .claude/scripts/spec-lint.py                         # id/enforced/якоря
python scripts/lint_brand.py                                 # или --stdin для текста из чата
make sdd-check
```

Все зелёные — передать change на `/tz-review`. Реализация без вердикта ревью
и без заполненного `## Grill` не начинается.

## Стиль

Русский, плотный и конкретный; ссылки на прежние ТЗ в форме «№NN», на
capability — путём (`openspec/specs/flow-execution/`), на § документа — «§8.x»;
честные оговорки о рисках и ограничениях прямо в тексте, а не между строк.
