# Авторинг ТЗ как OpenSpec change

Артефакт - каталог `openspec/changes/tz-NNN-<slug>/`:

| Файл | Что в нём |
|---|---|
| `proposal.md` | шапка-цитата, закрываемые дефекты / контекст, `## Why`, `## What Changes`, вне scope, что затрагивается в каноне, `## Grill`, `## Тир` |
| `specs/<capability>/spec.md` | дельта: `## ADDED Requirements` / `## MODIFIED Requirements` с `#### Scenario:` |
| `tasks.md` | критерии приёмки как чек-лист `- [ ]` |

**`docs/patches/` не закрыт - он просто не наш путь.** На ветке `main` идёт
параллельная разработка по старому процессу: файлы `docs/patches/patchNN-*.md`
там создавались (так появились №92-99) и будут создаваться до cutover процесса.
Change'ем оформляем требование **на ветке миграции** - и тогда файл в
`docs/patches/` этим change'ем **не создаётся**, дубля не делаем.

Отставание ветки миграции от `main` ловится не глазами, а
`bash sdd-kit/tools/cf/main-drift.sh` (из корня CF, `git fetch` перед прогоном;
exit 1 = дрейф есть) по протоколу `sdd-kit/tools/cf/sync-main.md`. Оттуда же
берётся список ТЗ и разделов, ещё не сконвертированных в openspec - глазами по
`ls` его не восстановить. Прямое следствие для шага 1: источник номера
`git ls-tree origin/main docs/patches/` **обязателен**.

Эталон стиля proposal - активная серия `openspec/changes/tz-092-*` ... `tz-099-*`
и пилотный `tz-100-*` (он же - самый полный: разделы серии плюс `## Grill` и
`## Тир`). Архивные `tz-082`...`tz-084` - прошлое поколение формата (разделы
`## Контекст` / `## Позиция` / `## Дизайн`, без `## Grill`/`## Тир`): читать как
историю, не копировать структуру. Прочитать `tz-100` и ещё один change серии
целиком до написания.

Цепочка процесса: **`/tz` -> `/tz-review` -> `plan-griller` -> `test-author` ->
`/tz-implement`** (ADR-0020: review и грилл - оба шага, не взаимозаменяемы).

## Шаг 1. Номер и id

Двойная нумерация (ADR-0019 §7):

- **id change** - `tz-NNN-<kebab-slug>`, `NNN` = сквозной номер ТЗ с ведущими
  нулями (`tz-092-...`), slug английский, как имена в архиве.
- **YouTrack-id** (если есть) - строкой в `proposal.md` (`> Тикет: WEB-1234`),
  **не** в имени каталога.

Следующий свободный номер = **максимум из четырёх источников** (считать, не
угадывать; ADR-0019 писался при №84 - цифра в нём устарела):

```bash
grep -oP 'ТЗ №\K[0-9]+' docs/DOCUMENTATION.md | sort -n | tail -1     # §17 changelog
ls docs/patches/ | grep -oP 'patch\K[0-9]+' | sort -n | tail -1       # легаси-архив, локально
git ls-tree --name-only origin/main docs/patches/ | grep -oP 'patch\K[0-9]+' | sort -n | tail -1
ls openspec/changes/ openspec/changes/archive/ | grep -oP '^tz-0*\K[0-9]+' | sort -n | tail -1
```

Третья команда **обязательна**, а не дублирует вторую: разработка на `main`
продолжает создавать патчи, а ветка миграции о них узнаёт только после мержа.
На `test-sdd-kit` локальный `docs/patches/` обрезан - там видно №91, тогда как
на `origin/main` уже лежат patch92...patch99. Без неё легко выдать №92 на занятый
номер. Полная картина отставания - `bash sdd-kit/tools/cf/main-drift.sh`
(протокол `sdd-kit/tools/cf/sync-main.md`).

Нюансы: **№33 использован дважды** (справочник LLM-моделей и события звонка в
Истории) - при подсчётах не споткнуться. Состояние на 2026-08-03: ТЗ №2-84 -
`docs/patches/` + `changes/archive/`; №85-91 - сконвертированы, лежат в
`changes/archive/tz-085-*`...`tz-091-*`; №92-99 - **активные** change'ы в
`openspec/changes/` (и параллельно исходники в `docs/patches/` на `origin/main`);
№100 - активный. Ни один источник в одиночку не даёт верный максимум.

**Change'ы не переписываются задним числом.** Реализованное требование -
зафиксированная история; коррекция - всегда **новый номер** (примеры: №48
корректирует №47, №49 заменяет модель №45/№46).

## Шаг 2. Разведка по коду - до текста

Ссылки - на **реальные** файлы, классы и поля, не на общие слова. До первой
строки текста проверить Grep/Read:

- какие модули/схемы/таблицы затрагиваются - точные пути
  (`engine/schema.py::TransferSpec`, `storage/models.py`, ...);
- **какие capability затронуты** - `ls openspec/specs/` (20 штук) и прочитать
  Requirements тех, что трогаются: дельта пишется поверх существующих `id:`,
  а не "с нуля";
- **точки расширения** - где уже заложен паттерн для подобного (реестры,
  builders, `*_PROVIDERS`/`*_KEY_ENVS`, репозитории) - перечислить в шапке-цитате;
- что из требуемого **уже реализовано** - в `## Why`, чтобы исполнитель
  достраивал, а не писал с нуля;
- кросс-репо контракты, если трогаются: `openspec list --specs --store cybernet-specs`,
  затем `openspec show <spec> --type spec --store cybernet-specs` (ADR-0018:
  правка контракта - отдельный change+PR в store, задача на него - в `tasks.md`).

Факты о внешнем мире (возможности провайдеров, параметры чужих API, версии
SDK), которые не удалось подтвердить, **не утверждать наугад** - писать явно
"**проверить перед реализацией**" и собирать в отдельный
`## Проверить перед реализацией` (образцы - `tz-100`, `tz-094`, `tz-097`).

## Шаг 3. Структура артефакта

### 3.1 `proposal.md`

Разделы - в этом порядке и **с этими именами** (эталон `tz-100`, серия
`tz-092`...`tz-099`). Обязательны все, кроме помеченных "если". В архиве ≤ №84
те же роли назывались `## Контекст` / `## Позиция` / `## Дизайн` - читая архив,
считать их синонимами п. 3/4/5; в новых change'ах используются имена ниже.

1. **H1**: `# tz-NNN - <Название по-русски>`.
2. **Шапка-цитата** (`>` сразу под H1): тикет YouTrack **или** источник, если
   тикета нет ("дефект найден верификацией спек, реестр `DEFECTS_CF.md`",
   "конвертировано из `docs/patches/patchNN-*.md`"); зависимости от прежних ТЗ и
   capability ("Опирается на: №83 (hangup-путь), №82 (гвард D3), ..."); **точки
   расширения** ("всё уже в коде, проверено" - с путями и именами хелперов);
   **подтверждение осуществимости** ("Осуществимость подтверждена по пиновым
   SDK: ..."). Если change активен и код ещё не написан - сказать прямо, что
   спек-дельта описывает **желаемое** поведение, а канон `openspec/specs/` пока
   описывает код "как есть" (образец - любой из `tz-092`...`tz-099`): иначе
   дельту принимают за описание реальности.
3. `## Закрываемые дефекты` - **если** ТЗ рождено из дефекта: ссылка на реестр
   `sdd-kit/docs/DEFECTS_CF.md` (+ раздел волны) и таблица
   "Дефект | Уровень | Где | Суть" с `file:line`. Где уместно - вторая таблица
   достижимости ("что уже произошло к моменту отказа | что видит клиент",
   образец `tz-100`) и факт отсутствия покрытия тестами, если он и скрыл дефект.
   ТЗ **без** дефекта-первопричины (новая функция) вместо этого раздела даёт
   `## Контекст` - что не работает/чего не хватает, с наблюдёнными фактами
   (uuid сессий, file:line, числа), а не общими словами.
4. `## Why` - почему чинится именно так: что из механизма **уже есть и
   работает** (чтобы исполнитель достраивал, а не писал с нуля), где ровно
   пробел, какие решения зафиксированы заранее, чем случай отличается от
   похожих прежних ТЗ ("различие с №92: там хватило `_scoped`, здесь фикс
   репозитория необходим, но недостаточен"). Здесь же - матрица покрытия
   таблицей, если уместна.
5. `## What Changes` - нумерованные пункты `**§1**...**§N**` (при дефектах - с
   пометкой закрываемого: `**§1 (RG1a)**`): только то, что нужно исполнителю и
   **не** выражается Requirement'ом - алгоритм, порядок вызовов, имена env,
   тайминги, отвергнутые альтернативы и почему отвергнуты. Нормативное
   поведение живёт в спек-дельте, не здесь. Последний § - тесты
   (`tests/test_patchNNN.py`, образец-аналог из `tests/`), поскольку Scenario'и
   идут в `test-author`.
6. `## Проверить перед реализацией` - **если** есть неподтверждённые внешние
   факты или риск регрессии легального пути.
7. `## Вне scope` - что осознанно не делается (при пользе - "отметить в спеке
   как возможности"), с фазовостью: узкая фаза 1 + явно отложенная фаза 2;
   отдельно - соседние дефекты того же файла, которые сюда сознательно не
   смешиваются (чтобы критический фикс не ждал их разбора).
8. `## Что затрагивается в каноне при реализации` - по каждому затронутому
   `openspec/specs/<capability>/spec.md`: какие `id:` и как (ADDED/MODIFIED);
   по каждому прежнему ТЗ и § документа: что меняется/дополняется; последним
   пунктом - "**Требование DOC / BRAND:** ..." (обновление
   `docs/DOCUMENTATION.md` §8.x/§11.x/§14/§16 + §17 changelog + версия
   `1.NN.0` + brand-clean).
9. `## Grill` - **обязательная секция с шапкой провенанса** (ADR-0021).
   Заполняет главная сессия после `plan-griller`; `/tz` оставляет заготовку:
   ```
   ## Grill
   Grilled by: <plan-griller agent | session inline> | questions: N | plan changes: <одна строка или "none">
   ```
   Пустая или без шапки - `/tz-implement` останавливается.
10. `## Тир` - тир и **обоснование** (см. шаг 5), чтобы ревьюер мог оспорить.

### 3.2 Спек-дельта `specs/<capability>/spec.md`

- Ключевые слова - **английские** (`## ADDED Requirements`,
  `### Requirement:`, `#### Scenario:`, WHEN/THEN); текст - **русский**
  (ADR-0019 §6).
- Одна capability = один файл дельты; новое поведение - `## ADDED`,
  изменение существующего Requirement - `## MODIFIED` с **полным** текстом
  нового варианта (правила идентичности - ниже).
- Каждое Requirement несёт метаданные (ADR-0017). Полные правила -
  `sdd-kit/tools/cf/mine-section.md` §4/§4a/§5 (whitelist общий для канона и
  дельт, не пересказывать - сверять по нему); здесь суть:
  ```
  ### Requirement: <короткое имя>
  <!-- id: <capability>.<kebab-id> -->
  <!-- entities: FlowRow, WebhookEndpointRow -->   # необязательный
  <!-- enforced: path/to/file.py:Symbol -->
  Система SHALL ...
  ```
  Разрешены **ровно три** ключа - `id`, `entities`, `enforced`. Любой другой
  HTML-комментарий (`<!-- verify: ... -->`, `<!-- note: ... -->`) даёт `unknown_key`
  в `spec-lint`: сомнение писать обычным текстом в теле требования. `id`
  уникален по всему канону (дубль - ошибка `duplicate_id`).
- Гарантия-инвариант без проверяемого сценария (в т.ч. негативная - "X никогда
  не попадает в Y") оформляется секцией `## Invariants` с блоками
  `### Invariant:` - **не** `### Requirement:` (вне `## Requirements` openspec
  его не видит) и **без** `#### Scenario:` (spec-lint это запрещает).
  Метаданные `id`/`enforced` там допустимы.
- Якорь `enforced:` - **проверяемый факт**, не намерение. Однозначное правило:
  - файл **существует** ⇒ якорить существующий символ-контейнер, который change
    правит (модуль, класс, метод, роут:
    `api/knowledge_bases.py:delete_knowledge_base`). Планируемый символ в
    существующем файле **не якорится вообще** - новый хелпер описывается текстом
    требования и задачей в `tasks.md`, якорь остаётся на контейнере;
  - файл **создаётся этим change'ем** ⇒ допустим планируемый путь и планируемый
    символ; в `tasks.md` обязана быть задача, которая их создаёт, а в
    `/tz-review` - пометка "файл создаётся";
  - несколько целей - через `;`, несколько символов/строк в одном файле - через
    `,` (`file.py:A,B`); суффикс может быть символом, номером строки или
    диапазоном `12-34`.
  Дефект M1: `agent.py:build_agent_session`, которого никогда не существовало,
  прошёл все гейты. `spec-lint.py` теперь валидирует символ подстрокой и в
  каноне, и в дельтах активных change'ев - но в дельте нерезолвящийся якорь
  печатается **советом**, а не нарушением (законный случай нового файла),
  поэтому разбор каждой такой строки - обязанность автора, см. шаг 6.
- `## MODIFIED Requirements` - правила идентичности (иначе openspec не сматчит
  требование при архивации и канон получит дубль вместо правки):
  - `### Requirement: <имя>` - **побуквенно** как в
    `openspec/specs/<capability>/spec.md`: скопировать строку, не перепечатывать;
  - `id:` - тот же **побуквенно**; `entities:` переносится как есть; `enforced:`
    переносится и обновляется на символы, которые будут энфорсить после
    реализации (по правилу выше);
  - текст даётся **целиком**: неизменные абзацы и Scenario'и - **дословно** из
    канона, меняется только то, что меняется. Дельта - не патч, а новая версия
    требования полностью; выпавший абзац = молча удалённое из канона поведение;
  - если требование покрывает несколько дефектов/аспектов, а change закрывает
    часть - незатронутые абзацы сохраняются и **помечаются**, что закрываются
    отдельной доработкой (образец - `tz-100`, `rag.cabinet-api` и RG2);
  - если то же требование трогает **другой активный** change - СТОП, доложить
    пользователю: два `MODIFIED` одного `id` конфликтуют при применении, порядок
    (какой change ждёт какого) решает он, а не автор ТЗ.
- **Каждое Requirement - минимум один измеримый Scenario** (WHEN/THEN), плюс
  краевые: невалидный ввод, права, пустые значения, повторные вызовы.
  Scenario'ы - вход `test-author`; отдельного раздела "Тесты" больше нет.

### 3.3 `tasks.md`

Критерии приёмки прежнего формата, как чек-лист `- [ ]` - проверяемые
утверждения, не "сделать хорошо". Последний пункт всегда:

```
- [ ] Тесты change'а зелёные; `make test` зелёный; спек-дельта применена
  в `openspec/specs/`; `docs/DOCUMENTATION.md` (§8.x/§14/§16) + §17 changelog +
  версия `1.NN.0` обновлены; brand-clean.
```

Отдельными задачами: регенерация `flow.gen.ts`, alembic-миграция, i18n-локали,
задача на store-change (ADR-0018) - если применимо.

## Шаг 4. Зашитые принципы платформы (сверять каждый пункт)

- **DoD доработки** = спек-дельта в `openspec/specs/` (канон) **+**
  обновление `docs/DOCUMENTATION.md` (§8.x/§14/§16) + запись в §17 changelog +
  bump minor-версии `1.NN.0` (ADR-0019 §5 - документ ведётся параллельно навсегда).
- Правка `engine/schema.py` ⇒ **регенерация `flow.gen.ts`**
  (`python scripts/gen_ts_types.py`) - в дизайне и в `tasks.md`.
- Новый API-домен ⇒ роутер в **`api/routes/`** + `include_router` в
  `api/main.py` (существующие в корне `api/` не переносить).
- Новая таблица ⇒ репозиторий от **`_RepoBase`** в `storage/repos/*.py` +
  реэкспорт в `storage/repos/__init__.py` + модель в `storage/models.py` +
  **alembic-миграция** (гард `scripts/lint_migrations.py`, append-only).
- Границы пакетов исполняемые (`scripts/lint_imports.py`): `engine/` не
  импортирует UI/API/доменные пакеты, `monitoring/` - лист, `api/` никто не
  импортирует. Новое исключение - только в ALLOWLIST с причиной.
- UI-строки ⇒ **i18next, все 6 локалей** (`editor/src/i18n/locales/`,
  `tests/test_i18n.py`).
- **Brand-clean**: `scripts/lint_brand.py` сканирует все `.md`, включая сам
  proposal - конкурирующие продукты упоминать нельзя (перевыражать:
  "референсная платформа"); вендоры инфраструктуры допустимы.
- Версионирование флоу (№18): новые поля схемы - часть снапшота published-версии;
  справочники - freeze-on-write (№33 §6).
- **Изоляция по организации** (№17/№40): любая новая сущность / реестр / запись
  - scoped по организации (contextvar-tenancy в репозиториях, наследование
  каталогов вниз по иерархии). Требование + Scenario + критерий приёмки.
- **Латентность**: если трогается голосовой путь (тёрн, STT/TTS, LLM-вызовы,
  вебхуки в звонке) - отдельный §: влияние на тёрн (round-trip, число
  **последовательных** LLM-вызовов), меры смягчения (timeout, filler-реплика,
  кэш №31, стриминг первого предложения) и требование **замера p50/p90
  до/после** для оптимизаций.
- **Внешние SDK**: клиент изолировать в одном модуле (образец -
  `api/livekit_sip.py`); **best-effort** - недоступность внешнего сервиса не
  роняет CRUD/агента; версии **пинить** и сверять с текущей.
- **Обратная совместимость** при добавлении полей в существующие схемы:
  дефолт или вывод из существующего поля, чтобы старые флоу не ломались
  (образец - №57 `sip_method`: не задан ⇒ вывод из `mode`).
- Константы движка - `frozenset`/`MappingProxyType` (тест ТЗ №10).

## Шаг 5. Тир и конвейер

Тир задаётся по таблицам "тир -> что значит" и "тир -> конвейер -> модели" из
`.claude/skills/feature-flow/SKILL.md`, раздел **`## 1b. Pick the tier`**
(заголовки в этом скилле английские - искать по `1b`, не по "§1b"; ADR-0010,
ADR-0021) - **свою тировку не изобретать**. Сигналы: категория запроса, число
затронутых пакетов, миграции, кросс-репо контракты, голосовой путь. Тир
масштабирует только **глубину подготовки**; гейты (спека, тесты до кода,
sdd-check, ревью) одинаковы на всех тирах.

- `light` - точечная правка/регресс: минимальный proposal (контекст + один
  Requirement с одним Scenario), гриль пропускается, тест всё равно пишет
  `test-author` до кода.
- `standard` - этот скилл как написан; гриль агентом или инлайн **с шапкой
  провенанса**.
- `deep` - + сравнение вариантов в `design.md` (`openspec instructions design
  --change <id> --json`); гриль **только агентом** `plan-griller`.

Тир и обоснование - в `## Тир` proposal.md; разработчик может его переопределить.

## Шаг 6. Гейты перед сдачей

```bash
make sdd-check                    # = AGENTS.md ≤500 + openspec validate --all --strict + spec-lint + sdd-flags
python scripts/lint_brand.py      # или --stdin для текста из чата
```

`make sdd-check` **сам** вызывает `npx -y @fission-ai/openspec@1.7.0 validate
--all --strict` и `python3 .claude/scripts/spec-lint.py` - прогонять их
отдельно нужно только чтобы увидеть вывод конкретного гейта. Его финальная
строка "spec-lint is advisory" - правда: без `SPEC_LINT_STRICT=1` spec-lint
выходит с 0, то есть его находки печатаются, но сборку не валят. Гейтом (exit≠0)
внутри `sdd-check` являются `AGENTS.md ≤ 500 строк`, `openspec validate --strict`
и `sdd-flags`.

**Что на авторинге ТЗ проверяется чем** - дельты активных change'ов
`spec-lint.py` теперь читает сам (`check_deltas`, `openspec/changes/*/specs/*/spec.md`;
`changes/archive/**` пропускается осознанно - закрытая история):

| Что | Чем на авторинге | Блокирует? |
|---|---|---|
| структура дельты, `### Requirement:`/`#### Scenario:`, англ. ключевые слова | `openspec validate --all --strict` (читает и `changes/**`) | да, exit≠0 |
| whitelist ключей `id`/`entities`/`enforced` (`unknown_key`), `missing_id`, `missing_enforced`, `#### Scenario:` под `## Invariants` | `spec-lint.py` по дельте, наравне с каноном | да - идёт в общий счётчик `metadata violations`, `SPEC_LINT_STRICT=1` ⇒ exit 1 |
| существование файла и символа в `enforced:` | `spec-lint.py` по дельте - **как совет**: `note: anchor does not resolve yet: <якорь> (expected only if this change creates it)` | нет, в violations не идёт |
| дубль `id` в дельте | **не проверяется намеренно**: `MODIFIED` переиспользует канонический `id` по замыслу, коллизия там - норма | - |
| свежесть `> Last verified:` | у дельт не считается вообще - дельта описывает поведение, которого ещё нет | - |
| brand-clean текста proposal | `lint_brand.py` (сканирует все `.md`, включая proposal) | да |

Почему якорь - совет, а не нарушение: дельта **законно** называет символ,
который change только создаст. Отсюда обязанность автора, которую инструмент
за него не выполнит - разобрать каждую `note` по правилу §3.2:

- файл создаётся этим change'ем ⇒ `note` ожидаема, в `tasks.md` обязана быть
  задача, которая файл создаёт, а в proposal - упоминание, что он новый;
- файл существует, а символа в нём нет ⇒ **это дефект дельты**, а не "совет":
  якорь переставить на существующий символ-контейнер, планируемый хелпер описать
  текстом требования. Именно так прошёл дефект M1.

Вывод по дельтам печатается отдельным блоком (`spec-lint: N change delta(s)
checked, M with findings`; перечисляются только дельты с находками). Проверить
один якорь точечно, не читая всю дельту:

```bash
python3 -c 'import importlib.util as u,sys;from pathlib import Path;s=u.spec_from_file_location("sl",".claude/scripts/spec-lint.py");m=u.module_from_spec(s);s.loader.exec_module(m);print(m.resolve_anchor(sys.argv[1],Path(".")) or "does not resolve")' 'storage/repos/knowledge.py:KnowledgeBaseRepository._row'
```

Все зелёные - передать change на `/tz-review`. Реализация без вердикта ревью
и без заполненного `## Grill` не начинается.

## Стиль

Русский, плотный и конкретный; ссылки на прежние ТЗ в форме "№NN", на
capability - путём (`openspec/specs/flow-execution/`), на § документа - "§8.x";
честные оговорки о рисках и ограничениях прямо в тексте, а не между строк.
