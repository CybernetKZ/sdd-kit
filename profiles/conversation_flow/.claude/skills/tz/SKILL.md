# Авторинг ТЗ как OpenSpec change

Артефакт - каталог `openspec/changes/tz-NNN-<slug>/`:

| Файл | Что в нём |
|---|---|
| `proposal.md` | шапка-цитата, закрываемые дефекты / контекст, `## Why`, `## What Changes`, вне scope, что затрагивается в каноне, `## Grill`, `## Тир` |
| `specs/<capability>/spec.md` | дельта: `## ADDED Requirements` / `## MODIFIED Requirements` с `#### Scenario:` |
| `tasks.md` | критерии приёмки как чек-лист `- [ ]` |

**`docs/patches/` не закрыт - он просто не наш путь.** На `main` идёт
параллельная разработка по старому процессу: `patchNN-*.md` там создавались (так
появились №92-99) и будут создаваться до cutover. Change'ем оформляем требование
**на ветке миграции**, и тогда файл в `docs/patches/` **не создаётся**.
Отставание ветки от `main` ловится не глазами, а
`bash sdd-kit/tools/cf/main-drift.sh` (из корня CF, `git fetch` перед прогоном;
exit 1 = дрейф) по протоколу `sdd-kit/tools/cf/sync-main.md`; оттуда же берётся
список ТЗ и разделов, ещё не сконвертированных в openspec - по `ls` его не
восстановить. Следствие для шага 1: источник номера
`git ls-tree origin/main docs/patches/` **обязателен**.

Эталон стиля - активная серия `openspec/changes/tz-092-*`...`tz-099-*` и
пилотный `tz-100-*` (самый полный: разделы серии плюс `## Grill` и `## Тир`);
до написания прочитать `tz-100` и ещё один change серии целиком. Архивные
`tz-082`...`tz-084` - прошлое поколение формата (`## Контекст` / `## Позиция` /
`## Дизайн`, без `## Grill`/`## Тир`): история, структуру не копировать.

Цепочка процесса: **`/tz` -> `/tz-review` -> `plan-griller` -> `test-author` ->
`/tz-implement`**; review и грилл - оба шага, не взаимозаменяемы.

## Шаг 1. Номер и id

**id change** - `tz-NNN-<kebab-slug>`: `NNN` = сквозной номер ТЗ с ведущими
нулями (`tz-092-...`), slug английский, как в архиве. **YouTrack-id** (если
есть) - строкой в `proposal.md` (`> Тикет: WEB-1234`), **не** в имени каталога.

Следующий свободный номер = **максимум из четырёх источников** (считать, не
угадывать):

```bash
grep -oP 'ТЗ №\K[0-9]+' docs/DOCUMENTATION.md | sort -n | tail -1     # §17 changelog
ls docs/patches/ | grep -oP 'patch\K[0-9]+' | sort -n | tail -1       # легаси-архив, локально
git ls-tree --name-only origin/main docs/patches/ | grep -oP 'patch\K[0-9]+' | sort -n | tail -1
ls openspec/changes/ openspec/changes/archive/ | grep -oP '^tz-0*\K[0-9]+' | sort -n | tail -1
```

Третья команда **обязательна**, а не дублирует вторую: `main` продолжает
создавать патчи, а ветка миграции узнаёт о них только после мержа. На
`test-sdd-kit` локальный `docs/patches/` обрезан (видно №91), тогда как на
`origin/main` уже лежат patch92...patch99 - без неё легко выдать №92 на занятый
номер. Ещё нюанс: **№33 использован дважды** (справочник LLM-моделей и события
звонка в Истории). Состояние на 2026-08-03: №2-84 - `docs/patches/` +
`changes/archive/`; №85-91 - в `changes/archive/`; №92-100 - **активные** (у
№92-99 параллельно исходники в `docs/patches/` на `origin/main`). Ни один
источник в одиночку не даёт верный максимум.

**Change'ы не переписываются задним числом.** Реализованное требование -
зафиксированная история; коррекция - всегда **новый номер** (примеры: №48
корректирует №47, №49 заменяет модель №45/№46).

## Шаг 2. Разведка по коду - до текста

Ссылки - на **реальные** файлы, классы и поля, не на общие слова. До первой
строки текста проверить Grep/Read:

- какие модули/схемы/таблицы затрагиваются - точные пути
  (`engine/schema.py::TransferSpec`, `storage/models.py`, ...);
- **какие capability затронуты** - `ls openspec/specs/` (20 штук) и прочитать
  Requirements тех, что трогаются: дельта пишется поверх существующих `id:`,
  а не "с нуля";
- **точки расширения** - где уже заложен паттерн для подобного (реестры,
  builders, `*_PROVIDERS`/`*_KEY_ENVS`, репозитории) - в шапку-цитату;
- что из требуемого **уже реализовано** - в `## Why`, чтобы исполнитель
  достраивал, а не писал с нуля;
- кросс-репо контракты, если трогаются: `openspec list --specs --store cybernet-specs`,
  затем `openspec show <spec> --type spec --store cybernet-specs`; правка
  контракта - отдельный change+PR в store, задача на него - в `tasks.md`.

Неподтверждённые факты о внешнем мире (возможности провайдеров, параметры чужих
API, версии SDK) **не утверждать наугад** - помечать "**проверить перед
реализацией**" и собирать в одноимённый раздел (образцы - `tz-100`, `tz-094`).

## Шаг 3. Структура артефакта

### 3.1 `proposal.md`

Разделы - в этом порядке и **с этими именами** (эталон `tz-100`, серия
`tz-092`...`tz-099`). Обязательны все, кроме помеченных "если". В архиве ≤ №84
те же роли назывались `## Контекст` / `## Позиция` / `## Дизайн` - читая архив,
считать их синонимами п. 3/4/5.

1. **H1**: `# tz-NNN - <Название по-русски>`.
2. **Шапка-цитата** (`>` сразу под H1): тикет YouTrack **или** источник, если
   тикета нет ("дефект найден верификацией спек, реестр `DEFECTS_CF.md`",
   "конвертировано из `patchNN-*.md`"); зависимости от прежних ТЗ и capability
   ("Опирается на: №83 (hangup-путь), №82 (гвард D3)"); **точки расширения** с
   путями и именами хелперов; **осуществимость** по пиновым SDK. Если код ещё не
   написан - сказать прямо, что дельта описывает **желаемое** поведение, а канон
   `openspec/specs/` пока описывает код "как есть" (`tz-092`...`tz-099`): иначе
   дельту принимают за описание реальности.
3. `## Закрываемые дефекты` - **если** ТЗ рождено из дефекта: ссылка на реестр
   `sdd-kit/docs/DEFECTS_CF.md` (+ раздел волны) и таблица
   "Дефект | Уровень | Где | Суть" с `file:line`; где уместно - вторая таблица
   достижимости ("что уже произошло к моменту отказа | что видит клиент",
   `tz-100`) и факт отсутствия покрытия тестами, если он и скрыл дефект. Новая
   функция без дефекта-первопричины вместо этого даёт `## Контекст` - что не
   работает/чего не хватает, с фактами (uuid сессий, `file:line`, числа).
4. `## Why` - почему чинится именно так: что из механизма **уже есть и
   работает** (чтобы исполнитель достраивал, а не писал с нуля), где ровно
   пробел, какие решения зафиксированы заранее, чем случай отличается от похожих
   прежних ТЗ ("различие с №92: там хватило `_scoped`, здесь фикс репозитория
   необходим, но недостаточен"); при уместности - матрица покрытия.
5. `## What Changes` - нумерованные `**§1**...**§N**` (при дефектах - с пометкой
   закрываемого: `**§1 (RG1a)**`): только то, что нужно исполнителю и **не**
   выражается Requirement'ом - алгоритм, порядок вызовов, имена env, тайминги,
   отвергнутые альтернативы и почему. Нормативное поведение - в спек-дельте.
   Последний § - тесты (`tests/test_patchNNN.py`, образец-аналог из `tests/`),
   поскольку Scenario'и идут в `test-author`.
6. `## Проверить перед реализацией` - **если** есть неподтверждённые внешние
   факты или риск регрессии легального пути.
7. `## Вне scope` - что осознанно не делается (при пользе - "отметить в спеке как
   возможности"), с фазовостью: узкая фаза 1 + явно отложенная фаза 2; отдельно -
   соседние дефекты того же файла, сознательно сюда не смешанные, чтобы
   критический фикс не ждал их разбора.
8. `## Что затрагивается в каноне при реализации` - по каждому затронутому
   `openspec/specs/<capability>/spec.md`: какие `id:` и как (ADDED/MODIFIED); по
   каждому прежнему ТЗ и § документа: что меняется; последним пунктом -
   "**Требование DOC / BRAND:** ..." (`docs/DOCUMENTATION.md`
   §8.x/§11.x/§14/§16 + §17 changelog + версия `1.NN.0` + brand-clean).
9. `## Grill` - **обязательная секция с шапкой провенанса**. Заполняет главная
   сессия после `plan-griller`; `/tz` оставляет заготовку:
   ```
   ## Grill
   Grilled by: <plan-griller agent | session inline> | questions: N | plan changes: <одна строка или "none">
   ```
   Пустая или без шапки - `/tz-implement` останавливается.
10. `## Тир` - тир и **обоснование** (см. шаг 5), чтобы ревьюер мог оспорить.

### 3.2 Спек-дельта `specs/<capability>/spec.md`

- Ключевые слова - **английские** (`## ADDED Requirements`, `### Requirement:`,
  `#### Scenario:`, WHEN/THEN); текст - **русский**. Одна capability = один файл
  дельты; новое поведение - `## ADDED`, изменение существующего Requirement -
  `## MODIFIED` с **полным** текстом нового варианта (идентичность - ниже).
- Метаданные Requirement'а: полные правила -
  `sdd-kit/tools/cf/mine-section.md` §4/§4a/§5 (whitelist общий для канона и
  дельт, не пересказывать - сверять по нему); суть:
  ```
  ### Requirement: <короткое имя>
  <!-- id: <capability>.<kebab-id> -->
  <!-- entities: FlowRow, WebhookEndpointRow -->   # необязательный
  <!-- enforced: path/to/file.py:Symbol -->
  Система SHALL ...
  ```
  Разрешены **ровно три** ключа - `id`, `entities`, `enforced`. Любой другой
  HTML-комментарий (`<!-- verify: ... -->`, `<!-- note: ... -->`) даёт `unknown_key`
  в `spec-lint`: сомнение писать обычным текстом в теле требования. `id`
  уникален по всему канону (дубль - `duplicate_id`).
- Гарантия-инвариант без проверяемого сценария (в т.ч. негативная - "X никогда
  не попадает в Y") идёт в секцию `## Invariants` блоками `### Invariant:` -
  **не** `### Requirement:` (вне `## Requirements` openspec его не видит) и
  **без** `#### Scenario:` (spec-lint это запрещает). `id`/`enforced` допустимы.
- Якорь `enforced:` - **проверяемый факт**, не намерение:
  - файл **существует** ⇒ якорить существующий символ-контейнер, который change
    правит (модуль, класс, метод, роут:
    `api/knowledge_bases.py:delete_knowledge_base`). Планируемый символ в
    существующем файле **не якорится вообще** - новый хелпер описывается текстом
    требования и задачей в `tasks.md`, якорь остаётся на контейнере;
  - файл **создаётся этим change'ем** ⇒ допустимы планируемый путь и символ; в
    `tasks.md` обязана быть задача, которая их создаёт, а в `/tz-review` -
    пометка "файл создаётся";
  - несколько целей - через `;`, несколько символов/строк в одном файле - через
    `,` (`file.py:A,B`); суффикс - символ, номер строки или диапазон `12-34`.
  Дефект M1: `agent.py:build_agent_session`, которого не существовало, прошёл все
  гейты. `spec-lint.py` валидирует символ подстрокой и в каноне, и в дельтах, но
  в дельте нерезолвящийся якорь - **совет**, а не нарушение (законный случай
  нового файла), поэтому разбор каждой такой строки на авторе (шаг 6).
- `## MODIFIED Requirements` - правила идентичности (иначе openspec не сматчит
  требование при архивации и канон получит дубль вместо правки):
  - `### Requirement: <имя>` и `id:` - **побуквенно** как в
    `openspec/specs/<capability>/spec.md`: скопировать строки, не перепечатывать.
    `entities:` переносится как есть; `enforced:` переносится и обновляется на
    символы, которые будут энфорсить после реализации (по правилу выше);
  - текст даётся **целиком**: неизменные абзацы и Scenario'и - **дословно** из
    канона, меняется только то, что меняется. Дельта - не патч, а новая версия
    требования полностью; выпавший абзац = молча удалённое из канона поведение;
  - закрывается часть аспектов требования ⇒ незатронутые абзацы сохраняются и
    **помечаются**, что закрываются отдельной доработкой (образец - `tz-100`,
    `rag.cabinet-api` и RG2);
  - то же требование трогает **другой активный** change ⇒ СТОП, доложить
    пользователю: два `MODIFIED` одного `id` конфликтуют при применении, порядок
    (какой change ждёт какого) решает он, а не автор ТЗ.
- **Каждое Requirement - минимум один измеримый Scenario** (WHEN/THEN), плюс
  краевые: невалидный ввод, права, пустые значения, повторные вызовы.
  Scenario'ы - вход `test-author`; отдельного раздела "Тесты" больше нет.

### 3.3 `tasks.md`

Критерии приёмки как чек-лист `- [ ]` - проверяемые утверждения, не "сделать
хорошо". Последний пункт всегда:

```
- [ ] Тесты change'а зелёные; `make test` зелёный; спек-дельта применена
  в `openspec/specs/`; `docs/DOCUMENTATION.md` (§8.x/§14/§16) + §17 changelog +
  версия `1.NN.0` обновлены; brand-clean.
```

Отдельными задачами - если применимо: регенерация `flow.gen.ts`,
alembic-миграция, i18n-локали, store-change по кросс-репо контракту.

## Шаг 4. Зашитые принципы платформы

Сверить каждый пункт раздела **«Конвенции»** в `AGENTS.md` (репозиторий от
`_RepoBase` + миграция, `api/routes/`, `frozenset`-константы, границы пакетов
`lint_imports`, i18n 6 локалей, DoD, версионирование флоу и freeze-on-write,
изоляция по организации, латентность голосового пути с p50/p90, изоляция и пин
внешних SDK, обратная совместимость новых полей). Задетая конвенция = Requirement
+ Scenario + критерий приёмки, а не "учтём при реализации". Специфично для
авторинга:

- `scripts/lint_brand.py` сканирует **все** `.md`, включая сам proposal:
  конкурирующие продукты перевыражать ("референсная платформа"); вендоры
  инфраструктуры допустимы;
- правка `engine/schema.py` ⇒ регенерация `flow.gen.ts`
  (`python scripts/gen_ts_types.py`) - в `## What Changes` и в `tasks.md`.

## Шаг 5. Тир и конвейер

Тир задаётся по таблицам "тир -> что значит" и "тир -> конвейер -> модели" из
`.claude/skills/feature-flow/SKILL.md`, раздел **`## 1b. Pick the tier`**
(заголовки там английские - искать по `1b`, не по "§1b") - **свою тировку не
изобретать**. Сигналы: категория запроса, число затронутых пакетов, миграции,
кросс-репо контракты, голосовой путь. Тир масштабирует только **глубину
подготовки**; гейты (спека, тесты до кода, sdd-check, ревью) одинаковы везде.

- `light` - точечная правка/регресс: минимальный proposal (контекст + один
  Requirement с одним Scenario), гриль пропускается, тест всё равно пишет
  `test-author` до кода.
- `standard` - этот скилл как написан; гриль агентом или инлайн **с шапкой
  провенанса**.
- `deep` - + сравнение вариантов в `design.md` (`openspec instructions design
  --change <id> --json`); гриль **только агентом** `plan-griller`.

Тир и обоснование - в `## Тир` proposal.md; разработчик может его переопределить.

## Шаг 6. Гейты перед сдачей

```bash
bash scripts/sdd/check.sh         # = AGENTS.md ≤500 + openspec validate --all --strict + spec-lint
python scripts/lint_brand.py      # или --stdin для текста из чата
```

`scripts/sdd/check.sh` **сам** вызывает `npx -y @fission-ai/openspec@1.7.0 validate
--all --strict` и `python3 .claude/scripts/spec-lint.py` - отдельно их прогоняют
только чтобы увидеть вывод конкретного гейта. Его строка "spec-lint is advisory"
- правда: без `SPEC_LINT_STRICT=1` spec-lint выходит с 0, находки печатаются, но
сборку не валят; гейты (exit≠0) внутри `sdd-check` - `AGENTS.md ≤ 500 строк`
и `openspec validate --strict`. Дельты активных change'ов
`spec-lint.py` читает сам (`check_deltas`, `openspec/changes/*/specs/*/spec.md`;
`changes/archive/**` пропускается осознанно - закрытая история).

| Что | Чем на авторинге | Блокирует? |
|---|---|---|
| структура дельты, `### Requirement:`/`#### Scenario:`, англ. ключевые слова | `openspec validate --all --strict` (читает и `changes/**`) | да, exit≠0 |
| whitelist ключей `id`/`entities`/`enforced` (`unknown_key`), `missing_id`, `missing_enforced`, `#### Scenario:` под `## Invariants` | `spec-lint.py` по дельте, наравне с каноном | да - идёт в общий счётчик `metadata violations`, `SPEC_LINT_STRICT=1` ⇒ exit 1 |
| существование файла и символа в `enforced:` | `spec-lint.py` по дельте - **как совет**: `note: anchor does not resolve yet: <якорь> (expected only if this change creates it)` | нет, в violations не идёт |
| дубль `id` в дельте | **не проверяется намеренно**: `MODIFIED` переиспользует канонический `id` по замыслу, коллизия там - норма | - |
| свежесть `> Last verified:` | у дельт не считается вообще - дельта описывает поведение, которого ещё нет | - |
| brand-clean текста proposal | `lint_brand.py` (сканирует все `.md`, включая proposal) | да |

Вывод по дельтам - отдельный блок (`spec-lint: N change delta(s) checked, M with
findings`; перечисляются только дельты с находками). Каждую `note` по якорю
разобрать по правилу §3.2: файл создаётся этим change'ем ⇒ ожидаемо (в `tasks.md`
