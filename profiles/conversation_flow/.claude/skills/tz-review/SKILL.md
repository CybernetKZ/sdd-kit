# Ревью change'а перед реализацией

Вход — `openspec/changes/tz-NNN-<slug>/` (или текст change'а, вставленный в чат).
Выход — **список замечаний с путями** и **вердикт**: «готово к реализации» /
«требует правок» (≡ `PLAN HOLDS` / `FIX THE PLAN`, ADR-0020 п.3).

Место в цепочке: `/tz` → **`/tz-review`** → `plan-griller` → `test-author` →
`/tz-implement`. Это **не** дубль гриллера (ADR-0020 п.2): здесь механический
аудит документа с вердиктом в чат, там — интерактивный допрос, который пишет
`## Grill` в proposal.md. Ревью бежит **первым**: гриллить документ с
выдуманными фактами бессмысленно.

**Ничего не редактировать.** Замечания — в чат; правки вносит автор (или по его
явной просьбе — через `/tz`). Каждое проверяемое утверждение подтверждается
Grep/Read/Bash по репозиторию, а не принимается на слово.

## 1. Формат артефакта

Структура — по `.claude/skills/tz/SKILL.md` §3 (не пересказывать её здесь,
сверять по ней). Проверить наличие и содержательность:

- `proposal.md`: H1 `# tz-NNN — <Название>`; шапка-цитата (тикет, зависимости
  от прежних ТЗ, точки расширения, подтверждение осуществимости);
  `## Контекст`; `## Позиция`; `## Дизайн` (§1…§N); `## Вне scope`;
  `## Что затрагивается` (последний пункт — DOC/BRAND); `## Тир` с
  обоснованием; `## Grill` — **заготовка с шапкой провенанса присутствует**
  (заполненность — предмет следующего шага, не этого).
- `specs/<capability>/spec.md`: хотя бы одна дельта; правильные англоязычные
  ключевые слова (`## ADDED Requirements` / `## MODIFIED Requirements`,
  `### Requirement:`, `#### Scenario:`, WHEN/THEN) при русском тексте;
  у каждого Requirement — `<!-- id: -->` и `<!-- enforced: -->`;
  **у каждого Requirement минимум один измеримый Scenario**.
- `tasks.md`: чек-лист `- [ ]`, проверяемые утверждения, финальный пункт с
  тестами + `make test` + спекой + DOCUMENTATION.md + brand-clean;
  отдельные задачи на регенерацию `flow.gen.ts` / миграцию / i18n / store-change,
  если change их трогает. Заглушки («сделать хорошо», «покрыть тестами») —
  замечание.
- `light`-тир: сокращённый proposal и отсутствие гриля законны — не требовать
  полной структуры; всё остальное (Scenario, tasks, якоря) обязательно.

## 2. Факты кода — ключевая часть

- Каждый упомянутый файл/класс/поле/функция/точка расширения **существует**
  (Grep по точному имени; в замечание — `file:line` фактического положения).
- Утверждения о текущем поведении («сейчас X делает Y», «уже реализовано»,
  «отсутствует») **сверяются с кодом** грепом, а не с памятью.
- Числа (строки, количества, версии SDK, тайминги) проверяются; устаревшие —
  замечание с фактическими значениями (не блокирует, если направление не
  меняется — предложить пометку «на момент написания»).
- Точки расширения из шапки реально пригодны: паттерн существует и расширяем
  именно так, как заявляет change.
- Заявленная осуществимость по внешним SDK — проверить на **пиновой** версии
  (`pip show <pkg>` / `package.json`), а не по описанию в тексте.

### 2a. Якоря `enforced:` — проверять символ, не только файл

Дефект **M1** миграции: майнер сослался на `agent.py:build_agent_session`,
которого никогда не существовало, и это прошло все гейты — проверялся только
файл. `spec-lint.py` теперь валидирует и суффикс (номер строки / диапазон /
символ подстрокой), но инструмент — не замена глазам ревьюера:

```bash
python3 .claude/scripts/spec-lint.py            # общий прогон
grep -rn 'enforced:' openspec/changes/tz-NNN-*/specs/   # затем каждый якорь руками
```

По каждому якорю `path:Symbol`:

- файл существует (или явно помечен как создаваемый этим change'ем);
- символ **существует в этом файле** (`grep -n '<Symbol>' <path>`) — либо
  создаётся задачей из `tasks.md`; символ, который «должен быть, но его нет и
  никто его не создаёт» — блокирующее замечание;
- символ находится именно там, где заявлено (не в другом модуле с тем же именем);
- якорь указывает на энфорсящий код, а не на тест или на docstring.

## 3. Непротиворечивость спекам и истории

- Change не переписывает зафиксированную историю: `openspec/changes/archive/`
  и `docs/patches/` append-only; коррекция реализованного — новый номер.
- Дельта `## MODIFIED` совпадает по `id:` с существующим Requirement в
  `openspec/specs/<capability>/spec.md` и содержит **полный** новый текст;
  `## ADDED` не дублирует уже существующее Requirement другими словами.
- Нет конфликта с зашитыми принципами платформы (`/tz` шаг 4): изоляция
  организаций №17/№40, freeze-on-write №33 §6, версионирование флоу №18,
  границы пакетов `lint_imports`, латентность голосового пути,
  best-effort внешних сервисов, обратная совместимость полей схемы.
- Расхождение с `docs/DOCUMENTATION.md` — отметить, но канон — `openspec/specs/`
  (ADR-0019 §5); если документ противоречит спеке, замечание адресуется документу.
- Кросс-репо контракт: если change трогает `/v1`, вебхуки или RAG-контракт —
  сверить со store (`openspec show <spec> --type spec --store cybernet-specs`)
  и убедиться, что в `tasks.md` есть задача на отдельный store-change (ADR-0018).
- При конфликте — **доложить в замечаниях**, не подгонять change и не «чинить»
  его молча.

## 4. Формальности

- **Номер**: сквозной, следующий свободный — пересчитать по всем четырём
  источникам (`/tz` шаг 1); помнить дубль №33 и что ТЗ №85–91 лежат только в
  `docs/patches/`. Занятый номер — блокирующее замечание.
- **id каталога** `tz-NNN-<kebab-slug>` с ведущими нулями; YouTrack-id — в
  proposal, не в имени.
- **Гейты** прогнать самому, а не поверить на слово:
  ```bash
  npx -y @fission-ai/openspec@1.7.0 validate --all --strict
  python3 .claude/scripts/spec-lint.py
  python scripts/lint_brand.py            # --stdin для текста из чата
  make sdd-check
  ```
- **Brand-clean**: стоп-слова брендинга запрещены во всех `.md`, включая сам
  proposal (`scripts/lint_brand.py`, режим `--stdin`).

## Вывод

1. **Замечания** — нумерованный список; каждое с `file:line` и предложением,
   как исправить. Группировать: формат / факты кода / якоря / непротиворечивость
   / формальности. Помечать блокирующие.
2. **Результаты гейтов** — по строке на каждый (`validate`, `spec-lint`,
   `lint_brand`, `sdd-check`): что вернул.
3. **Вердикт** — ровно одной строкой: «**готово к реализации**» (при мелких
   правках — перечислить какими) или «**требует правок**» (перечислить
   блокирующие).

После вердикта «готово» и решения автора по замечаниям change идёт на
`plan-griller` (standard/deep) и затем на `/tz-implement`.
