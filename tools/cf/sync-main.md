# sync-main — догон дрейфа с ветки разработки

Инструкция для агента-синхронизатора. Разработка идёт на `main` по старому
процессу (патчи + LIVING SPEC) параллельно с миграцией на openspec в
`test-sdd-kit`. Задача — периодически подтягивать накопившееся, ничего не
теряя. Мерж делает Даниил, агент — только чтение, конвертация и верификация.

## Вход

- Репозиторий: `/home/octrow/cybernet/conversation_flow`
- Отчёт о дрейфе: `bash tools/cf/main-drift.sh` (из корня; `--main <ref>`,
  по умолчанию `origin/main`; exit 1 = дрейф есть). Перед прогоном `git fetch`.
- Протоколы: [patch2change.md](patch2change.md) (архивная конвертация ТЗ),
  [mine-section.md](mine-section.md) (новый раздел LIVING SPEC → capability-спека),
  [verify-section.md](verify-section.md) (ре-верификация спеки против кода).

## Порядок операций (не переставлять)

`spec-lint` считает спеку STALE, сравнивая её `> Last verified: … (commit …)` с
`git diff <commit>..HEAD` — то есть **видит только историю своей ветки**. Пока
`main` не влит в `test-sdd-kit`, изменения кода на `main` для гейта не
существуют: `spec-lint` зелёный, спеки описывают вчерашний код. Это ловушка №1,
из неё вытекает жёсткий порядок:

1. **drift-отчёт до мержа** — `bash tools/cf/main-drift.sh`, сохранить вывод.
   Это единственный момент, когда список «что именно приедет» получается дёшево.
2. **мерж `main` → `test-sdd-kit`** — работа Даниила. Ни скрипт, ни агент
   мержа не делают и не предлагают его сделать за него.
3. **прогон drift после мержа** — должен показать 0 ТЗ и 0 файлов дрейфа
   (иначе мерж неполный или на `main` уже приехало новое).
4. **ре-верификация** спек из раздела 3 отчёта — по
   [verify-section.md](verify-section.md), только после мержа: до него в рабочем
   дереве нет нового кода, сверять нечего.
5. **обновление маркеров** `> Last verified: <дата> (commit <hash мержа>)` —
   только у тех спек, которые реально перепроверены. Обновлять маркер без
   верификации запрещено: это единственная защита от «спека врёт, а гейт зелёный».
6. **`python3 .claude/scripts/spec-lint.py --strict`** и
   `npx -y @fission-ai/openspec@1.7.0 validate --all --strict` — оба зелёные.

## Раздел 1 отчёта: ТЗ без openspec-представления

Куда класть change, решает **факт реализации кода**, а не дата ТЗ. OpenSpec:
change живёт в `openspec/changes/` пока не реализован, после реализации
архивируется.

Признаки реализованного ТЗ №N (достаточно любого, проверять на `main`):

- в §17 changelog `docs/DOCUMENTATION.md` есть запись со ссылкой «ТЗ №N»
  (номер версии документа с номером ТЗ **не совпадает**: ТЗ №91 → 1.88.0 —
  искать по «ТЗ №N», не по `1.N.0`);
- существует `tests/test_patchN.py`;
- поведение видно в коде по путям из §1..§N патча (последняя инстанция, если
  первые два признака противоречат друг другу).

Развилка:

- **реализовано** → `openspec/changes/archive/tz-0NN-<slug>/` по
  [patch2change.md](patch2change.md), плюс поведение должно быть в
  `openspec/specs/` (если раздел LIVING SPEC новый — [mine-section.md](mine-section.md)).
- **не реализовано** (типичный случай для свежих патчей: ТЗ написано как
  требование на исправление найденного дефекта, кода ещё нет) → **активный**
  `openspec/changes/tz-0NN-<slug>/` с `proposal.md` + `tasks.md`, чекбоксы
  `- [ ]` (не `- [x]`) и спек-дельтами `specs/<capability>/spec.md` там, где
  требование меняет поведение существующей capability. Архивировать такой
  change нельзя — он архивируется, когда код будет написан.
- **реализовано частично** → активный change, в `tasks.md` отмечены
  выполненные пункты; в `proposal.md` строкой указано, что уже в коде.

## Раздел 2 отчёта: LIVING SPEC

- Новые записи §17 — история, в спеки не конвертируются
  ([mine-section.md](mine-section.md) п. 7). Их роль здесь другая: по ним
  сверяется признак «реализовано» из раздела 1.
- Новые/переписанные нормативные разделы (не §17) — вход для
  [mine-section.md](mine-section.md): либо новая capability-спека, либо правка
  существующей + ре-верификация.
- **Ловушка №2: мерж-конфликт в `docs/DOCUMENTATION.md` ожидаем и штатен.**
  На `test-sdd-kit` в шапку добавлен блок про канон openspec, на `main`
  правится тело документа и §17. Конфликт будет по шапке (первые ~30 строк) и,
  реже, по §17. Разрешение — **объединение, не выбор стороны**: блок про канон
  openspec с `test-sdd-kit` + версия документа, дата и все записи §17 с `main`.
  `git checkout --ours/--theirs` на этом файле запрещён: любая из сторон теряет
  чужие правки молча.

## Раздел 3 отчёта: изменённый код

- Файл с якорями → перечисленные спеки идут в ре-верификацию (шаг 4 порядка).
  Ре-верифицируется вся спека, а не один Requirement: якоря в ней пересекаются.
- Файл без якорей ни в одной спеке → это либо не-код (`AGENTS.md`, `values/*.yaml`,
  CI), либо **пробел покрытия**: код, который ни одна capability-спека не
  описывает. Пробел — не ошибка скрипта: занести в отчёт как кандидата на
  доработку спеки (пример: `editor/src/shell/TelephonyPage.tsx` — UI телефонии
  ни в одной спеке не заякорен).
- Скрипт снимает пути из `enforced:`-якорей той же логикой, что
  `templates/spec-lint.py::resolve_anchor`, но суффиксы (`:12-34`, `:symbol`) не
  валидирует. Поэтому спека со сломанным якорем может попасть в список ложно —
  проверяется прогоном `spec-lint` на шаге 6.

## Отчёт агента

Terse: (1) прогнанные ТЗ → куда легли (active / archive) с обоснованием
признака реализации; (2) конвертированные разделы LIVING SPEC; (3) ре-верифицированные
спеки → вердикт + новый `Last verified`-коммит; (4) пробелы покрытия и
MISMATCH-кандидаты в `docs/DEFECTS_CF.md`; (5) что осталось (например: мерж
ещё не сделан — тогда шаги 4–6 не начинались).
