# sdd-kit

> Перевод от 2026-08-03. Источник истины - `README.md` (английский):
> при расхождении верен он. Правишь README.md - обнови и этот файл.

Инструмент для быстрой настройки (bootstrap) разработки на основе спецификаций (SDD) в любом репозитории - как новом,
так и старом.
Всего один скрипт. Он идемпотентен: никогда не перезаписывает существующие файлы, а только добавляет то, чего не
хватает.

**С чего начать:**

- Новичок в команде или в SDD -> `docs/ONBOARDING.md`.
- Как устроен процесс (сигнал -> влитый PR) -> `WORKFLOW.md`.
- Установка кита в репозиторий -> читай дальше этот файл.
- Кит уже стоит, вопрос "чем из этого пользоваться и как начать таску?" ->
  [После установки: чем пользоваться](#после-установки-чем-пользоваться) и
  [Работа над новой задачей](#работа-над-новой-задачей).

## Usage

Одна команда - из каталога репозитория, который настраиваем:

```bash
sdd-kit/install.sh                   # файлы репозитория + личные инструменты на машине
sdd-kit/install.sh --repo-only       # только файлы репозитория (путь можно не указывать - берётся текущий каталог)
sdd-kit/install.sh --machine-only    # только личные инструменты на этой машине
sdd-kit/install.sh --refresh         # обновить файлы кита в репозитории до текущей версии
sdd-kit/uninstall.sh /path/to/repo   # откатить репозиторную часть: вернуть репозиторий как было
sdd-kit/uninstall.sh --force /path/to/repo  # удалить файлы кита, даже если их правили после установки
```

Запускать повторно - безопасно. У каждого вопроса есть значение по умолчанию, и просто Enter его принимает
(`[Y/n]` - да, `[y/N]` - нет). `SDD_KIT_ASSUME_YES=1` или запуск без TTY берёт все значения по умолчанию без
вопросов; в этом режиме ничего, что скачивает и запускает код из сети, не выполняется - вместо этого печатается
команда, которую надо выполнить самому. Токен YouTrack читается только из интерактивного ввода.

`bootstrap.sh` и `setup-dev.sh` остаются как deprecated-обёртки над `--repo-only` / `--machine-only` и будут
удалены через релиз.

## Обновление кита в репозитории: `install.sh --refresh`

Обычная установка ничего не перезаписывает, поэтому в репозитории, настроенном месяцы назад, остаются старые
шаблоны. Чтобы подтянуть текущие:

```bash
cd /путь/к/sdd-kit && git pull
cd /путь/к/репозиторию && /путь/к/sdd-kit/install.sh --refresh
```

`--refresh` перезаписывает только **манифест файлов кита** (список - в `install.sh`, функция `kit_manifest`):
`.claude/hooks/*.cjs`, `.claude/agents/*.md`, `.claude/skills/{feature-flow,incident-flow}/SKILL.md`,
`.claude/scripts/{spec-lint.py,sdd-doctor.sh,review-prompt.md}`, `Makefile.sdd`,
`.github/workflows/{sdd-ci,autoreview}.yml` и `.git/hooks/pre-commit` (пересобирается со вставкой LIVING SPEC,
если так велит профиль). Каждый изменённый файл печатается как `refreshed: <path> (+X/-Y lines)`, второй прогон
даёт ноль изменений. Файлы репозитория не трогаются: `AGENTS.md`, `CLAUDE.md`, `.spec-guard-paths`,
`feature_flags.py`, `.claude/expected-env`, `ruff.toml`, `openspec/**`, `.mcp.json`. `.claude/settings.json`
только сравнивается: если блок `hooks` разошёлся с шаблоном - WARN и слияние вручную (в репо могли добавить свои
хуки). Результат смотреть через `git diff` до коммита. `--refresh` работает только с репозиторной частью: у
машинных инструментов нет семантики обновления - для них перезапустите `--machine-only`.

## Деинсталляция

`uninstall.sh` разворачивает установку с одним правилом безопасности: файл удаляется,
только если он байт-в-байт совпадает с шаблоном кита (или payload профиля), который его
поставил - всё, что команда правила, остаётся с WARN и точной командой для ручного
удаления. `--force` удаляет файлы кита даже изменёнными (полезно, когда в репозитории
стоит старая версия кита); AGENTS.md и openspec/ - командный контент, force их не
трогает никогда. Переименование `CLAUDE.md -> AGENTS.md` предлагается откатить;
`openspec/` (спеки + change'и) удаляется только после явного "да". Регистрация центрального
стора - машинное состояние, общее для всех репозиториев: снимается только при интерактивном
"да" или с `--force`; unattended-прогон (нет TTY / `SDD_KIT_ASSUME_YES=1`) её сохраняет и
печатает ручную команду. На нетронутой установке раунд-трип чистый: `git status` показывает
репозиторий ровно таким, каким он был до установки.

## What it installs

| Artifact | Purpose |
|---|---|
| `AGENTS.md` (+ симлинк `CLAUDE.md`) | Главный контекст для ИИ-агентов, до 500 строк; существующий `CLAUDE.md` переименовывается, а не теряется |
| `openspec/` | `openspec init --tools claude` на запинованном CLI **`@fission-ai/openspec@1.7.0`** (тот же пин в `install.sh`, `Makefile.sdd` и `sdd-doctor.sh`, каждый помечен `# openspec-pin` - поднимать версию только во всех сразу). Создаёт `openspec/specs/` (capability-спеки), `openspec/changes/` (+ `archive/`), `openspec/config.yaml` и шесть skills `.claude/skills/openspec-*`. Профиль может вместо инициализации восстановить готовое дерево `openspec/` из `PROFILE_OPENSPEC_SEED_REF` |
| `Makefile.sdd` (+ `-include` в Makefile) | 6 целей: `sdd-check` (гейт: `AGENTS.md` существует и ≤500 строк + `openspec validate --all --strict` + `sdd-flags`, блокируют; spec-lint консультативно, пока не включён `SPEC_LINT_STRICT=1`), `sdd-flags`, `sdd-doctor`, `sdd-test` (консультативные ruff+pytest, переопределяется `SDD_TEST_CMD`), `sdd-review` (локальное ИИ-ревью диффа), `sdd-index` (граф graphify, гейтом не бывает - ADR-0004). При любой ошибке выводится конкретный шаг `next:` |
| `feature_flags.py` | Минимальный реестр фича-флагов (ADR-0007), **по требованию - ни один шаг процесса не обязывает заводить флаг** (ADR-0015): имя флага -> дата `expires`, включение через `FLAG_<NAME>=1`, чтение только через `is_enabled()`; `make sdd-flags` предупреждает 7 дней после истечения срока, потом роняет CI. Lifecycle описан в docstring модуля; не забудь `git add` - гейт смотрит на файлы в индексе |
| `.github/workflows/sdd-ci.yml` | SDD-проверка на каждом pull request - **сегодня консультативная**: branch protection выключена, required check не назначен (ADR-0015); + джоба `tbd-gates` (ADR-0006): возраст ветки (предупреждение >2 дней, красная >5) и размер PR (ошибка >1500 изменённых строк; если репозиторию нужен другой порог - поправь `PR_XL_LINES` в самом workflow) - метки-обходы `long-lived-ok`/`xl-ok` требуют причину `Why ...:` в описании PR |
| `.github/workflows/autoreview.yml` | Автоматическое ревью PR: ИИ-ревью через headless `claude -p` с общим промптом `.claude/scripts/review-prompt.md`, которому подаётся отчёт статических анализаторов (radon, complexipy, vulture, semgrep security patterns), и он обязан его проверить перед публикацией; без секрета `CLAUDE_CODE_OAUTH_TOKEN` job завершается за секунды |
| `.claude/agents/` | 7 агентов: `planner` и `plan-griller` (план и гриль фазы 2 на opus через `model` frontmatter, ADR-0013), `test-author` (падающие тесты фазы 3 по спек-дельте, sonnet, ADR-0016), `executor` (реализация фазы 4 на sonnet, строго по `tasks.md`, ADR-0021), `backend-reviewer` (Python/FastAPI) и `database-reviewer` (PostgreSQL/SQLAlchemy) для шага ИИ-ревью, `repo-auditor` (read-only аудит агентопригодности репо). Полная таблица со связкой с OpenSpec: [После установки](#после-установки-чем-пользоваться) |
| `.claude/hooks/` + `.claude/settings.json` | spec-guard (блокирует правки кода без активной `openspec/changes/<id>/` - **молчит, пока в `.spec-guard-paths` нет ни одного префикса пути**), блокировщик `git commit --no-verify` и пакет выживания при PreCompact (`.claude/last-session-state.md` - активное изменение + незакоммиченная работа, чтобы агенты продолжали работу после компакции; идея из ProjectStore, ADR-0008) |
| `.claude/scripts/spec-lint.py` | Свежесть спецификаций (`Last verified` против `git diff` по якорям `enforced:`) + проверка метаданных спек; выполняется внутри `sdd-check`, только предупреждает, пока не включён `SPEC_LINT_STRICT=1`. Формат якоря: `<!-- enforced: path/to/file.py:ClassName.method -->` - сначала путь от корня репозитория, после двоеточия символ (или строка/диапазон). **Проверяются обе половины**: отсутствующий файл ИЛИ символ, которого в файле нет, делает спеку MISSING (голые якоря вида `ClassName.method()` больше не резолвятся - см. "Заметки о дизайне") |
| `.git/hooks/pre-commit` | Защита от коммитов в защищённые ветки (main/master/prod/stage блокируются, dev предупреждает; `SDD_ALLOW_PROTECTED=1` обходит), автофикс+форматирование ruff для застейдженного Python, проверки гигиены (маркеры слияния, файлы >5 МБ, `breakpoint()`, паттерны секретов/токенов, новые сабмодули, битый JSON/TOML/YAML) + `make sdd-check` (если хук уже есть, сливается вручную) |
| `.claude/scripts/review-prompt.md` | Единственный канонический промпт ИИ-ревью: его читают и `make sdd-review`, и `autoreview.yml` |
| `.claude/scripts/sdd-doctor.sh` | Доктор окружения (`make sdd-doctor`): нужные утилиты (git, node, python3 ≥3.10, uv, ruff, openspec), claude/gh CLI и авторизация, регистрация в сторе, токен youtrack, наличие хуков/pre-commit, и (по профилю) наличие файлов `.env` для каждого сервиса, нужных свежему клону - только пути, никогда не значения секретов; запускается в конце установки; находки в формате `{level, group, code, message, next}` с точной командой-исправлением, `--json` для машин (ADR-0008) |
| `.mcp.json` | MCP-серверы проекта: context7 + youtrack (пути подобраны под эту машину) |
| `.claude/skills/feature-flow/` | Командный процесс "от тикета до PR" в виде skill: разбор тикета YouTrack -> выбор тира (light/standard/deep, ADR-0010) -> OpenSpec change + грилль -> проверка спек-дельты, затем агент `test-author` пишет тесты ДО кода (QA-SDD-PROCESS.md, ADR-0016; автор реализации свои тесты не пишет, владение QA - целевое состояние) -> реализация -> ручная проверка -> ревью -> PR -> хендофф ready_to_test |
| `.claude/skills/incident-flow/` | Командный процесс работы с инцидентами: сбор улик (CybernetKZ/incident_collect) -> документ с корневой причиной (bug/misuse/infra - для misuse/infra сам документ и есть результат) -> OpenSpec change -> сначала регресс-тест (пишет агент `test-author` по сценарию инцидента), потом фикс -> проверка по инциденту -> хендофф ready_to_test |
| `ruff.toml` | Явный (explicit-select) конфиг Ruff (классика E/F + отобранные дополнения) - ставится, ТОЛЬКО если в репозитории нет своего конфига Ruff; explicit select нужен, потому что в ruff ≥0.15 набор правил по умолчанию раздулся до 400+ |
| `.spec-guard-paths` + подключение к стору | Для известных репозиториев (см. "Профили" ниже): настраивается автоматически |

## Профили

`profiles/<имя-репо>.env` подстраивает установку под известные репозитории. Когда имя целевой папки совпадает с
профилем, `install.sh` дополнительно:

- заполняет `.spec-guard-paths` реальными префиксами продакшен-кода репозитория (тесты/доки/миграции/helm values
  остаются без охраны);
- копирует payload-каталог `profiles/<имя-репо>/`, если он есть - заранее подготовленные файлы для этого репозитория
  (заполненный `AGENTS.md`, конфиг openspec, ...), никогда не перезаписывая существующие;
- подключает центральное хранилище спецификаций (store): клонирует его, если отсутствует (с разрешения), регистрирует
  (`openspec store register`) и добавляет `references:` в `openspec/config.yaml` - `openspec validate` остаётся
  зелёным на машинах/CI без стора; `openspec doctor` подскажет, как его зарегистрировать;
- пропускает Python-инструменты для не-Python репозиториев (`PROFILE_SKIP_PY=1`);
- заполняет `.claude/expected-env` из `PROFILE_ENV_FILES`, чтобы `sdd-doctor` предупреждал, если файл `.env` для
  какого-то сервиса, нужный свежему клону, отсутствует (WBN перечисляет все 8 сервисов);
- для самого репозитория-стора (`PROFILE_IS_STORE=1`): минимальная установка - только локальная регистрация и
  строгая проверка в CI, больше ничего.

Стор для сервисного репозитория доступен только на чтение. Если change в репо требует правки кросс-репо контракта,
обоснование остаётся в его `proposal.md`, а сам текст спеки правится отдельным change'ем и PR в `cybernet-specs`;
в `tasks.md` репо-change'а обязательна явная задача-связка, и репо-change не архивируется, пока этот PR открыт
(ADR-0018). Формат метаданных зависит от места: требования в локальном `openspec/specs/**` несут
`<!-- id: -->` / `<!-- enforced: -->` (их читает `spec-lint.py`), контракты стора остаются прозой с якорями
`file.py:line` (ADR-0017).

Встроенные профили: web-backend-new, voice-agent-constructor-backend,
voice-agent-postcall-analitics-backend, cybernet3.0, web-frontend-new,
conversation_flow, cybernet-specs (сам стор). Для неизвестных репозиториев применяется стандартная установка с
TODO в `.spec-guard-paths`.

## Зависимости

Проверяется при запуске: git, node/npx, uv. Если не хватает openspec CLI или youtrack-mcp, скрипт предложит их
установить (с разрешения). Если нет токена YouTrack -> скрипт покажет
https://cybernet.youtrack.cloud/users/me?tab=account-security, скрытно считает токен и сохранит его только в
`.env` youtrack-mcp (chmod 600) - никогда не в репозиторий.

## После установки (руками)

1. Заполнить TODO в `AGENTS.md`.
2. Создать `.spec-guard-paths` (префиксы путей к коду, по одному на строку), чтобы включить spec-guard -
   для известных репозиториев делается автоматически (см. "Профили"). Пока в файле нет ни одной
   не-комментарной строки, spec-guard и pre-commit-фрагмент LIVING SPEC - осознанные no-op'ы.
3. Наполнять `openspec/specs/` по одной capability за раз. Агента spec-miner кит **не поставляет** -
   используй skills `openspec-explore` / `openspec-sync-specs` либо своего майнера на уровне машины;
   прогон на conversation_flow, из которого выросла текущая конвенция, описан в
   `docs/SPEC_MINER_PILOT.md` и `docs/STORE_VERIFICATION.md`. Формат якоря -
   `<!-- enforced: path/to/file.py:ClassName.method -->`, и `spec-lint.py` проверяет **обе** половины:
   выдуманный символ делает спеку MISSING.
4. Прогнать `make sdd-doctor` и закрыть FAIL'ы. WARN'ы - это отчёт о мусоре, а не блокеры.
5. Авторизация для ИИ-ревью (по подписке, без API-ключа): токены выдаются НА КАЖДОГО разработчика, на уровне
   машины - без общего секрета GitHub. Запускать ревью локально через `make sdd-review`; ИИ-шаг в CI аккуратно
   пропускается (за секунды), если секрета нет.

Защита ветки в GitHub и обязательные проверки намеренно **не** входят в настройку: принуждение сегодня
живёт локально и остаётся консультативным (ADR-0015). Включение серверных гейтов - отдельное осознанное
решение.

## После установки: чем пользоваться

В репозиторий попадают три вида сущностей. Блокирует только третий.

**Skills** - процессы уровня промпта, которые ты вызываешь. Два поставляет кит, и они
model-invocable (агент может подхватить их сам); шесть skills `openspec-*` приходят из
`openspec init` и несут `disable-model-invocation: true` - то есть работают только по явному вызову.

| Skill | Для чего | Связка с OpenSpec |
|---|---|---|
| `/feature-flow` | тикет YouTrack (фича/багфикс) от начала до конца (8 шагов, таблица тиров) | читает `openspec/specs/` и стор, пишет `openspec/changes/<id>/intake.md`, дальше ведёт change до архивации |
| `/incident-flow` | инцидент с прода из чата | та же механика change'ей, но первый результат - документ с корневой причиной |
| `/openspec-propose` | создать change (proposal + спек-дельты + tasks) | пишет `openspec/changes/<id>/` |
| `/openspec-update-change` | поправить change в работе | перезаписывает тот же каталог |
| `/openspec-apply-change` | реализовать по change'у | читает `tasks.md` |
| `/openspec-archive-change` | закрыть выпущенный change | переносит в `openspec/changes/archive/` и вливает дельты в `openspec/specs/` |
| `/openspec-sync-specs` | привести спеки в соответствие с реальностью | перезаписывает `openspec/specs/` |
| `/openspec-explore` | узнать, что уже описано, до того как что-то писать | только чтение `openspec/` |

**Агенты** - субагенты, которым делегируется фаза. Skills они вызывать не могут, поэтому
нужный протокол зашит в каждого инлайном.

| Агент | Фаза | Модель | Связка с OpenSpec |
|---|---|---|---|
| `planner` | 2 - план | opus | **пишет** `openspec/changes/<id>/` (proposal + спек-дельты + tasks) |
| `plan-griller` | 2 - допрос плана | opus | **читает** change, возвращает готовый к вставке блок `## Grill` для `proposal.md`; сам диалог ведёт главная сессия (ADR-0012) |
| `test-author` | 3 - RED-тесты | sonnet | **читает** спек-дельту, один тест на `#### Scenario:`, трассирующий комментарий `# spec: <requirement-id> / <scenario>` |
| `executor` | 4 - реализация | sonnet | **читает** `tasks.md`, доводит RED до зелёного; не коммитит, не правит тесты, при отклонении останавливается и докладывает (ADR-0021) |
| `backend-reviewer` | 5 - ревью | sonnet | читает дифф и спеки |
| `database-reviewer` | 5 - ревью | sonnet | читает миграции и запросы |
| `repo-auditor` | в любой момент | наследует | read-only scorecard агентопригодности репо |

**Utils** - детерминированная половина. Только это и может тебя остановить.

| Util | Блокирует? | Что делает |
|---|---|---|
| `make sdd-check` | да (pre-commit + джоба CI) | `AGENTS.md` есть и ≤500 строк, `openspec validate --all --strict`, `sdd-flags`; spec-lint консультативно |
| `.claude/scripts/spec-lint.py` | только при `SPEC_LINT_STRICT=1` | свежесть спек (`> Last verified: <дата> (commit <hash>)` против `git diff` по якорям `enforced:`) + метаданные (`id`+`enforced` у каждого Requirement, уникальность id, только whitelist-ключи, никаких `#### Scenario:` под `## Invariants`) |
| `.git/hooks/pre-commit` | да | защищённые ветки, гигиена, секреты, автофикс ruff, затем `sdd-check`, если застейджены спек-файлы |
| `.claude/hooks/spec-guard.cjs` | да, как только заполнен `.spec-guard-paths` | никаких правок кода без активного change'а |
| `.claude/hooks/block-no-verify.cjs` | да | никаких `--no-verify` / `commit -n` |
| `make sdd-doctor` | нет | аудит окружения, репозитория и мусора, `--json` для машин |
| `make sdd-test` | нет | ruff + pytest, консультативно (ADR-0015); переопределяется `SDD_TEST_CMD` |
| `make sdd-review` | нет | локальное ИИ-ревью `git diff $(SDD_REVIEW_BASE)...HEAD` |
| `make sdd-index` | нет | граф graphify только для навигации (ADR-0004) |
| `make sdd-flags` | да | просроченные фича-флаги: 7 дней WARN, потом FAIL |

Корректно ли всё это связано с OpenSpec? Да, с двумя оговорками. CLI запинован на `1.7.0`
в четырёх местах (`# openspec-pin`) - поднимать версию нужно везде сразу, иначе `sdd-check` и
`sdd-doctor` разойдутся. И `openspec validate --all --strict` проверяет *структуру* (у Requirement
есть хотя бы один Scenario, у change'а есть дельты), а `spec-lint.py` - *правдивость* (существуют ли
символы, на которые указывают якоря `enforced:`, не устарела ли спека). Обе проверки идут внутри
`make sdd-check`, и одна не заменяет другую.

## Работа над новой задачей

Конвейер один, глубин три. Глубину выбираешь по таблице тиров в
`.claude/skills/feature-flow/SKILL.md` §1b (ADR-0010/ADR-0021): меняется глубина подготовки,
**гейты не меняются никогда**.

```
тикет -> intake -> change -> [гриль] -> RED-тесты -> реализация -> ревью -> PR -> архивация
```

| Тир | Когда | Конвейер |
|---|---|---|
| light | одно очевидное изменение, вопросов по дизайну нет | intake -> change -> `test-author` -> `executor` |
| standard | по умолчанию | + change пишет `planner`, + допрашивает `plan-griller` |
| deep | архитектура, кросс-репо контракт, рискованный путь данных | + исследование через `openspec instructions design`, гриль агентом |

Конкретно, для "у нас новая таска":

1. **Вызвать `/feature-flow` с id тикета.** Он делает intake-допрос и выбирает тир; всё
   нижеследующее происходит внутри него. Делать шаги руками тоже нормально - skill здесь
   чеклист, а не обёртка.
2. **Сначала читать, потом писать.** `/openspec-explore` (или стор:
   `openspec list --specs --store cybernet-specs`) показывает, что уже описано. Менять
   задокументированное поведение - это другая задача, чем добавлять новое.
3. **Создать change, а не код**: `openspec/changes/<id>/` с `proposal.md`, спек-дельтами и
   `tasks.md`. Для standard/deep это делает `planner`. Именно change разблокирует spec-guard.
4. **Гриль и ревью - в этом порядке.** `plan-griller` закаляет план; механическое ревью
   в духе `tz-review` сверяет утверждения с кодом. Это не дубли (ADR-0020): ревью первым - за
   факты, гриль после - за дизайн.
5. **`test-author` пишет падающие тесты по спек-дельтам** - по одному на `#### Scenario:`.
   RED до любого продакшен-кода (ADR-0016). Автор реализации свои тесты не пишет никогда.
6. **`executor` реализует** по `tasks.md`, пока тесты не станут зелёными. При отклонении от
   плана он останавливается и докладывает, а не импровизирует.
7. **`make sdd-test`, `make sdd-check`, `make sdd-review`**, затем агенты-ревьюверы на дифф.
8. **PR -> merge -> архивация change'а** (`/openspec-archive-change`), которая вливает дельты
   в `openspec/specs/`. Если задача затронула кросс-репо контракт, правка стора - это отдельный
   change + PR в `cybernet-specs`, и текущий change не архивируется, пока тот PR открыт (ADR-0018).

**Репозиторий может это переопределить.** Живой пример - `conversation_flow`: там вместо
`feature-flow` работает проектная трилогия `/tz -> /tz-review -> plan-griller -> test-author ->
/tz-implement`, `docs/DOCUMENTATION.md` ведётся как LIVING SPEC параллельно с `openspec/specs/`
навсегда, а `.spec-guard-paths` намеренно пуст, пока идёт конвертация (ADR-0019,
`docs/PLAN_CF_MIGRATION.md`). `feature-flow` там установлен, но используется только как источник
таблицы тиров. Всегда читай `AGENTS.md` целевого репозитория до того, как считать применимым
дефолтный процесс кита: собственные линты и гарды репозитория сильнее китовых.

## Инструменты для каждого разработчика: install.sh --machine-only

Репозиторная часть ставит файлы в репозиторий; личные инструменты живут на машине каждого разработчика (зашивать
их в каждый репозиторий раздувает контекст и дублирует состояние). Эта секция выполняется в обычном
`install.sh` или отдельно:

```bash
sdd-kit/install.sh --machine-only   # базовый набор ставится по умолчанию [Y/n]
```

**Базовый набор (ставится по умолчанию - качество выше, расход токенов ниже):**
**ponytail** (плагин: минимальные рабочие решения, экономит токены),
**rtk** (компрессор вывода шелла + глобальный хук),
**Graphify** (граф знаний репозитория - быстрее и дешевле анализ кода; имя пакета в PyPI -
`graphifyy`, ставится как `graphifyy[postgres,sql]`), **ast-grep** (кодмоды на AST для массового механического рефакторинга).
`make sdd-doctor` предупреждает, если базового инструмента не хватает.

**По желанию (y/N):** **gh-axi** и **chrome-devtools-axi**
(удобные для агента CLI-обёртки, ~/.claude/skills), **serena** (MCP для семантической навигации по коду через
uvx - от прошлой пробы остался мусор `.serena/`, который ловит секция audit в sdd-doctor, поэтому по умолчанию не ставится).

Не предлагается: **caveman** (это просто один из бенчмарк-вариантов внутри репозитория ponytail, а не отдельный
инструмент - ponytail его уже покрывает), **grill-with-docs** (командная практика, а не самостоятельная установка),
**Playwright** (chrome-devtools-axi покрывает работу с браузером), **Headroom**
(выпилен 31.07.2026: сжимает ~0-2%, ломает префикс prompt-кэша, замеры дают
+45..62% к стоимости - см. [ADR-0014](docs/ADR/ADR-0014-drop-headroom.md)).

## Configuration

- `YOUTRACK_URL` - адрес инстанса YouTrack для youtrack-mcp (по умолчанию: cybernet.youtrack.cloud).
- `YOUTRACK_MCP_DIR` - где лежит youtrack-mcp (поиск по умолчанию: ~/dev, ~/cybernet).
- `SDD_KIT_ASSUME_YES=1` - автоподтверждение установок при запуске без TTY (кроме токена).
- `SPEC_LINT_STRICT=1` - сделать нарушения свежести/метаданных спецификаций блокирующими.
- `SDD_TEST_CMD` - заменить команду `make sdd-test` (монорепозитории, стеки без pytest).
- `SDD_REVIEW_BASE` - база диффа для `make sdd-review` (по умолчанию `origin/HEAD`, фолбэк `dev`).
- `SDD_ALLOW_PROTECTED=1` - разовый обход защиты коммитов в защищённые ветки.
- `SDD_STORE_ID` / `SDD_STORE_DIR` / `SDD_STORE_GIT` - id центрального стора спецификаций,
  путь локальной копии и URL клона (по умолчанию: cybernet-specs,
  ~/cybernet/cybernet-specs, github.com/octrow/cybernet-specs).

## Документы по процессу

- `WORKFLOW.md` - весь цикл работы команды (сигнал -> влитый PR) с точкой подключения каждого инструмента.
- `QA-SDD-PROCESS.md` - отдельный процесс QA: тесты пишутся ДО реализации по
  спек-дельте OpenSpec, с проверкой прослеживаемости (каждый Scenario ⇄ один тест) и состязательной
  проверкой сгенерированных тестов. Автор реализации свои тесты не пишет никогда: сегодня их
  пишет агент `test-author`, владение фазой человеком-QA - целевое состояние (ADR-0016).

## Design notes

Формат вывода проверок следует принципам агентской эргономики [axi](https://github.com/kunchenguid/axi):
сначала главная строка с итогом, явное "0 issues" вместо тишины и конкретное предложение команды `next:`
на каждом пути с ошибкой.

Никакой магии: "skills"/"rules"/"plugins" - это промпты, добавляемые в контекст модели, - они
рекомендательные по своей природе, модель может их проигнорировать. Хуки
(pre-commit, PreToolUse/PreCompact) - это детерминированный код, и его игнорировать нельзя. Поэтому всё
принудительное живёт только в хуках и CI-проверках, и каждая установленная часть должна быть проверяемой
(проверка, строка в логе, измеримый артефакт) - секция audit в `sdd-doctor` показывает всё, что никогда не запускается.

Якоря в спеках - это пути, а не символы. Раньше `spec-lint` резолвил голый
`ClassName.method()` через индекс CamelCase->файл и `git grep` в качестве запасного
варианта; в монорепозитории это цепляло одноимённые классы из соседних сервисов, и
счётчик `enforced_files` превращался в выдумку. Резолвер убрали: пишите путь прямо в
спеке (`path/to/file.py:ClassName.method`), а символ после двоеточия остаётся для людей
и code-explorer. Старые спеки с голыми символами будут показывать MISSING, пока их не
перепишут. Символ теперь тоже проверяется: майнер, сославшийся на выдуманный
`agent.py:build_agent_session`, раньше проходил ВСЕ гейты (дефект M1 в
conversation_flow), поэтому `spec-lint` требует, чтобы символ встречался в указанном файле.

След решений по форме процесса: **ADR-0021** (субагент executor + таблица
тир->конвейер->модели), **ADR-0020** (`tz-review` и `plan-griller` - не дубли: ревью первым,
гриль после), **ADR-0019** (онбординг conversation_flow: сначала конвертировать и
верифицировать все спеки, только потом первая таска по новому процессу), **ADR-0010** (три тира
меняют подготовку, но не гейты). Индекс с однострочными выжимками - `docs/ADR/README.md`.

И сегодня даже половина с CI - консультативная, осознанно (ADR-0015): branch protection выключена,
required check не назначен, поэтому реально блокируют только локальные вещи (spec-guard, блокировщик
`--no-verify`, pre-commit). Серверные проверки - честные сигналы в логе; включение - одно отдельное
решение, отложенное, а не отменённое.

## Layout

```
install.sh            установщик: --repo-only (файлы репозитория) / --machine-only (личные инструменты)

bootstrap.sh          deprecated-обёртка -> install.sh --repo-only
setup-dev.sh          deprecated-обёртка -> install.sh --machine-only
WORKFLOW.md           весь цикл команды + живая таблица "что работает сегодня, что запланировано"
QA-SDD-PROCESS.md     половина QA: тесты до кода, по спек-дельте
profiles/             переопределения под конкретные репозитории: пути spec-guard, подключение стора, py/no-py
                      (+ необязательные payload-каталоги, копируемые в репозиторий)
templates/            всё, что устанавливается в репозитории (только на английском)
  agents/             7 субагентов (planner, plan-griller, test-author, executor,
                      backend-reviewer, database-reviewer, repo-auditor)
  skills/             командные skills (feature-flow, incident-flow)
tools/cf/             инструкции миграции conversation_flow - запускаются руками,
                      НЕ устанавливаются (mine-section, verify-section, patch2change, ...)
docs/                 ADR/ (реестр решений), GLOSSARY.md, ONBOARDING.md,
                      SDD_KIT_LAYERS.md, PLAN_CF_MIGRATION.md, DEFECTS_CF.md, ...
```
