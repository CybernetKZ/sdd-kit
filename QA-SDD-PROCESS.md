# QA-процесс в Spec-Driven Development

> **Статус: target-процесс — включён не везде.** Примеры путей и команд взяты из
> `web-backend-new` (WBN); в других репозиториях они другие. Реально действующие
> (блокирующие) гейты перечислены в [WORKFLOW.md](WORKFLOW.md), раздел
> «Status: what runs today vs what is planned» — traceability gate и QA quality
> gate пока не реализованы.

**Ключевая идея:** разработка пишет манифест фичи (OpenSpec change) ДО кода.
QA не ждёт готовый код, чтобы придумать, что тестировать - QA подключается
сразу после манифеста, ещё до того, как написана хоть одна строка реализации.

```
Dev: манифест (OpenSpec change)
        │
        ▼
QA: валидация манифеста 
        │
        ▼
QA: написание тестов из манифеста
        │
        ▼
Dev: реализация кода (spec-guard требует активный change)
        │
        ▼
CI: тесты из манифеста + contract-drift + Schemathesis + smoke/rag
        │
        ▼
CI: quality gate - валидация прохода тестов (новых по фиче и старого набора см.выше, сравнение контрактов api)
          │
          ▼
Deploy -> post-deploy contract-check (уже реализовано, см. ниже)
```

---

## Откуда берётся манифест

Манифест - это change, который разработка создаёт через `sdd-kit`, ДО начала работы над фичей:

```
openspec/changes/<change-name>/
├── proposal.md      # зачем, что меняется
├── design.md        # технический подход
├── tasks.md         # чеклист реализации
└── specs/
    └── <capability>/
        └── spec.md  # дельта требований к спекам:
                      #   ## ADDED Requirements
                      #   ### Requirement: <name>
                      #   The system SHALL <requirement>
                      #   #### Scenario: <name>
                      #   - WHEN <условие>
                      #   - THEN <результат>
```

QA имеет свой манифест, в котором учтено:

1) необходимые АС когда мы считаем что тесты валидны и их результат нас устраивает
2) последовательность шагов - какие проверки за чем идут, шаги при НЕ успешным проверках
3) манифест (или будущая КБ) дополняются исходя из новых тестов которые пишуться + туда добавляются данные по снапшоту
   контрактов

**Пример использования BDD через геркин**

```
Сценарий: Успешная авторизация
  Дано пользователь находится на странице входа
  Когда он вводит логин "admin" и пароль "12345"
  И нажимает кнопку "Войти"
  Тогда он переходит на главную страницу сервиса
  ```

## Этап 1 - Валидация манифеста (до кода)

Прежде чем разработка начнёт писать код, QA (агент) читает манифест и проверяет:

- **У каждого `Requirement` есть хотя бы один `Scenario`** с явными
  `WHEN`/`THEN` - требование без сценария нельзя протестировать.
- **`WHEN`/`THEN` измеримы**, а не расплывчаты - не "система должна работать
  быстро", а "ответ приходит быстрее N мс".
- **Задеты edge cases** - что с невалидным вводом, правами доступа, пустыми
  значениями, повторным вызовом. Если в манифесте есть только happy path -
  QA возвращает манифест на доработку ДО того, как разработка начнёт кодить.
- **Манифест не противоречит существующему контракту** - если change трогает
  API-поверхность, сверяем затрагиваемые пути/схемы с `pytest-api/specs/*.json`
  (тем же принципом, что уже работает в `test_openapi_contract_drift.py` -
  сравнение "что было" и "что заявлено", просто здесь сравниваем с манифестом,
  а не с live-свагером).

Результат этапа - не свободный текст, а **чеклист по каждому Scenario**:
тестируем/не тестируем и почему. Если хоть один `Requirement` не проходит -
change не считается готовым к разработке, QA возвращает его автору манифеста.

---

## Этап 2 - Генерация тестов из манифеста

Как только манифест прошёл валидацию, агент генерирует тесты - **по одному
тесту (или explicit-skip с причиной) на каждый `Scenario`**, не с нуля
придумывая, что проверять, а переводя `WHEN`/`THEN` в `assert`.
Возможно добавление негативных сценариев (под вопросом)

Каждый сгенерированный тест обязан нести трейсер обратно на манифест:

```python
# openspec: <change-name> / Requirement: <name> / Scenario: <name>
def test_<


scenario_slug > (api):
...
```

Это даёт то, чего сейчас нет ни у одного файла в `pytest-api/tests/` -
прямую, грепаемую связь "тест ⇄ пункт манифеста, из которого он появился".
Именно это отсутствие в своё время позволило `test_smoke.py` разойтись с
реальным контрактом (`transfer_next_day` пропало из API, а тест продолжал
слать это поле - см. `pytest-api/tests/test_openapi_contract_drift.py`,
который был написан уже постфактум, чтобы ловить именно такой дрейф).

**Adversarial-проверка сгенерированных тестов.** Тесты пишет тот же класс
агентов, что и код фичи - значит, нужен независимый агент со стороны QA, который
пытается опровергнуть каждый сгенерированный тест: "он реально проверяет
`WHEN`/`THEN` из манифеста, или это зелёная заглушка, которая пройдёт при
любом поведении кода?" Тест, который не пережил эту проверку, не мержится.

## Этап 3 - Реализация (параллельно с dev)

Разработка пишет код под тем же `openspec/changes/<name>/` (у них уже стоит
`spec-guard`-хук - правки кода без активного change блокируются). Тесты из
этапа 2 уже существуют к этому моменту - разработка может гонять их локально
по ходу реализации, а не ждать финального ревью, чтобы узнать, что сломалось.

---

## Этап 4 - CI-гейт на PR

Когда PR с реализацией открыт, обязательные проверки (в порядке из уже
существующей инфраструктуры этого репозитория):

1. **Traceability-гейт (новый):** каждый `Scenario` из
   `openspec/changes/<name>/specs/` имеет ровно один соответствующий тест
   (по трейсеру из этапа 2). Новый `Scenario` без теста - блокирует мерж.
2. **`npm run pytest:contract:dev` / `pytest:fuzz:dev`** - Schemathesis
   сверяет live-ответы API с `specs/openapiVA.json`/`openapiBACK.json`
   (уже реализовано, `pytest-api/tests/test_openapi_contract.py`).
3. **Сами тесты из этапа 2** - прогоняются как обычный pytest-сьют.
4. **`security-review`** - на диффе PR (уже доступно как skill).
5. **`quality gate`** - првоерка всех требований:
   **успешный проход написанных тестов** (негативные сценарии заведомо возможны)
   **контракты** соответствуют заявлнным - нового ничего не появилось ВНЕ манифеста разработки
   **нагрузка** (если требуется) проверена и полученные значения укладываются в описанные в QA манифесте значения

## Этап 5 - Деплой и после деплоя (уже реализовано)

Эта часть уже работает и не требует новых инструментов:

- **`contract-check`** (`.github/workflows/api-test-reusable.yml`) - при
  каждом деплое сверяет live-swagger с `specs/*.json`, печатает diff в лог
  шага, грепает `test_*.py` на упоминания удалённых полей/эндпоинтов, и
  автообновляет снапшот на следующий цикл
  (`pytest-api/tests/test_openapi_contract_drift.py`).
- **Smoke + RAG** (`api-test-reusable.yml`, jobs `smoke-test`/`rag-test`) -
  функциональные тесты по факту деплоя.
- **Allure + Qase** - отчётность, `publish-report` job.

## Что ещё не решено (открытые вопросы)

- **Формат traceability-гейта** - grep по комментарию-трейсеру достаточен для
  старта (дёшево, как `contract-drift`'s "affected tests" grep), но не
  проверяет, что тест содержательный, а не заглушка - это отдельная задача
  adversarial-верификации из этапа 2, ей нельзя подменять traceability-чек.
- **Кто пишет манифест для уже существующих (legacy) фич** - этот процесс
  описывает поток для НОВЫХ change; для существующего кода в
  `pytest-api/tests/*.py` манифестов пока нет и ретроактивно их никто не
  писал.
- **Риск-тиринг** - не каждый `Scenario` одинаково критичен; часть манифеста
  (например, косметика) могла бы мерджиться по упрощённому гейту, а
  auth/платежи/схема БД - только с обязательным ревью человека. Правило пока
  не формализовано.
