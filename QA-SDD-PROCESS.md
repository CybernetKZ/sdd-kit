# QA-процесс в Spec-Driven Development

> **Статус: target-процесс - включён не везде.** Примеры путей и команд взяты из
> `web-backend-new` (WBN); в других репозиториях они другие. Реально действующие
> (блокирующие) гейты перечислены в [WORKFLOW.md](WORKFLOW.md), раздел
> "Status: what runs today vs what is planned" - traceability gate и QA quality
> gate пока не автоматизированы (и не будут - см. этап 4).

**Ключевая идея:** разработка пишет OpenSpec change (спек-дельту: Requirements +
`#### Scenario:`) ДО кода. QA не ждёт готовый код, чтобы придумать, что
тестировать - QA подключается сразу после change'а, ещё до того, как написана
хоть одна строка реализации.

```
Dev: OpenSpec change (спек-дельта: Requirements + Scenarios)
        │
        ▼
QA: валидация спек-дельты
        │
        ▼
QA: написание тестов из спек-дельты (test-author)
        │
        ▼
Dev: реализация кода (spec-guard требует активный change)
        │
        ▼
Локальные гейты перед PR: traceability (Scenario ⇄ тест) +
                          scripts/sdd/test.sh + review.sh + security-review
        │
        ▼
PR -> ревью человека -> мерж
        │
        ▼
Deploy -> post-deploy contract-check (только там, где эта инфраструктура есть,
                                       см. этап 5)
```

---

## Откуда берётся change

OpenSpec change - документ, который разработка создаёт через `sdd-kit`, ДО
начала работы над фичей:

```
openspec/changes/<change-name>/
├── proposal.md      # зачем, что меняется
├── design.md        # технический подход
├── tasks.md         # чеклист реализации
└── specs/
    └── <capability>/
        └── spec.md  # дельта требований к спекам:
                      #   ## ADDED Requirements
                      #   ### Requirement: <name>
                      #   The system SHALL <requirement>
                      #   #### Scenario: <name>
                      #   - WHEN <условие>
                      #   - THEN <результат>
```

Requirements + `#### Scenario:` внутри change'а - это и есть спек-дельта: то,
что QA валидирует и из чего пишет тесты.

У QA свой рабочий чеклист (или будущая база знаний по проекту), в котором
учтено:

1) необходимые АС - когда мы считаем, что тесты валидны и их результат нас
   устраивает
2) последовательность шагов - какие проверки за чем идут, шаги при
   НЕ успешных проверках
3) чеклист (или будущая КБ) дополняется исходя из новых тестов, которые
   пишутся + туда добавляются данные по снапшоту контрактов

**Пример использования BDD через геркин**

```
Сценарий: Успешная авторизация
  Дано пользователь находится на странице входа
  Когда он вводит логин "admin" и пароль "12345"
  И нажимает кнопку "Войти"
  Тогда он переходит на главную страницу сервиса
  ```

## Этап 1 - Валидация спек-дельты (до кода)

Прежде чем разработка начнёт писать код, QA (агент) читает спек-дельту change'а
и проверяет:

- **У каждого `Requirement` есть хотя бы один `Scenario`** с явными
  `WHEN`/`THEN` - требование без сценария нельзя протестировать.
- **`WHEN`/`THEN` измеримы**, а не расплывчаты - не "система должна работать
  быстро", а "ответ приходит быстрее N мс".
- **Задеты edge cases** - что с невалидным вводом, правами доступа, пустыми
  значениями, повторным вызовом. Если в спек-дельте есть только happy path -
  QA возвращает change на доработку ДО того, как разработка начнёт кодить.
- **Спек-дельта не противоречит существующему контракту** - если change трогает
  API-поверхность, сверяем затрагиваемые пути/схемы с `pytest-api/specs/*.json`
  (тем же принципом, что уже работает в `test_openapi_contract_drift.py` -
  сравнение "что было" и "что заявлено", просто здесь сравниваем со
  спек-дельтой, а не с live-свагером).

Результат этапа - не свободный текст, а **чеклист по каждому Scenario**:
тестируем/не тестируем и почему. Если хоть один `Requirement` не проходит -
change не считается готовым к разработке, QA возвращает его автору change'а.

## Этап 2 - Генерация тестов из спек-дельты

Как только спек-дельта прошла валидацию, агент (`test-author`) генерирует
тесты - **по одному тесту (или explicit-skip с причиной) на каждый
`Scenario`**, не с нуля придумывая, что проверять, а переводя `WHEN`/`THEN`
в `assert`. Возможно добавление негативных сценариев (под вопросом)

Каждый сгенерированный тест обязан нести трейсер обратно на change:

```python
# spec: <requirement-id> / <scenario>
def test_<scenario_slug>(api):
    ...
```

Это даёт то, чего сейчас нет ни у одного файла в `pytest-api/tests/` -
прямую, грепаемую связь "тест ⇄ Scenario спек-дельты, из которого он появился".
Именно это отсутствие в своё время позволило `test_smoke.py` разойтись с
реальным контрактом (`transfer_next_day` пропало из API, а тест продолжал
слать это поле - см. `pytest-api/tests/test_openapi_contract_drift.py`,
который был написан уже постфактум, чтобы ловить именно такой дрейф).

**Adversarial-проверка сгенерированных тестов.** Тесты пишет тот же класс
агентов, что и код фичи - значит, нужен независимый агент со стороны QA, который
пытается опровергнуть каждый сгенерированный тест: "он реально проверяет
`WHEN`/`THEN` из спек-дельты, или это зелёная заглушка, которая пройдёт при
любом поведении кода?" Тест, который не пережил эту проверку, не мержится.

---

## Этап 3 - Реализация (параллельно с dev)

Разработка пишет код под тем же `openspec/changes/<name>/` (у них уже стоит
`spec-guard`-хук - правки кода без активного change блокируются). Тесты из
этапа 2 уже существуют к этому моменту - разработка может гонять их локально
по ходу реализации, а не ждать финального ревью, чтобы узнать, что сломалось.

---

## Этап 4 - Локальные гейты перед PR

Сервер­ного CI больше нет (ADR-0023): branch protection и required checks
сняты, `sdd-ci.yml`/`autoreview.yml` уехали в архив кита. Все обязательные
проверки перед тем, как открыть PR, разработчик запускает сам, локально:

1. **Traceability-гейт.** Каждый `Scenario` из
   `openspec/changes/<name>/specs/` имеет ровно один соответствующий тест
   (по трейсеру из этапа 2). Автоматики здесь нет и не планируется - это
   процесс-правило: ревьюер (человек, при `scripts/sdd/review.sh` - агент) проверяет
   соответствие глазами/грепом по трейсеру. Новый `Scenario` без теста -
   причина не открывать PR.
2. **`scripts/sdd/test.sh`** - локальный прогон pytest-сьюта, включая тесты,
   сгенерированные на этапе 2.
3. **`scripts/sdd/review.sh`** - AI-ревью диффа PR (включает статические находки:
   стиль, потенциальные баги, паттерны безопасности).
4. **`security-review`** (skill) - отдельный прогон на диффе, локально, до
   открытия PR.

Всё перечисленное - гейты, которые разработчик проходит сам до PR; сравнение
контрактов и проверка нагрузочных порогов из спек-дельты (если они заданы) -
часть того же `scripts/sdd/review.sh`/ручного ревью, а не отдельный автоматический
шаг.

**Инфраструктура WBN-эпохи** - применима, если в репозитории она есть; в
текущем приоритетном репо (conversation_flow) её нет. Schemathesis-проверки
(`npm run pytest:contract:dev`/`pytest:fuzz:dev`,
`pytest-api/tests/test_openapi_contract.py`) и contract-drift
(`test_openapi_contract_drift.py`) - унаследованы от `web-backend-new`
(сам репозиторий считается deprecated); там, где эта инфраструктура уже
стоит, её можно продолжать гонять локально перед PR, но она не обязательный
этап process'а в общем случае.

## Этап 5 - Деплой и после деплоя (инфраструктура WBN-эпохи)

Этот этап - не часть общего SDD-процесса, а то, что уже работает в
репозиториях, унаследовавших deploy-конвейер `web-backend-new` (сам
репозиторий считается deprecated); серверного CI в остальном ките больше нет
(ADR-0023), но deploy-time проверки конкретного репозитория - его собственное
дело:

- **`contract-check`** (`.github/workflows/api-test-reusable.yml`) - при
  каждом деплое сверяет live-swagger с `specs/*.json`, печатает diff в лог
  шага, грепает `test_*.py` на упоминания удалённых полей/эндпоинтов, и
  автообновляет снапшот на следующий цикл
  (`pytest-api/tests/test_openapi_contract_drift.py`).
- **Smoke + RAG** (`api-test-reusable.yml`, jobs `smoke-test`/`rag-test`) -
  функциональные тесты по факту деплоя.
- **Allure + Qase** - отчётность, `publish-report` job.

В текущем приоритетном репо (conversation_flow) этой инфраструктуры нет -
пункт применим только там, где она уже стоит, и не обязателен нигде ещё.

## Что ещё не решено (открытые вопросы)

- **Формат traceability-гейта** - grep по комментарию-трейсеру достаточен для
  старта (дёшево, как `contract-drift`'s "affected tests" grep), но не
  проверяет, что тест содержательный, а не заглушка - это отдельная задача
  adversarial-верификации из этапа 2, ей нельзя подменять traceability-чек.
- **Кто пишет спек-дельту для уже существующих (legacy) фич** - этот процесс
  описывает поток для НОВЫХ change; для существующего кода в
  `pytest-api/tests/*.py` спек-дельт пока нет и ретроактивно их никто не
  писал.
- **Риск-тиринг** - не каждый `Scenario` одинаково критичен; часть спек-дельты
  (например, косметика) могла бы мерджиться по упрощённому гейту, а
  auth/платежи/схема БД - только с обязательным ревью человека. Правило пока
  не формализовано.
